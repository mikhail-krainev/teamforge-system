# ADR-0019. Локальное S3-хранилище разработки и тестов: SeaweedFS вместо MinIO

Статус: принято. Дата: 2026-10-13. Фаза 6, срез 1 (S1-08). Уточняет ADR-0010 в части образа хранилища; прикладное решение ADR-0010 (загрузка через API, приватные бакеты, подписанные ссылки) не меняется.

## Контекст

План и architecture.md (раздел 1, 13.11, 13.17) предполагали MinIO как S3-совместимое хранилище в `docker-compose.yml` и в тестовом стеке. При сборке среза 1 образы MinIO оказались недоступны: `minio/minio` на Docker Hub отвечает `pull access denied`, `quay.io/minio/minio` - `401`, `bitnami/minio` отсутствует. Сообщество MinIO больше не публикует готовые образы, поэтому закрепить образ по digest (требование 13.18) и получать обновления безопасности через Renovate/Dependabot для него нельзя.

Приложению нужен только S3 API: `HeadBucket` (готовность, `healthReady`), `PutObject`/`GetObject`/`DeleteObject`, подписанные ссылки на скачивание, path-style адресация (клиент `@aws-sdk/client-s3` с `forcePathStyle: true`), приватные бакеты и ключи доступа из окружения. Нужно хранилище, которое поднимается одним контейнером за секунды, умеет статические идентичности с ключами из переменных окружения и подходит для CI (Linux, без привилегий, без кластерной инициализации).

## Решение

- Для разработки (`docker-compose.yml`) и тестов (`docker-compose.test.yml`) используется SeaweedFS (`chrislusf/seaweedfs`, Apache-2.0), образ закреплён тегом `4.48` и digest. Режим `weed server -s3`: master, volume, filer и S3-шлюз в одном процессе; порт S3 внутри сети 9000 (на хосте `127.0.0.1:9000`, в тестовом стеке `9100`). Анонимная телеметрия отключена (`-master.telemetry=false`), размер тома ограничен (`SEAWEEDFS_VOLUME_SIZE_MB`, по умолчанию 256 МБ), данные - в именованном томе (в тестовом стеке `tmpfs`).
- Идентичности S3 задаёт файл конфигурации, который `docker/seaweedfs/start.sh` собирает при старте из `S3_ACCESS_KEY` и `S3_SECRET_KEY` (файл `0600` в `/tmp` контейнера, в репозитории ключей нет; `pnpm run env:init` генерирует их случайно). Анонимный доступ запрещён.
- Бакеты `resumes` и `artifacts` (имена из `S3_BUCKET_RESUMES`, `S3_BUCKET_ARTIFACTS`) создаёт одноразовый контейнер `seaweedfs-init` (`amazon/aws-cli`, закреплён по digest) через S3 API (`head-bucket` / `create-bucket`, идемпотентно) и проверяет, что анонимный запрос к бакету получает `403`. Инициализация не зависит от SeaweedFS-специфичных утилит и подойдёт любому S3-бэкенду.
- Код `apps/api` не меняется: адрес и ключи приходят из `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. В `docker-compose.yml` `S3_ENDPOINT=http://seaweedfs:9000`.
- Интеграционный тест `apps/api/test/integration/s3-storage.test.ts` проверяет те же вызовы `HeadBucket`, что и `healthReady`, на реальном SeaweedFS: бакеты есть - 200, нет бакета или неверный ключ - 503. Тест пропускается явно, если не задан `S3_TEST_ENDPOINT`.
- Выбор хранилища для выпуска (фаза 7) этим ADR не принимается: архитектура может остаться на S3-совместимом сервисе, который будет выбран позже; граница - S3 API, поэтому замена - изменение образа и конфигурации в compose, а не кода.

## Последствия

- Плюсы: образ доступен и закрепляется по digest; один контейнер без кластерной инициализации; идентичности из переменных окружения; лицензия Apache-2.0; тот же compose-файл работает локально и в CI.
- Минусы и риски: расхождение с architecture.md (там MinIO) до фазы 7; SeaweedFS не полностью воспроизводит поведение MinIO. Не проверено в срезе 1 и должно быть проверено при первом использовании: подписанные ссылки `GET` с `response-content-disposition` и сроком 5 минут (срез 5, S5-06), `Content-Disposition`/`nosniff` при раздаче, условные запросы, ограничения на ключи объектов, сроки жизни объектов (задача очистки сирот). Каждая из этих проверок получает тест на реальном SeaweedFS в соответствующем срезе.
- В образе включён режим FIPS 140 для Go (`GODEBUG=fips140=on` в entrypoint образа); на работу S3 с подписью SigV4 это не повлияло в тестах среза 1.
- Образ тяжелее MinIO (около 190 МБ в сжатом виде); пропускная способность и поведение под нагрузкой не оценивались (нагрузочная проверка - фаза 7).

## Альтернативы

- MinIO: образы недоступны (см. контекст); сборка из исходников в CI замедляет каждый запуск и добавляет обязанность сопровождать сборку. Отклонено.
- Garage (`dxflrs/garage`, AGPL-3.0): лёгкий S3-совместимый кластерный сервис, но перед первым вызовом S3 требуется назначить раскладку кластера и создать ключ и бакеты утилитой `garage` или административным API, а ключи выдаёт сам сервис, а не конфигурация; это усложняет идентичность "ключи из env" и инициализацию в CI. В срезе 1 не запускался с приложением. Возможная замена, если SeaweedFS не пройдёт проверки из раздела "Последствия".
- RustFS (`rustfs/rustfs`, Apache-2.0): простая модель "один бинарник, ключи из переменных окружения", но проект молодой, и полнота S3 API и стабильность форматов хранения не подтверждены; для хранилища пользовательских файлов, которое не пересоздаётся при обновлении, риск выше, чем у SeaweedFS. В срезе 1 не запускался с приложением. Кандидат на повторную оценку.
- VersityGW (`versity/versitygw`, Apache-2.0): S3-шлюз поверх каталога на диске, прост и быстр для тестов; но объекты лежат как обычные файлы, это другая модель хранения, чем у промышленного объектного хранилища (атомарность перезаписи, права, пользовательские метаданные зависят от файловой системы). Годится как тестовый двойник, но не как отражение будущего хранилища. В срезе 1 не запускался с приложением.
- Встроенный двойник S3 в тестах (как `fake-s3.ts`): остаётся для модульных и API-тестов без реального хранилища, но не проверяет подпись запросов и поведение реального сервиса; поэтому дополнен проверкой на SeaweedFS.
