# ADR-0002. Межмодульные ссылки - идентификаторы без внешних ключей

Статус: принято. Дата: 2026-10-12. Фаза 3.

## Контекст

Таблицы ссылаются на сущности других модулей: `teams.membership.user_id` -> `auth.user`, `workspace.contribution.team_id` -> `teams.team` и т.д. В одной БД можно объявить FK между схемами. Спецификация (6.1) говорит, что такие ссылки "хранятся как идентификаторы без прямых запросов во владельца", но не решает вопрос FK. Удаление ПД (FR-AUTH-09) требует обезличивания, а не каскадного удаления вклада в чужих проектах.

## Решение

- FK объявляются только внутри схемы одного модуля.
- Межмодульная ссылка - колонка `uuid`/`bigint` без FK, с комментарием `-- ref <module>.<table>` в DDL и branded-типом в TypeScript (`UserId`, `TeamId`).
- Существование и права проверяются через фасад владельца в момент записи (например, `TeamsApi.assertMember`, `ProfilesApi.assertRolesExist`).
- Удаление и обезличивание распространяются событиями (`auth.user_deletion_requested`), каждый модуль чистит свои строки.
- Ночная задача `orphan-scan` сверяет межмодульные ссылки пакетными вызовами фасадов и пишет отчёт в журнал (без автоудаления).

## Последствия

- Плюсы: модуль можно вынести в отдельную БД без переделки схемы; нет каскадов, которые незаметно удаляют данные другого модуля; миграции модулей независимы; FK-проверки не берут `KEY SHARE`-блокировки на строки чужих модулей (меньше взаимного влияния блокировок, ADR-0003).
- Минусы: БД не гарантирует ссылочную целостность между модулями; возможны "висячие" ссылки при ошибке в обработчике события - их ловит `orphan-scan`, а API показывает "Удалённый пользователь"/"Недоступно".

## Альтернативы

- FK между схемами: строгая целостность, но жёсткая связь модулей, каскады противоречат обезличиванию (FR-AUTH-09 (в)), блокировки на чужих строках. Отклонено.
- FK с `ON DELETE SET NULL`: решает часть удаления, но физического удаления пользователя у нас нет (строка `auth.user` остаётся обезличенной), а связь модулей сохраняется. Отклонено.
