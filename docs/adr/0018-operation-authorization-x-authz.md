# ADR-0018. Авторизация операций: `x-authz` в контракте, проверка цепочки владения в запросе к БД

Статус: принято. Дата: 2026-10-12. Фаза 3 (по аудиту безопасности, SEC-03).

## Контекст

В контракте не было правил доступа по операциям, а у многих путей есть вложенные идентификаторы (`/teams/{teamId}/checklist-items/{itemId}/files/{fileId}`, `voteId`, `departureId`, `contributionId`, `offerId`). Типичная ошибка - проверить членство в `teamId`, а ресурс выбрать только по последнему id: участник команды A получает файл команды B (IDOR, OWASP A01). Для предложений на место не было зафиксировано, какая сторона вправе отвечать.

## Решение

- У каждой операции `openapi.yaml` расширение `x-authz`: `actor` (`public`, `github-signature`, `authenticated`, `self`, `team-member`, `team-participant`, `team-lead`, `offer-party`, `invitee`, `vote-participant`, `admin`), `chain` - идентификаторы пути в порядке владения, `rule` - дополнительное условие (например, "lead_to_user принимает только адресат, user_to_lead - только текущий тимлид").
- Guard читает `x-authz` по `operationId` при старте; операция без него не регистрируется.
- Вложенный id проверяется самим запросом к БД: репозиторный метод принимает всю цепочку и фильтрует её целиком (`WHERE f.id = :fileId AND i.id = :itemId AND i.team_id = :teamId`); методов выборки только по последнему id в репозиториях контроллеров нет (правило линтера). Id из тела проверяются так же. Чужой ресурс - 404, отсутствие роли при своём - 403.
- `self`-ресурсы берут id пользователя только из сессии; администратор не получает чужие отзывы и резюме.
- CI: проверка наличия и формата `x-authz`, генерация отрицательных тестов доступа и обязательный тест IDOR на каждый вложенный id (две команды, перекрёстные id - 404 и неизменная БД).

## Последствия

- Плюсы: правило доступа видно в контракте рядом с операцией и проверяется машинно; IDOR закрыт единым паттерном, а не вниманием автора каждого обработчика.
- Минусы: расширение нужно поддерживать при каждом изменении операции; генератор тестов - дополнительный код в срезе "каркас".

## Альтернативы

- Матрица прав в отдельном документе: расходится с контрактом. Отклонено.
- Проверка принадлежности отдельными запросами перед выборкой ресурса: лишние запросы и риск забыть звено цепочки. Отклонено.
- Политики на уровне PostgreSQL (RLS): требуют передачи пользователя в сессию БД, плохо сочетаются с PgBouncer в режиме транзакций и межмодульными границами. Отложено.
