# ADR-0004. Ключ идемпотентности: хранение в PostgreSQL, фиксация результата в бизнес-транзакции

Статус: принято. Дата: 2026-10-12. Фаза 3. Обновлено в фазе 3 по ревью архитектуры (`locked_until`, токен захвата) и аудиту (SEC-11).

## Контекст

FR-WORK-08: все изменяющие запросы принимают `Idempotency-Key`; повтор с тем же ключом и телом возвращает сохранённый ответ без повторного действия; тот же ключ с другим телом - 422; запрос в обработке - 409; срок хранения 24 ч (C-50). Повторы коррелированы с деградацией (тайм-ауты блокировок, сеть), то есть происходят именно тогда, когда дубли наиболее вероятны.

## Решение

- Таблица `platform.idempotency_key`, PK (`user_id`, `key`) - область ключа - пользователь. Ключ - UUID, генерируемый клиентом на каждое нажатие пользователя и переиспользуемый только при повторе после сетевой ошибки, тайм-аута, 429, 503 и 5xx; любой итоговый ответ (2xx, сохранённый 4xx) завершает попытку, и следующая получает новый ключ (иначе сохранённый отказ состояния, например `GITHUB_REQUIRED`, воспроизводился бы до 24 часов после устранения причины).
- Захват - `INSERT ... ON CONFLICT DO NOTHING RETURNING` (атомарно, без "проверить, затем вставить"), статус `in_progress`, `locked_until = now + 120 s`, новый `lock_token`. 120 с больше худшего случая запроса: каждая попытка транзакции ограничена 15 с, повторов не более 3, запрос целиком - жёстким сроком 70 с (architecture.md 12.1); финальный `UPDATE` ключа в бизнес-транзакции проверяет `lock_token` (fencing): если захват истёк и перехвачен, транзакция откатывается с 409, поэтому двойного эффекта нет даже при нарушении оценки срока.
- Конфликт: другой `request_hash` (SHA-256 от operationId, параметров пути и канонического тела) или другой `operationId` - 422 `IDEMPOTENCY_KEY_REUSED`; `completed` - повтор сохранённого ответа с `Idempotent-Replayed: true`; `in_progress` - 409 `IDEMPOTENCY_IN_PROGRESS`; истёкший захват - перехват условным `UPDATE`.
- Результат (`completed`, статус, тело) записывается последним оператором бизнес-транзакции, поэтому эффект и сохранённый ответ фиксируются атомарно. Доменные отказы 4xx сохраняются отдельным оператором; 5xx и `LOCK_TIMEOUT` удаляют захват - повтор выполнит операцию.
- Заголовок обязателен на изменяющих операциях `/v1` (400 без него). Исключения: маршруты Better Auth, вебхук GitHub (идемпотентность по `X-GitHub-Delivery`), безопасный `previewInvitation`, `cancelDeletionRequest` (идемпотентна по одноразовому токену).
- TTL 24 ч, очистка раз в час. Фоновые задачи не используют этот механизм: у них детерминированные `jobId` и уникальные ограничения, поэтому срок хранения ключа не должен перекрывать мёртвую очередь.
- Тела ответов с ПД (`saveMyProfile`, `uploadResume`, `confirmResumeFields`) не сохраняются: хранится статус и id ресурса, тело при повторе перечитывается с текущей проверкой прав; строки пользователя удаляются в саге удаления (SEC-11).

## Последствия

- Плюсы: "эффект без сохранённого ответа" невозможен; повтор после 503 безопасен; гонка двух повторов решается уникальным ключом.
- Минусы: два дополнительных оператора на изменяющий запрос; таблица растёт пропорционально числу изменяющих запросов за сутки (при 30 rps пиковой записи - сотни тысяч строк, допустимо, индекс по `expires_at`).

## Альтернативы

- Redis `SET NX` с ответом: не атомарен с записью в PostgreSQL - сбой между коммитом и записью ответа даёт повторное действие. Отклонено.
- Ожидание завершения первого запроса вместо 409: противоречит FR-WORK-08 и держит соединение. Отклонено.
- Ключ, вычисляемый сервером из тела: два законных одинаковых действия (например, два разных приглашения на одно место) склеились бы. Отклонено.
