# ADR-0001. Модульный монолит, схема PostgreSQL на модуль и проверка границ

Статус: принято. Дата: 2026-10-12. Фаза 3.

## Контекст

Оркестратор задаёт модульный монолит из восьми модулей (auth, profiles, teams, matching, playbooks, workspace, github, rewards): модуль обращается к другому только через публичный интерфейс, не в чужие таблицы, и должен выноситься в сервис без переписывания. Один VPS, небольшая команда агентов, MVP. Нужен механизм, который не даёт границам "размыться" при параллельной работе нескольких агентов.

## Решение

- Одна кодовая база `apps/api`, модули - NestJS-модули в `src/modules/<m>/` с подкаталогом `internal/` и единственной поверхностью импорта `public.ts` (интерфейс фасада, DTO, типы событий, токены портов).
- Одна БД PostgreSQL, но отдельная схема на модуль (`auth`, `profiles`, ...) и `platform` для общего слоя (outbox, inbox, идемпотентность). Drizzle-таблицы модуля объявлены через `pgSchema('<m>')` и лежат в `internal/db/`.
- Границы проверяются автоматически в CI: `eslint-plugin-boundaries` (импорт только `public.ts` другого модуля), `dependency-cruiser` (разрешённые рёбра графа из architecture.md 2.2, `no-circular`, правило "rewards не зависит от profiles"). Нарушение роняет сборку.
- Синхронные вызовы идут по ацикличному графу; обратные направления - порты (ADR-0013) или события outbox (ADR-0005).
- Фронтенд собирает составные страницы из нескольких эндпоинтов разных модулей вместо того, чтобы один модуль агрегировал чужие данные.

## Последствия

- Плюсы: модуль виден в БД и коде как единица; вынос модуля в сервис сводится к переносу схемы и замене фасада на HTTP-клиент; агенты могут работать над разными модулями параллельно.
- Минусы: больше пакетных вызовов фасадов вместо JOIN по чужим таблицам; приходится держать проекции (`candidate_stats`, `review_eligibility`) и снимки (`project_completion.snapshot`).
- Отчёты, которым нужны данные нескольких модулей (антифрод), строятся из фактов, которые модули отдают через фасады.

## Альтернативы

- Микросервисы сразу: распределённые транзакции для вступления и автодобавления, сетевые сбои, лишние процессы на одном VPS. Отклонено.
- Монолит без явных границ (общая схема `public`, свободные JOIN): быстрее на старте, но требование "не в чужие таблицы" держалось бы только на ревью. Отклонено.
- Отдельные БД на модуль: исключает разрешённые транзакции T1-T7 (ADR-0013) и усложняет эксплуатацию. Отклонено.
