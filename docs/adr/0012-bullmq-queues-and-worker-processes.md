# ADR-0012. Процессы api / worker / resume-worker и очереди BullMQ

Статус: принято. Дата: 2026-10-12. Фаза 3. Обновлено в фазе 3 по аудиту безопасности (`docs/security-review-phase3.md`, SEC-01, SEC-05, SEC-10, SEC-11).

## Контекст

Тяжёлая работа идёт в очередях (разбор резюме, подбор, синхронизация GitHub, проверки ссылок, зачёт, уведомления); задачи идемпотентны, до 5 повторов с экспоненциальной задержкой, мёртвая очередь (spec 5.1). Разбор резюме - недоверенные файлы, изоляция без доступа к БД и сети (spec 5.3). Нужны таймеры (голосование, испытательный срок, охлаждение, решения после выхода).

## Решение

- Одна кодовая база `apps/api`, три точки входа: `api` (HTTP, WebSocket, вебхуки; без процессоров очередей), `worker` (все процессоры, ретранслятор outbox, планировщик), `resume-worker` (отдельный образ: только BullMQ-процессор `resume-parse` в отдельном экземпляре `redis-resume`; разбор unpdf + mammoth в одноразовом дочернем процессе под отдельным uid с лимитом 256 МБ и тайм-аутом 15 с; без переменных БД и S3, без доступа к основному Redis, MinIO и интернету; read-only ФС, non-root, лимиты CPU и памяти контейнера; ADR-0010, architecture.md 13.15), `link-checker` (тот же образ, процессор очереди `link-check`: исходящие проверки URL пользователей SSRF-клиентом; без БД и S3, к Redis - ACL-пользователем только на ключи своей очереди; результат - коды, записывает `worker`; SEC-05).
- Очереди по назначению (architecture.md 13.12), у каждой своя конкурентность и политика повторов. Таймеры - отложенные задачи с детерминированным `jobId`, плюс сканеры по индексам сроков раз в минуту на случай потери задач в Redis.
- Формат `jobId` (проверено по исходникам BullMQ 6): без `:` (допустимо ровно три сегмента, иначе исключение при постановке), не целое число, части соединяются `_`; задача с существующим id не добавляется, пока старая хранится в любом состоянии (включая завершённую), поэтому id, которым нужна повторная постановка (`recompute_*`, `auto-add_*`), включают временное окно, а их очереди работают с `removeOnComplete: true` (architecture.md 13.12). Платные функции BullMQ Pro (группы, пакеты) не используются.
- Идемпотентность каждой задачи: детерминированный `jobId` и проверка состояния под блокировкой строки или уникальным ограничением; обработчики можно безопасно запускать параллельно (тесты CC-3, CC-4, CC-6).
- Redis с AOF (`appendfsync everysec`), `maxmemory-policy noeviction` (требование BullMQ). `request_id` передаётся в данные задачи. Укрепление (SEC-10): ACL-пользователь на процесс с минимальными ключами и командами, `default` выключен, опасные команды запрещены, порт не публикуется, AOF на зашифрованном томе, проверка имени пользователя при старте. Данные задач не содержат ПД сверх id (адрес письма читается при отправке, SEC-11).

## Последствия

- Плюсы: API отвечает быстро и не зависит от GitHub и разбора файлов; падение разбора резюме не задевает остальное; воркеры масштабируются отдельно.
- Минусы: три образа/конфигурации; Redis становится критичным компонентом (очереди) - мониторинг глубины очередей в `/health/ready` и метриках.

## Альтернативы

- Процессоры в процессе api: тяжёлые задачи и GitHub-лимиты влияют на задержку API. Отклонено.
- `pg-boss` (очередь в PostgreSQL): совместимость с PgBouncer (LISTEN) и нагрузка на БД; BullMQ уже в стеке. Отклонено.
- cron в контейнере для таймеров: не точен, не распределён, не идемпотентен сам по себе. Отклонено.
