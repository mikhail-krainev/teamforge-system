# ADR-0014. Подбор: предрасчёт рекомендаций и автодобавление по окнам запуска

Статус: принято. Дата: 2026-10-12. Фаза 3. Обновлено в фазе 3 по ревью архитектуры.

## Контекст

FR-MATCH-01: рекомендации отдаются из предрасчитанного результата. FR-MATCH-05..07: автодобавление по событиям и раз в минуту (C-38), роль, для которой проект нашёлся раньше, при одновременности - роль с более высоким приоритетом; два параллельных запуска не добавляют кандидата дважды. FR-MATCH-12: жёсткие фильтры и взвешенная сумма (C-44), порог 0.5 (C-45). Обучаемых моделей в MVP нет.

## Решение

- Оценка - детерминированная функция (`matching/internal/score.ts`) с весами из конфигурации; формула и фильтры - architecture.md 6.1-6.2.
- Предрасчёт в таблицу `match_candidate` задачами `matching-recompute` с дедупликацией по месту и пользователю в окне 5 с (`jobId = recompute_seat_<id>_<окно>`; постоянный id отбрасывал бы пересчёты после первого, пока завершённая задача хранится; очередь с `removeOnComplete: true`; задержка 5 с) и суточным полным пересчётом; API только читает таблицу. Запись - upsert по `(seat_id, user_id)` с условием по `computed_at` и удалением только устаревших пар после прогона (не DELETE + INSERT), поэтому читатель никогда не видит пустого списка (ревью архитектуры).
- Автодобавление: пары упорядочиваются по `(окно(match_possible_at), приоритет, -score, opened_at, seat_id)`, где окно - номер минутного интервала запуска; "одновременно" = в одном окне. Заявки обрабатываются по `enqueued_at` (справедливость к дольше ждущим). Каждая попытка - транзакция T2 с блокировками пользователь -> заявка -> команда -> место; повтор или параллельный запуск безопасен.
- Отказ из-за лимита проектов, GitHub или согласия пропускает всю заявку до следующего запуска; занятое место - переход к следующей паре.
- Возврат исключённого: восстановление старой заявки с прежним `enqueued_at` или, если уже есть новая, перенос исключения команды и более раннего `enqueued_at` в неё; время в команде не учитывается в ожидании (`paused_seconds`).
- Уникальности `application_role (application_id, priority)` и `profile_role_pref (user_id, ordinal)` - `DEFERRABLE INITIALLY DEFERRED`: обмен приоритетами выполняется одним сохранением без промежуточного нарушения; эти ограничения не используются как цель `ON CONFLICT`.

## Последствия

- Плюсы: чтение рекомендаций - один индексный запрос; поведение автодобавления воспроизводимо в тестах (оба порядка и ничья, FR-MATCH-06); корректность не зависит от единственности планировщика.
- Минусы: рекомендации отстают от изменений на секунды; при большом числе пар полный пересчёт растёт как места x кандидаты на роль (для MVP - до тысяч пар, приемлемо).

## Альтернативы

- Расчёт рекомендаций в запросе: противоречит FR-MATCH-01, N+1 по профилям. Отклонено.
- Глобальное оптимальное назначение (венгерский алгоритм): не соответствует правилу "раньше найденная роль" и сложнее объяснить пользователю. Отклонено.
- "Одновременно" = точное равенство меток времени: практически никогда не срабатывает, приоритет терял бы смысл. Отклонено.
