# ADR-0008. Интеграция с GitHub через GitHub App: только чтение, вебхуки и суточная сверка

Статус: принято. Дата: 2026-10-12. Фаза 3. Обновлено в фазе 3 по аудиту безопасности (`docs/security-review-phase3.md`, SEC-02, SEC-06).

## Контекст

Своей доски задач нет: вклад считается по закрытым Issues и слитым PR (FR-GH-05, FR-GH-11). components.md 3 рекомендует GitHub App (гранулярные права, токены установки на 1 ч, масштабируемые лимиты, один вебхук на установку); Projects v2 не годится как основа (нет вебхуков для App). Нельзя доверять логину (переименование), датам коммитов (подделка), автоматической повторной доставке вебхуков (не гарантирована).

## Решение

- GitHub App с правами Repository: Metadata, Issues, Pull requests, Actions - только чтение. Actions: read нужен сигнальной проверке `ci_workflow` и запрашивается сразу (добавление права позже требует повторного одобрения у каждого владельца установки). Contents не запрашивается: коммиты и авторы для проверки репозитория берутся из `GET /repos/{id}/contributors` (по таблице прав GitHub достаточно Metadata read); Contents: read добавляется только отдельным решением, если прототип покажет, что данных `contributors` недостаточно (architecture.md, Р-9, 7.1). Подписки: `issues`, `pull_request`, `pull_request_review`, `installation`, `installation_repositories`, `repository`.
- Вход пользователей - тот же App (user-to-server OAuth, Account permission Email addresses: read; запасной вариант - отдельное OAuth App, переменные `GITHUB_OAUTH_*` по умолчанию равны переменным App). Установка: включено "Request user authorization (OAuth) during installation", поэтому GitHub возвращает `code` на первый Callback URL App (`/api/v1/github/setup`), а не на Setup URL; одноразовый `state` в Redis (10 мин, привязан к команде и пользователю) проверяется там же, и по `code` подтверждается, что пользователь имеет доступ к установке (`GET /user/installations`); пользовательский токен сразу отбрасывается. Результат - строка `github.installation_grant (installation_id, team_id, user_id)`: установка привязывается к пользователю, подтвердившему доступ через `GET /user/installations`, и к команде, для которой он тимлид (SEC-02). `listAvailableRepositories` и `linkRepository` работают только при действующем grant текущего тимлида для этой команды, иначе 404 `INSTALLATION_NOT_GRANTED`; сам `installationId` из запроса прав не даёт. Grant отзывается при удалении установки, смене тимлида, выходе пользователя и удалении ПД. Привязка репозитория - частичный уникальный индекс по `repository_id` (CC-9).
- Вебхук: проверка `X-Hub-Signature-256` по сырому телу за постоянное время, вставка `webhook_delivery` по `delivery_id` (`ON CONFLICT DO NOTHING`), задача BullMQ с `jobId = delivery_id`, ответ 202. Обработка в воркере, полезная нагрузка проверяется zod; после обработки тело удаляется.
- Атрибуция по числовым `repository.id` и `user.id`; время - серверное `received_at`. Исполнитель задачи - assignee, иначе автор закрывающего PR; вклад PR - автор. Роль вклада - метка `role:<code>` или основная роль (FR-WORK-17).
- Суточная сверка с ETag (304 не расходует лимит) догоняет пропущенные доставки; `plugin-throttling` и `plugin-retry`.
- Токен установки - по требованию, кэш в Redis 55 мин (зашифрован), в БД не хранится; ключ App, секрет вебхука, client secret - только окружение, проверка при старте.
- Порядок и повтор вебхуков (SEC-06): `gh_item.source_updated_at` из GitHub, условный upsert только при более новом `updated_at`, события вклада - только при реальной смене состояния; разрушительные события (`installation.deleted`, `repository.*`) перепроверяются через API перед отвязкой; доставки по непривязанным репозиториям пишутся как `ignored` без тела; вебхук вне общего лимита по IP, свой лимит на `installation_id`; при расхождении источник истины - суточная сверка.

## Последствия

- Плюсы: минимальные права (только чтение), лимиты на установку, а не на сервис; устойчивость к потере вебхуков; дубли исключены уникальными ключами.
- Минусы: тимлид должен быть способен установить App на репозиторий (владелец или админ организации); смена тимлида не переносит установку (уведомление, spec 9.5); пакеты Octokit - только ESM, поэтому `apps/api` собирается как ESM на NestJS 12 (ESM-пакет), Node.js 22+ (architecture.md, 17.3).

## Альтернативы

- OAuth App со scope `repo`: доступ на запись ко всему коду пользователя, общий лимит 5000/ч на пользователя. Отклонено.
- Опрос API без вебхуков: задержка и расход лимита. Отклонено (опрос только как суточная сверка).
- Projects v2 как источник задач: нет вебхуков для App, ограничения для личных досок. Отклонено (вторая версия, опционально).
