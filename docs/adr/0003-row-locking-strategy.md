# ADR-0003. Стратегия блокировок: строки, единый порядок, тайм-аут, совместимость с PgBouncer

Статус: принято. Дата: 2026-10-12. Фаза 3.

## Контекст

Оркестратор требует: занятие роли, вступление, автодобавление, голосование, переход этапа, зачёт - одна транзакция с блокировкой строки или уникальным ограничением; проверка "свободно ли" без блокировки запрещена; на каждый сценарий тест с параллельными запросами. Spec 5.1 задаёт порядок "пользователь, заявка, команда, место" и тайм-аут блокировки 5 с (C-62). Соединения идут через PgBouncer в режиме транзакций: сессионное состояние между транзакциями не сохраняется.

## Решение

- Пессимистические блокировки строк (`SELECT ... FOR UPDATE` для изменяемой строки, `FOR NO KEY UPDATE` для родительских строк, чтобы не блокировать вставки дочерних строк с FK) в сценариях с инвариантами "не больше N" (места, размер команды, лимит проектов, голосование, переход этапа, зачёт).
- Уникальные (часто частичные) индексы как вторая линия и как основной механизм там, где инвариант - "не больше одного" (активный держатель места, одна активная заявка, одно открытое голосование, один открытый этап, одна запись завершения, `delivery_id`, `repository_id`).
- Оптимистическая блокировка (`version`) для редактируемых сущностей (пункты чек-листа, профиль, места, заявка): условный `UPDATE ... WHERE version = :v`, иначе 409.
- Единый глобальный порядок блокировок из 11 уровней (architecture.md 12.1), расширяющий порядок spec. Внутри уровня - по возрастанию `id`.
- `SET LOCAL lock_timeout = '5s'` и `SET LOCAL statement_timeout = '10s'` первым оператором; `55P03` -> 503 `LOCK_TIMEOUT` (безопасно повторить с тем же ключом идемпотентности); `40P01`/`40001` -> до 3 повторов транзакции.
- Изоляция `READ COMMITTED`.
- Совместимость с PgBouncer (transaction pooling): только `SET LOCAL`; никаких сессионных advisory-блокировок (`pg_advisory_lock`) - при необходимости только `pg_advisory_xact_lock`; без `LISTEN/NOTIFY`; драйвер `postgres` с `prepare: false` (без именованных подготовленных выражений); миграции через прямое подключение.
- Время в условиях блокировочных транзакций передаётся параметром из `Clock`, не `now()`.

## Последствия

- Плюсы: поведение детерминировано и проверяемо тестами-гонками; нет зависимости от `SERIALIZABLE` и повторов при каждой гонке; инварианты видны в схеме.
- Минусы: блокировка строки команды сериализует все вступления и действия тимлида в одной команде (до 8 человек - приемлемо); строка пользователя сериализует его вступления (приемлемо); нужно дисциплинированно соблюдать порядок блокировок (ревью + тест "все сценарии одновременно" без дедлоков).

## Альтернативы

- `SERIALIZABLE` везде: меньше ручных блокировок, но частые `40001` под нагрузкой гонок, повторы с непредсказуемой задержкой и сложнее объяснимые ошибки пользователю. Отклонено.
- Advisory-блокировки по ключу (команда, пользователь): сессионные несовместимы с PgBouncer, транзакционные не видны в схеме и легко забываются. Отклонено (оставлены как резерв).
- Распределённые блокировки в Redis (Redlock): вторая система согласования поверх БД, не атомарна с записью. Отклонено.
