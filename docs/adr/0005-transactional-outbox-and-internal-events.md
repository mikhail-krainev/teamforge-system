# ADR-0005. Transactional outbox и внутренняя шина событий на BullMQ

Статус: принято. Дата: 2026-10-12. Фаза 3. Обновлено в фазе 3 по ревью архитектуры (мёртвые события, сканеры).

## Контекст

Модули согласуются асинхронно: вклад из GitHub попадает в workspace, завершение проекта запускает охлаждение в rewards, открытие места - подбор, удаление ПД - шаги во всех модулях, изменения - события реального времени. Публикация события после коммита в отдельную систему (Redis) может потеряться при сбое процесса, публикация до коммита - сообщить о несостоявшемся изменении. Доставка в BullMQ - "не менее одного раза".

## Решение

- Событие пишется в `platform.outbox_event` в той же транзакции, что и изменение.
- Ретранслятор в процессе `worker` (опрос раз в 250 мс и "толчок" через Redis после коммита) читает неопубликованные строки `FOR UPDATE SKIP LOCKED`, создаёт по задаче BullMQ в очереди `events` на каждого подписчика с `jobId = <consumer>_<eventId>` (id BullMQ не содержит `:`, см. architecture.md 13.12), публикует сигнал реального времени (ADR-0011) и ставит `published_at`.
- Потребитель обрабатывает событие в своей транзакции и в ней же вставляет `platform.inbox_event (consumer, event_id)`; конфликт PK означает "уже обработано".
- Порядок доставки не гарантируется ни внутри агрегата, ни между агрегатами. Группы BullMQ (`group`) - функция платной BullMQ Pro, в стеке её нет, и очередь `events` работает с конкурентностью 20. Решение: обработчик не опирается на порядок и на содержимое нагрузки, а по `aggregate_id` читает текущее состояние через фасад владельца (или проверяет его под блокировкой) и приводит свою проекцию к нему; событие - только повод. Тест на каждого потребителя: пара событий в обратном порядке даёт то же итоговое состояние.
- Полезная нагрузка - идентификаторы и статусы, без ПД; версия схемы `v`. Типы событий экспортируются из `public.ts` модуля-издателя.
- Повторы: 5 попыток с экспоненциальной задержкой, затем `failed` (мёртвая очередь), журнал error и метрика. Очистка: outbox 7 дней после публикации, inbox 14 дней.
- Мёртвые события: после последней попытки строка `platform.event_dead_letter` (только id и текст ошибки без ПД) хранится до разбора, независимо от очистки outbox и `removeOnFail`. Повтор - CLI `events:replay` (фильтры по потребителю, типу, времени; `jobId = <consumer>_<eventId>_r<n>`); идемпотентность даёт `inbox_event`. Для событий, без которых теряется бизнес-эффект, есть сканеры состояния: `credit-run-scan` (`project_completion` без `credit_run`), `review-eligibility-scan` (architecture.md 4, 10.1).

## Последствия

- Плюсы: нет потерянных и "фантомных" событий; повторная доставка безопасна; модули не знают друг о друге в рантайме.
- Минусы: задержка доставки 0,25-1 с; дополнительная запись на каждое изменение; обработчики обязаны быть "перечитать и привести" (идемпотентны по состоянию), а не "применить дельту из нагрузки"; это дороже на один чтение фасада, но исключает зависимость от порядка.

## Альтернативы

- Прямой вызов фасада вместо события: создаёт циклы зависимостей (architecture.md, Р-1). Отклонено для асинхронных реакций.
- PostgreSQL `LISTEN/NOTIFY`: несовместим с PgBouncer в режиме транзакций и не хранит сообщения. Отклонено.
- Внешний брокер (Kafka, RabbitMQ): лишний процесс на одном VPS; BullMQ и Redis уже есть в стеке. Отклонено.
- Публикация в BullMQ после коммита без outbox: теряет события при сбое между коммитом и публикацией. Отклонено.
