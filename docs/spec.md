# Teamforge: спецификация

Версия: 1 (фаза 2). Дата: 2026-10-12. Язык: русский. Спецификация написана без интервью с пользователем: ответы взяты из `docs/orchestrator.md` (главный источник), `docs/decisions.md`, `docs/status.md`, `docs/research/components.md`, `docs/research/methodologies.md`, `docs/backlog.md`. Всё, чего в них нет, помечено **[решение автора]** и подлежит подтверждению. Содержание сценариев проектов (этапы, шаги, шаблоны) лежит в `docs/playbooks.md`; здесь описан только их формат как данных (FR-PLAY).

Карта модулей (Phase 0 скилла spec-driven-development) уже задана в оркестраторе и принята как утверждённая: auth, profiles, teams, matching, playbooks, workspace, github, rewards. Направление зависимостей (модуль вызывает только публичный интерфейс нижележащего): auth <- profiles <- playbooks <- teams <- matching; teams, playbooks <- workspace <- github (github сообщает workspace о событиях через интерфейс workspace); teams, workspace, github, profiles <- rewards. Циклов нет: вызовы "вверх" (например, matching -> teams.joinAuto) идут только через публичные интерфейсы и очередь событий. Детали интерфейсов - в `docs/architecture.md` (фаза 3).

Шесть областей спецификации (скилл): цель - раздел 1; команды - раздел 1.4; структура проекта - 1.5; стиль кода - 1.6; стратегия тестирования - 5.9; границы "всегда / спросить / никогда" - 1.7.

## 1. Цель и границы MVP

### 1.1 Цель

Бесплатная веб-платформа для студентов и начинающих специалистов из России и СНГ. Пользователи собираются в команды и проходят полный цикл создания продукта (идея, разработка, релиз) по готовому сценарию. Результат для пользователя: релевантный командный опыт и проект для резюме, подтверждённый косметическими наградами. Рейтингов, уровней пользователей и сравнений между людьми нет.

Критерии успеха MVP:
- пользователь может зарегистрироваться, заполнить профиль, создать команду либо встать в очередь и оказаться в команде;
- команда проходит маршрут веб-сервиса или ML-продукта в рабочем пространстве и завершает проект;
- участник, выполнивший условия зачёта, получает награды;
- все сценарии конкурентного доступа (раздел 5.1) покрыты тестами с параллельными запросами.

### 1.2 Входит в MVP

Всё из раздела "Продукт" оркестратора: профиль и резюме; команды, роли, совмещение двух ролей, несколько проектов, лимит активных проектов, выход участника и тимлида с голосованием; подбор, очередь на несколько ролей с приоритетами, автодобавление, испытательный срок, витрина спроса, приглашения друзей; маршрут проекта как данные (два типа продукта: веб-сервис и ML-продукт), запасные шаги, просрочка; рабочее пространство (чек-лист этапа, лента задач и вклад из GitHub, файлы в S3); награды, антифрод, приватные отзывы; удаление персональных данных; вход через GitHub OAuth и email (magic link).

### 1.3 Вторая версия (в MVP не делаем, записано в `docs/backlog.md`)

Остальные типы продукта (мобильный, бот, игра, CLI и др.), встроенный редактор документов, встроенная доска для мозговых штурмов, чат реального времени, обучаемые модели подбора, английский интерфейс (строки уже в словарях), значок "Коллекционер форматов" (4 типа продукта), опрос Projects v2, антивирус ClamAV, пароль как способ входа (включается только если magic link недоставляем), OCR сканов резюме.

Никогда не разрабатываем своё: видеосвязь (только внешняя ссылка), хостинг кода, код-ревью и доска задач (GitHub через интеграцию), файловый диск общего назначения (только вложения к артефактам), авторизация (Better Auth).

### 1.4 Команды (приводятся как контракт для CI и агентов; точные скрипты создаются в срезе "каркас")

```
Установка:      pnpm install --frozen-lockfile
Разработка:     docker compose up --build            (web :3000, api :4000, MinIO, Redis, PostgreSQL, PgBouncer)
Проверка типов: pnpm -r run typecheck
Линтер:         pnpm -r run lint
Юнит/интегр.:   pnpm -r run test                      (Vitest)
Сквозные:       pnpm --filter web exec playwright test
Миграции:       pnpm --filter api exec drizzle-kit generate  /  drizzle-kit migrate
Контракт:       pnpm --filter shared run generate     (типы из OpenAPI)
Сборка:         pnpm -r run build
```
Менеджер пакетов pnpm - [решение автора] (стек оркестратора его не фиксирует; подтверждается в фазе 3). Node.js и Docker на машине сейчас нет (status.md): нужны до фазы 5.

### 1.5 Структура репозитория

```
apps/web         Next.js + React: интерфейс, словари i18n
apps/api         NestJS на Fastify: модули auth, profiles, teams, matching, playbooks, workspace, github, rewards; воркеры BullMQ
packages/shared  типы из OpenAPI
docs             orchestrator.md, decisions.md, spec.md, playbooks.md, architecture.md, adr/, research/
```
Тесты лежат рядом с модулем (`*.test.ts`), сквозные - в `apps/web/e2e`. Миграции Drizzle - в `apps/api/drizzle`.

### 1.6 Стиль кода

Код и комментарии на английском, документы на русском. Функции до 50 строк, файлы до 800 строк, вложенность до 4, явная обработка ошибок, без отладочного вывода. Пример границы модуля:

```ts
// teams/public.ts - the only import surface other modules may use
export interface TeamsApi {
  joinSeat(input: JoinSeatInput, idempotencyKey: string): Promise<JoinSeatResult>;
}
```

### 1.7 Границы для агентов

- Всегда: валидация входа схемой на границе; параметризованные запросы; миграции только через Drizzle; тест с параллельными запросами на каждый сценарий 5.1; числа из конфигурации (раздел 7), не из кода; соблюдать правила "Правила для всех агентов" оркестратора.
- Спросить сначала: отклонение от стека; новая зависимость; изменение контракта OpenAPI после фазы 3; изменение числовых констант из раздела 7; расширение границ MVP.
- Никогда: секреты, `.env`, токены GitHub и резюме в репозитории; запросы в чужие таблицы модуля; проверка "свободно ли" без блокировки; коммиты в main; удаление падающих тестов.

## 2. Роли пользователей

| Роль | Кто | Что может | Чего не может |
|---|---|---|---|
| Гость | Не вошёл | Видеть лендинг, политику ПД, список типов продукта; войти или зарегистрироваться | Видеть профили, команды, витрину спроса |
| Пользователь | Вошёл, дал согласие на ПД | Вести профиль, загружать резюме, искать команды, создавать команду (становится тимлидом), вставать в очередь, получать приглашения, видеть витрину спроса, получать отзывы | Вступать в команду без привязанного GitHub (FR-AUTH-05) |
| Кандидат в очереди | Пользователь с активной заявкой поиска (не более 1 заявки) | Всё, что пользователь; до 5 ролей с приоритетами; быть автоматически добавленным в команду | Иметь вторую активную заявку |
| Участник | Активный член команды (до 2 ролей в проекте); не более 2 активных проектов одновременно | Видеть рабочее пространство команды, закрывать пункты чек-листа, загружать артефакты, проверять чужие пункты, голосовать за тимлида, оставлять отзывы коллегам, выйти | Переводить этап, завершать проект, исключать участников |
| Тимлид | Участник, владеющий командой (один на команду) | Всё, что участник; описывать роли и места, помечать роль желательной, приглашать, исключать автодобавленного в испытательный срок, выбирать замену при выходе, назначать исполнителя запасного шага, привязывать репозиторий, переводить этап, подтверждать участие в этапе, завершать проект | Менять результаты зачёта и награды |
| Администратор справочников | Выдаётся вне интерфейса (переменная окружения / команда CLI) [решение автора] | Добавлять и отключать роли, теги стека, типы продукта, загружать сценарии (FR-PLAY-05); разбирать очередь ручной проверки антифрода (FR-REW-16) [решение автора: роль администратора совмещает справочники и модерацию] | Читать резюме и отзывы, править вклад и награды вручную (только подтвердить или снять флаг антифрода) |

Системные акторы: воркеры BullMQ (разбор резюме, подбор, синхронизация GitHub, проверки ссылок, зачёт, уведомления), планировщик (таймеры голосования, испытательного срока, охлаждения).

## 3. Пользовательские сценарии

### auth
1. Гость нажимает "Войти через GitHub", разрешает доступ, принимает согласие на ПД и попадает в профиль.
2. Гость вводит email, получает одноразовую ссылку (15 минут), входит, принимает согласие. Перед вступлением в команду привязывает GitHub.
3. Пользователь запрашивает удаление данных: сразу теряет доступ, в течение 30 дней данные удаляются или обезличиваются.

### profiles
1. Пользователь заполняет профиль: стек, опыт, сильные и слабые стороны, желаемые роли с уровнем, часовой пояс, доступность.
2. Загружает резюме (PDF или DOCX), ждёт разбора, видит извлечённый текст как подсказку, вручную подтверждает каждое поле.
3. Видит в профиле витрину спроса по своим ролям и свои награды; читает приватные отзывы коллег без имён авторов.

### teams
1. Пользователь создаёт команду под проект, описывает роли и места, помечает желательные, приглашает друзей, запускает проект.
2. Участник выходит; тимлид выбирает замену из очереди или продолжение без него.
3. Тимлид выходит; участники выдвигаются и голосуют; победитель становится тимлидом.
4. Тимлид исключает автоматически добавленного участника в течение 7 дней; тот возвращается в очередь.

### matching
1. Тимлид видит рекомендованных кандидатов на открытую роль; кандидат видит рекомендованные команды.
2. Кандидат встаёт в очередь на несколько ролей, расставляет приоритеты; система добавляет его в команду автоматически.
3. Пользователь видит по каждой роли, сколько команд её ищут и сколько в среднем ждут.

### playbooks
1. Тимлид выбирает тип продукта (веб-сервис или ML-продукт) при создании команды; сценарий фиксируется на версии.
2. Администратор загружает новый сценарий файлом данных; новый тип продукта появляется без правки кода.

### workspace
1. Команда видит чек-лист текущего этапа; для каждого шага назначен исполнитель; для роли, которой нет в команде, показан запасной шаг, тимлид назначает исполнителя.
2. Участник закрывает пункт: прикладывает ссылку или файл либо заполняет ритуал (дата, внешняя ссылка, итоги).
3. Другой участник проходит чек-лист ревью; тимлид переводит этап; в конце тимлид завершает проект; каждый участник видит просрочку.

### github
1. Тимлид устанавливает GitHub App на репозиторий команды; участники привязывают свои GitHub-учётки.
2. Команда ведёт Issues и PR в GitHub; платформа показывает ленту задач и вклад каждого участника.

### rewards
1. После завершения проекта и 7 дней охлаждения зачтённые участники получают награды; командный бонус получают все зачтённые.
2. Подозрительный проект уходит в ручную проверку, награды замораживаются.

## 4. Функциональные требования

Формат критерия: **Дано** (начальное состояние) / **Когда** (действие) / **Тогда** (проверяемый результат). Каждый критерий проверяется автоматическим тестом (Vitest для API, Playwright для интерфейса). Числа ссылаются на константы раздела 7 (C-xx).

### 4.1 auth

**FR-AUTH-01. Вход через GitHub.** Дано: гость, есть действующий GitHub-аккаунт. Когда: завершает OAuth-поток. Тогда: создана запись пользователя с `github_user_id`, создана сессия (cookie HttpOnly, Secure, SameSite=Lax), токены GitHub в БД лежат зашифрованными (`encryptOAuthTokens`).

**FR-AUTH-02. Вход по ссылке на email.** Дано: гость вводит email. Когда: запрашивает ссылку. Тогда: письмо с одноразовой ссылкой, срок C-30 (15 минут); повторное использование и просроченная ссылка дают 400/401; пароль не вводится.

**FR-AUTH-03. Согласие на обработку ПД.** Дано: пользователь вошёл впервые. Когда: пытается открыть любой раздел, кроме страницы согласия. Тогда: доступ закрыт (403 `CONSENT_REQUIRED`), пока не записано согласие (версия текста, хэш текста, время UTC, хэш IP). Согласие явно называет передачу логина и репозитория в GitHub. Отзыв согласия запускает FR-AUTH-09.

**FR-AUTH-04. Ограничение частоты.** Дано: лимиты C-31..C-34. Когда: превышены (запрос ссылки, вход, загрузка файлов, регистрация). Тогда: 429 с заголовком `Retry-After`; счётчики в Redis; обход сменой email с того же IP не работает (лимит и на IP).

**FR-AUTH-05. Привязка GitHub обязательна для вступления.** Дано: пользователь вошёл по email, GitHub не привязан. Когда: пытается занять место в команде или встать в очередь. Тогда: 409 `GITHUB_REQUIRED`; после привязки операция проходит. Один `github_user_id` привязывается только к одной учётной записи (повтор: 409).

**FR-AUTH-06. Нормализация email и защита от мультиаккаунтов.** Дано: существует пользователь `a.b+x@gmail.com`. Когда: регистрируется `ab@gmail.com`. Тогда: отказ (одна нормализованная запись). Правила нормализации: нижний регистр; gmail: без точек и без части после `+`; Яндекс (`yandex.ru`, `ya.ru`, `yandex.com`, `yandex.kz`, `yandex.by`, `yandex.ua`): единый домен, точка равна дефису, часть после `+` отбрасывается; mail.ru (`mail.ru`, `inbox.ru`, `list.ru`, `bk.ru`): единый ящик, часть после `+` отбрасывается [решение автора, закрывает MEDIUM из backlog]. Одноразовые домены блокируются при регистрации.

**FR-AUTH-07. Сессии.** Дано: вошедший пользователь. Когда: запрос к API. Тогда: сессия читается из Redis; срок C-35 (30 дней), продление при активности; выход удаляет сессию; очистка Redis приводит только к повторному входу. API не хранит состояние в памяти процесса.

**FR-AUTH-08. Роль администратора справочников.** Дано: пользователь. Когда: вызывает эндпоинт справочников. Тогда: 403, если он не в списке администраторов; список задаётся вне интерфейса (миграция-посев или команда CLI), через интерфейс выдать роль нельзя.

**FR-AUTH-09. Удаление персональных данных по запросу (152-ФЗ).** Дано: пользователь запросил удаление (или отозвал согласие). Когда: подтверждает запрос. Тогда: (а) сессии сразу отозваны, вход закрыт; (б) в течение C-36 (30 дней) удалены: профиль, резюме и извлечённый текст, файлы в S3, отзывы о пользователе, награды, заявки, токены GitHub, записи согласия сохраняются только как факт (хэши) для доказательства; (в) вклад в чужих проектах (закрытые задачи, артефакты, голоса) обезличивается ("Удалённый пользователь"), а не удаляется; (г) если пользователь был тимлидом, запускается голосование (FR-TEAM-14); если участником - выход (FR-TEAM-11); (д) резервные копии очищаются не позже C-37 (30 дней); (е) записан журнал удаления без ПД. Тест: после удаления SQL-проверка показывает отсутствие email, GitHub-логина, текста резюме, файлов.

### 4.2 profiles

**FR-PROF-01. Поля профиля.** Дано: пользователь. Когда: сохраняет профиль. Тогда: сохранены имя (2-60 символов), часовой пояс (IANA), доступность часов в неделю (C-20: 3..40), стек (теги справочника, до 30), опыт (до 10 записей), сильные и слабые стороны (до 10 пунктов по 200 символов), желаемые роли (до 5) с уровнем (`beginner`, `junior`, `middle`) [решение автора], ссылка на портфолио (https). Данные проверены схемой, HTML экранируется при выводе.

**FR-PROF-02. Загрузка резюме.** Дано: файл. Когда: загружает. Тогда: принят только PDF (магические байты `%PDF-`) или DOCX (`PK\x03\x04`) размером до C-21 (5 МБ); иное: 415/413; файл лежит в приватном бакете под случайным ключом; запись создана в статусе `queued`; задача разбора в очереди; лимит C-33.

**FR-PROF-03. Разбор резюме в изолированном воркере.** Дано: задача. Когда: воркер берёт её. Тогда: unpdf/mammoth `extractRawText` в `дочернем процессе [изменено в фазе 3]` с лимитом памяти C-22 (256 МБ) и таймаутом C-23 (15 с); PDF до C-24 (30) страниц; DOCX: проверка распакованного размера до C-25 (50 МБ) и числа записей архива до разбора; результат - обычный текст до C-26 (100 000) символов без управляющих символов; статусы `queued`, `processing`, `done`, `failed` (причина: скан без текста, таймаут, лимит). Тест: zip-бомба и бесконечный PDF дают `failed`, воркер жив.

**FR-PROF-04. Ручное подтверждение полей.** Дано: статус `done`. Когда: пользователь открывает форму. Тогда: предложенные значения (предложение по правилам, без ML) показаны как подсказка рядом с извлечённым текстом; поля профиля меняются только после явного подтверждения каждого поля; для скана форма пуста. Извлечённый текст показывается как plain text.

**FR-PROF-05. Удаление исходного файла резюме.** Дано: подтверждены поля. Когда: пользователь не выбрал "хранить файл". Тогда: файл из S3 и извлечённый текст удаляются; иначе хранятся до удаления пользователем или FR-AUTH-09.

**FR-PROF-06. Видимость профиля.** Дано: чужой пользователь. Когда: открывает профиль. Тогда: видит имя, роли и уровень, стек, часовой пояс, доступность, число завершённых проектов, награды; не видит email, текст резюме, файлы, отзывы, слабые стороны [решение автора]. Резюме видит только владелец.

**FR-PROF-07. Витрина спроса в профиле.** Дано: у пользователя желаемые роли. Когда: открывает профиль. Тогда: по каждой роли показано число команд, которые её ищут, и среднее ожидание в очереди (данные matching, FR-MATCH-09).

**FR-PROF-08. Приватные отзывы коллег.** [изменено в фазе 3, SEC-04] Дано: проект завершён, автор и адресат были участниками. Когда: автор пишет отзыв адресату в течение C-27 (14 дней после завершения). Тогда: отзыв (текст до 2000 символов, один на пару автор-адресат-проект) виден только адресату, без имени автора и без точного времени; автор после отправки видит только факт отправки; API адресата не возвращает `author_id`; отзыв не передаётся в rewards и не влияет на награды; нельзя писать себе. Чтобы автора нельзя было вычислить по времени, порядку или малому числу авторов: (1) отзывы по проекту публикуются адресату одним пакетом только после закрытия окна C-27; до этого адресат их не видит, уведомлений и событий реального времени о создании отзыва нет; (2) пакет публикуется, только если адресат получил по этому проекту отзывы не менее чем от 2 разных авторов; иначе отзыв не публикуется никогда и удаляется через 30 дней после закрытия окна (автору при отправке сообщается, что отзыв будет показан, только если по проекту наберётся не менее двух отзывов); (3) адресату показывается только дата публикации пакета (день закрытия окна), одинаковая для всех отзывов пакета; порядок отзывов в пакете случайный и не связан со временем создания; (4) идентификатор отзыва, выдаваемый адресату, - случайный UUID v4 без метки времени; (5) связь отзыва с автором хранится отдельно от текста и используется только для запрета повторного отзыва и для удаления, в выдачу адресату не попадает. Тест: ни один ответ API, лог и экспорт не содержат автора; до закрытия окна список отзывов адресата пуст; при одном авторе после закрытия окна список пуст; у всех отзывов пакета одинаковая дата; идентификатор отзыва - UUID версии 4.

**FR-PROF-09. Справочники.** Дано: администратор. Когда: добавляет роль или тег стека. Тогда: запись появляется в формах; удалить используемую запись нельзя, только отключить (она остаётся у существующих проектов). Начальный справочник ролей: менеджер проекта, frontend, backend, mobile, бизнес-аналитик, продуктовый аналитик, системный аналитик, дизайнер, ML-инженер, data-инженер, QA, DevOps.

### 4.3 teams

**FR-TEAM-01. Создание команды.** Дано: пользователь, лимит C-10 не исчерпан. Когда: создаёт команду (название, описание, тип продукта, часовой пояс, часы в неделю). Тогда: пользователь - тимлид и участник; статус `forming`; команда считается активным проектом (FR-TEAM-05); версия сценария зафиксирована.

**FR-TEAM-02. Роли и места.** Дано: тимлид. Когда: добавляет места: роль из справочника, число мест, пометка "желательная", минимальный уровень, часы в неделю, стек. Тогда: сохранено; суммарно не более C-04 (12) мест; обязательных ролей нет, команда может стартовать с любым набором.

**FR-TEAM-03. Желательная роль.** Дано: место. Когда: тимлид переключает пометку. Тогда: пишется журнал изменений (время, кто); пометка, выставленная менее C-17 (7 дней) до завершения, даёт сигнал антифрода (AF-14); для бонуса учитывается пометка на момент завершения проекта.

**FR-TEAM-04. Занятие места (вступление).** Дано: открытое место, кандидат. Когда: кандидат вступает (по приглашению, принятием предложения тимлида, автодобавлением). Тогда: в одной транзакции с блокировкой строк пользователя, команды и места (в порядке раздела 5.1) и уникальным ограничением: место свободно, число участников команды меньше C-02 (8; если вступающий уже участник, берётся второе место и размер не растёт; блокировка строки команды не даёт двум вступающим на разные места одновременно превысить C-02), лимит проектов кандидата C-10 не нарушен, GitHub привязан. При двух параллельных запросах на одно место ровно один успешен, второй получает 409 `SEAT_TAKEN`.

**FR-TEAM-05. Лимит активных проектов.** Дано: пользователь состоит в C-10 (2) активных проектах (команды в статусах `forming`, `active`, `voting`, `suspended`; тимлидство тоже считается; `completed` и далее не считаются). Когда: пытается создать команду, вступить или быть автодобавленным. Тогда: отказ 409 `PROJECT_LIMIT`; автодобавление пропускает такую заявку (она остаётся в очереди). Проверка и вставка - в одной транзакции под блокировкой строки пользователя; параллельные вступления в 3 команды дают не более 2 успешных. Выход из проекта освобождает слот сразу.

**FR-TEAM-06. Максимальный размер.** Дано: в команде C-02 (8) участников. Когда: ещё один пытается вступить. Тогда: 409 `TEAM_FULL`; открытые места такой команды не попадают в подбор и в витрину спроса.

**FR-TEAM-07. Совмещение двух ролей.** Дано: участник с одним местом. Когда: тимлид предлагает ему второе место другой роли, участник подтверждает. Тогда: участник держит два места; не более C-03 (2) разных ролей в одной команде; одно место одной роли дважды не занимается; проект считается как один в лимите C-10. Подтверждение обрабатывается как FR-TEAM-04 (блокировка места).

**FR-TEAM-08. Приглашение друзей.** Дано: тимлид. Когда: создаёт приглашение на конкретное место (ссылка с токеном или адресное по логину GitHub / email), срок C-12 (7 дней), не более C-13 (20) активных приглашений. Тогда: токен одноразовый, хранится хэшем; приглашение не резервирует место; пригласить в команду, где места нет, нельзя.

**FR-TEAM-09. Принятие приглашения.** Дано: действующее приглашение. Когда: пользователь принимает. Тогда: выполняется FR-TEAM-04; испытательного срока нет; просроченное или использованное приглашение: 410; приглашение чужого адресата: 403.

**FR-TEAM-10. Старт проекта.** Дано: команда `forming`, тимлид. Когда: нажимает "Начать". Тогда: статус `active`, открывается первый этап (workspace), записан `started_at` и плановая дата окончания (FR-WORK-12); минимум участников для старта - 1 (сам тимлид) [решение автора: по оркестратору, когда стартовать, решает тимлид; минимум C-01 проверяется только при завершении].

**FR-TEAM-11. Выход участника.** Дано: участник (не тимлид). Когда: выходит. Тогда: членство `left`, места освобождены, лимит проектов освобождён сразу; назначенные ему пункты чек-листа остаются без исполнителя; зачёт ему недоступен; тимлиду приходит уведомление и открывается решение FR-TEAM-12.

**FR-TEAM-12. Решение тимлида после выхода.** Дано: освободилось место. Когда: тимлид выбирает "заменить из очереди" или "продолжить без него". Тогда: при замене место остаётся открытым и участвует в подборе (FR-MATCH-05); при продолжении тимлид перераспределяет задачи (FR-TEAM-13), место закрывается (убирается из набора), если тимлид так решил. Если решение не принято C-14 (7 дней), действует замена из очереди с открытым местом [решение автора].

**FR-TEAM-13. Перераспределение задач.** Дано: у вышедшего были пункты чек-листа без выполнения. Когда: тимлид выбирает нового исполнителя. Тогда: пункты переназначены (версия увеличена); ссылки на GitHub-задачи платформа не меняет (назначение в GitHub делают люди), на экране показан список "задачи без исполнителя".

**FR-TEAM-14. Выход тимлида запускает голосование.** Дано: тимлид выходит или удаляет аккаунт, либо команда подаёт запрос после C-15 (14 дней) неактивности тимлида (запрос подают не менее половины участников; действие тимлида до первого голоса отменяет голосование [решение автора]). Когда: событие произошло. Тогда: создаётся ровно одно голосование на команду (уникальное ограничение: одно открытое); статус команды `voting`; переходы этапов и завершение недоступны до назначения тимлида; если остался один участник - он становится тимлидом без голосования; если участников нет - команда архивируется.

**FR-TEAM-15. Выдвижение.** Дано: голосование открыто. Когда: имеющий право (участник, у которого закончился испытательный срок; если таких нет - все активные участники) выдвигает себя или другого с согласием кандидата. Тогда: кандидат записан один раз; первые C-16 (24 часа) идёт приём выдвижений.

**FR-TEAM-16. Голос.** Дано: голосование открыто, голосующий имеет право. Когда: голосует за кандидата (в том числе за себя). Тогда: один голос на человека (уникальное ограничение), изменить нельзя; повторный и параллельный голос: 409; не имеющий права: 403.

**FR-TEAM-17. Закрытие, кворум, срок.** Дано: N имеющих право. Когда: срок C-18 (72 часа) истёк либо один кандидат набрал более N/2 голосов (досрочно). Тогда: кворум = ⌊N/2⌋+1 проголосовавших (3 человека - 2, 8 - 5); победитель - кандидат с наибольшим числом голосов; победитель подтверждает в течение 24 часов, иначе следующий по голосам. Закрытие выполняется одной транзакцией с блокировкой голосования; параллельные "последний голос" и "истечение срока" дают ровно одного тимлида.

**FR-TEAM-18. Нет кворума.** Дано: срок истёк, голосов меньше кворума. Когда: первый раз. Тогда: срок продлён один раз на C-19 (48 часов); повторно нет кворума - тимлидом предлагается участник с наибольшим сроком в команде (по дате вступления), он может отказаться - следующий.

**FR-TEAM-19. Ничья.** Дано: два и более кандидатов с равным максимумом. Когда: срок истёк. Тогда: второй тур только между ними, C-29 (24 часа); снова ничья - побеждает тот, кто дольше в команде; при равенстве - серверный случайный выбор, записанный в журнал.

**FR-TEAM-20. Нет кандидатов.** Дано: за C-16 (24 часа) никто не выдвинулся. Когда: срок приёма истёк. Тогда: роль предлагается участнику с наибольшим сроком; все отказались - статус `suspended` на C-28 (14 дней), таймеры этапов заморожены, затем команда архивируется без зачёта.

**FR-TEAM-21. Журнал голосования.** Дано: голосование закрыто. Тогда: итоги (кандидаты, число голосов, причина исхода) видны всем участникам команды; кто за кого голосовал - не показывается [решение автора].

**FR-TEAM-22. Исключение автоматически добавленного участника в испытательный срок.** Дано: участник добавлен в команду из очереди поиска, испытательный срок (C-константа испытательного срока) не истёк. Когда: тимлид исключает участника. Тогда: участник выходит из команды, место роли снова открыто, заявка участника восстанавливается по FR-MATCH-08. Дано: испытательный срок истёк или участник вступил не через автодобавление. Когда: тимлид пытается исключить его этим действием. Тогда: отказ с кодом 409. Исключение голосованием команды после испытательного срока в MVP не предусмотрено. Тест: исключение на последнем дне срока проходит, на следующий день отклоняется.

**FR-TEAM-23. Расторжение участником в испытательный срок.** Дано: автодобавленный участник. Когда: выходит в срок. Тогда: выход без последствий; в очередь автоматически не возвращается [решение автора: возврат только после исключения тимлидом].

**FR-TEAM-24. Подтверждение испытательного срока.** Дано: срок истёк без исключения (или тимлид подтвердил досрочно). Тогда: `trial_until` снимается, участник получает право выдвигаться и голосовать.

**FR-TEAM-25. Фиксация дефицитности при вступлении.** Дано: вступление на место роли R. Когда: транзакция вступления. Тогда: по правилу FR-MATCH-11 вычислены открытые места роли R во всех командах и кандидаты в очереди на R (до вступления: занимаемое место и вступающий кандидат входят в подсчёт); результат (`deficit_at_join`, числа) записан в запись занятого места и не пересчитывается до конца проекта.

**FR-TEAM-26. Каталог команд.** Дано: пользователь. Когда: открывает список команд. Тогда: пагинация (C-40), фильтры по роли, стеку, часовому поясу, типу продукта; скрыты команды без открытых мест по фильтру.

**FR-TEAM-27. Состояния проекта.** Допустимые статусы команды: `forming`, `active`, `voting`, `suspended`, `completed` (до охлаждения и после), `archived`. Переходы вне схемы запрещены (409). Максимальная длительность C-06 (120 дней) от старта: после неё `suspended` с причиной `max_duration`.

**FR-TEAM-28. Предложение места тимлидом.** [добавлено в фазе 3, Р-5] Дано: тимлид команды в статусе `forming` или `active`, место в статусе `open`, пользователь (кандидат из рекомендаций FR-MATCH-01 или участник этой команды для второй роли по FR-TEAM-07). Когда: тимлид отправляет предложение на это место (сообщение до 500 символов необязательно). Тогда: создано предложение (направление "тимлид -> пользователь", статус `pending`, срок C-12 (7 дней)); место не резервируется; адресат получает уведомление в интерфейсе и по email; на пару (место, пользователь) не более одного ожидающего предложения или заявки (409); не более 30 ожидающих предложений тимлида на команду (409 `OFFER_LIMIT`; число считается под блокировкой строки команды); место не `open` - 409 `SEAT_NOT_OPEN`; не тимлид этой команды - 403. Тест: 30 ожидающих предложений, затем 31-е - 409 `OFFER_LIMIT`; два параллельных запроса на последнее свободное значение лимита - ровно один успех.

**FR-TEAM-29. Заявка кандидата на место.** [добавлено в фазе 3, Р-5] Дано: пользователь с привязанным GitHub и действующим согласием, не участник команды; место в статусе `open` команды в статусе `forming` или `active`. Когда: пользователь подаёт заявку на место (из рекомендаций FR-MATCH-02 или каталога FR-TEAM-26; сообщение до 500 символов необязательно). Тогда: создана заявка (направление "пользователь -> тимлид", статус `pending`, срок C-12 (7 дней)); место не резервируется; тимлид получает уведомление в интерфейсе; заявка в очередь поиска (FR-MATCH-03) не создаётся и не меняется; без GitHub - 409 `GITHUB_REQUIRED`; повтор на ту же пару (место, пользователь) при ожидающей заявке или предложении - 409; не более 10 ожидающих заявок кандидата во все команды (409 `OFFER_LIMIT`; число считается под блокировкой строки пользователя). Тест: 10 ожидающих заявок, затем 11-я - 409 `OFFER_LIMIT`; два параллельных запроса на последнее свободное значение лимита - ровно один успех.

**FR-TEAM-30. Ответ на предложение или заявку.** [добавлено в фазе 3, Р-5] Дано: ожидающее предложение (FR-TEAM-28) или заявка (FR-TEAM-29). Когда: отвечает вторая сторона: на предложение - его адресат, на заявку - текущий тимлид команды; или создатель отзывает своё. Тогда: принятие выполняет вступление по FR-TEAM-04 (те же блокировки, лимиты C-02, C-03, C-10 и коды 409; испытательного срока нет, он только для автодобавления); отклонение - статус `rejected`, отзыв создателем - `cancelled`; ответ любого другого пользователя - 404 (существование не раскрывается); после срока C-12 статус `expired`, и принятие даёт 409 `INVALID_STATE`; если место к моменту принятия занято или закрыто - 409 `SEAT_TAKEN` / `SEAT_NOT_OPEN`, а предложение переходит в `cancelled`; остальные ожидающие предложения и заявки на занятое или закрытое место переводятся в `cancelled` фоновым обработчиком. Тест: 20 кандидатов принимают 20 разных предложений на одно место параллельно - 1 успех, 19 x 409 `SEAT_TAKEN` (CC-1); заявку принимает участник, не тимлид, - 404; адресат предложения отзывает чужую заявку - 404.

### 4.4 matching

**FR-MATCH-01. Рекомендации кандидатов на роль.** Дано: открытое место. Когда: тимлид открывает подбор. Тогда: список кандидатов из очереди и профилей, отсортированный по оценке (FR-MATCH-12), с пагинацией; отдаётся из предварительно рассчитанного результата (задача в очереди), не считается в запросе.

**FR-MATCH-02. Рекомендации команд кандидату.** Дано: пользователь с желаемой ролью. Когда: открывает подбор. Тогда: список команд с открытыми местами нужной роли, отсортированный по оценке, с причинами совпадения (роль, стек, уровень, часовой пояс, доступность, число завершённых проектов).

**FR-MATCH-03. Заявка в очередь на несколько ролей.** Дано: пользователь, GitHub привязан, нет активной заявки. Когда: создаёт заявку с 1..C-07 (5) ролями, у каждой уникальный приоритет (1 - высший). Тогда: одна активная заявка на пользователя (уникальное ограничение); `enqueued_at` записан; повторное создание: 409.

**FR-MATCH-04. Изменение и отмена заявки.** Дано: активная заявка. Когда: меняет роли, приоритеты или отменяет. Тогда: изменение применяется атомарно под блокировкой заявки; `enqueued_at` сохраняется при изменении, не при повторной подаче после отмены.

**FR-MATCH-05. Автодобавление.** Дано: в очереди есть заявка, появилось открытое место подходящей роли. Когда: запускается подбор (по событию "место открыто" / "заявка создана" и по расписанию C-38, раз в минуту). Тогда: кандидат добавляется вызовом FR-TEAM-04 с признаком `auto`, получает `trial_until` = сейчас + C-11; заявка закрывается статусом `fulfilled`; кандидату приходит уведомление.

**FR-MATCH-06. Выбор роли при нескольких совпадениях.** Дано: заявка на роли A (приоритет 1) и B (приоритет 2). Когда: место для B найдено раньше (по моменту `match_possible_at` = позже из "место открыто" и "роль добавлена в заявку"). Тогда: сработает B. Если совпадения для нескольких ролей найдены в одном запуске подбора (одновременно), выбирается роль с меньшим номером приоритета (A). Тест: оба порядка и ничья.

**FR-MATCH-07. Защита автодобавления.** Дано: подходящее место. Когда: у кандидата исчерпан лимит C-10, нет GitHub, не дано согласие, число участников команды C-02, или кандидат уже в этой команде. Тогда: пара пропускается, заявка остаётся в очереди (при исчерпанном лимите - целиком). Два параллельных запуска подбора добавляют кандидата не более одного раза (блокировка заявки + уникальное ограничение).

**FR-MATCH-08. Возврат исключённого в очередь.** Дано: участник исключён тимлидом в испытательный срок. Когда: исключение зафиксировано. Тогда: заявка восстановлена с прежними ролями, приоритетами и прежним `enqueued_at` (ожидание не обнуляется); в ту же команду автодобавление его больше не ставит [решение автора]; время, проведённое в команде, не входит в среднее ожидание.

**FR-MATCH-09. Витрина спроса.** Дано: роль R. Когда: пользователь открывает профиль или очередь. Тогда: показаны: число команд, ищущих R (команды в `forming`/`active` с не менее чем одним открытым местом R и числом участников меньше C-02), число открытых мест R, число кандидатов в очереди на R, среднее ожидание. Данные кэшируются до C-39 (60 секунд). Ожидание - среднее за последние C-41 (90 дней) значений (`matched_at - enqueued_at`) по заявкам, закрытым автодобавлением на роль R; при менее чем C-42 (5) наблюдений вместо числа показывается "недостаточно данных".

**FR-MATCH-10. Среднее ожидание считается по закрытым ожиданиям.** Тест: заявка, отменённая без добавления, в среднее не входит.

**FR-MATCH-11. Правило дефицитности.** Роль R дефицитна, если открытых мест на R во всех командах (с числом участников меньше C-02, статусы `forming`/`active`) строго больше, чем кандидатов в очереди с R среди ролей их заявки. Вычисляется без кэша, внутри транзакции вступления (FR-TEAM-25), результат возвращается в teams как (`deficit`, `open_seats`, `queued`). При равенстве чисел роль не дефицитна. Кандидат, вступающий через приглашение, в числе кандидатов не учитывается; вступающий из очереди учитывается (до вступления).

**FR-MATCH-12. Оценка подбора на правилах и весах.** Жёсткие фильтры: роль; уровень не ниже минимального для места; доступность не ниже часов места; разница часовых поясов не более C-43 (6 часов). Оценка 0..1 как взвешенная сумма: стек (доля совпавших тегов) C-44a 0.35; уровень C-44b 0.20; часовой пояс C-44c 0.20; доступность C-44d 0.15; число завершённых проектов в этой роли (насыщение на 3) C-44e 0.10. Порог автодобавления C-45 = 0.5 [решение автора]. Веса в конфигурации. Алгоритм подробно - в фазе 3.

### 4.5 playbooks

**FR-PLAY-01. Сценарий как данные.** Сценарий хранится в БД и описывается файлом данных (JSON/YAML), загружаемым администратором. Структура совпадает с форматом `docs/playbooks.md` (раздел 2.1) и сид-данными веб-сервиса и ML-продукта:

| Сущность | Поля |
|---|---|
| Тип продукта | `code`, `name`, `active` |
| Сценарий | `product_type` (ключ типа), `title`, `version` (строка semver, например `1.0.0`; растёт), `total_days` (сумма `duration_days` этапов; вычисляется и сверяется при загрузке), `stages[]`; служебно в БД: `status` (`draft`, `published`) |
| Этап | `key`, `title`, `goal`, `duration_days` (целое число дней > 0, срок), `exit_criteria` (критерий перехода, человекочитаемый текст), `steps[]`; порядок этапов - порядок в списке. Машинные условия перехода одинаковы для всех этапов и описаны в FR-WORK-10 (обязательные пункты закрыты, чек-листы ревью пройдены, минимум времени C-08 = 24 часа); отдельного поля `min_hours` в сценарии нет |
| Шаг | `key`, `title`, `description`, `type` (`artifact`, `ritual`), `required` (bool), `owner_role` (ключ роли из справочника или `any`), `alt_roles[]` (роли, любая из которых тоже может выполнить шаг; пусто для `any`), `fallback` (объект или `null`), `review_checklist` (bool), `review_items[]` (формулировки "да/нет", пригодные для новичка), `auto_checks[]` (ключи проверок, FR-PLAY-08), `sources[]` (URL источников из фазы 1, не пусто) |
| Только для артефакта | `submission`: `link`, `file` или `either` |
| Только для ритуала | `ritual_kind`: `call` (созвон), `retro` (ретроспектива), `brainstorm` (мозговой штурм), `code_review` (код-ревью); обязательные поля пункта: дата, внешняя ссылка, итоги (FR-WORK-06) |
| Запасной шаг (`fallback`) | `title`, `instruction`, `template` (ключ шаблона платформы), `url` (внешняя ссылка на шаблон или инструкцию, необязательно) |

Каждый шаг с `owner_role` не `any` обязан иметь запасной шаг (`fallback`); у шага с `owner_role: any` запасного шага и `alt_roles` нет. Шаг с `required: false` (необязательный) не блокирует переход этапа и завершение проекта (FR-WORK-02, -10).

**FR-PLAY-02. Проверка при загрузке.** Дано: файл сценария. Когда: администратор загружает. Тогда: проверка схемой; отклонение (422 со списком ошибок), если: шаг с `owner_role` не `any` без `fallback`, или `any` с `fallback`/`alt_roles`; `owner_role` или `alt_roles` не из справочника ролей, либо `alt_roles` содержит `owner_role`; `template` запасного шага не из каталога шаблонов платформы; `duration_days` не целое положительное; `total_days` не равно сумме `duration_days`; ключи этапов или шагов повторяются; на этапе нет ни одного обязательного артефакта; `sources` шага пусто; `submission` указан у ритуала, `ritual_kind` у артефакта; `review_checklist: true` без `review_items` (и наоборот); неизвестный ключ в `auto_checks`; последний этап не содержит обязательного шага со ссылкой на релиз и репозиторий.

**FR-PLAY-03. Версии и закрепление.** Дано: команда создана на версии V. Когда: опубликована более новая версия (semver больше). Тогда: команда продолжает на V; новые команды берут последнюю `published`; опубликованную версию нельзя менять (только новая версия).

**FR-PLAY-04. Новый тип продукта без правки кода.** Дано: тестовый сценарий с новым типом. Когда: администратор загружает и публикует. Тогда: тип доступен в создании команды, workspace строит чек-лист, ни одна строка кода не менялась (интеграционный тест на данных-фикстуре).

**FR-PLAY-05. Загрузка администратором.** Загрузка в MVP - эндпоинт приёма файла данных и CLI-команда; визуального редактора нет [решение автора]. Начальные сценарии (веб-сервис, ML-продукт) из `docs/playbooks.md` попадают в БД миграцией-посевом.

**FR-PLAY-06. Типы продукта в MVP.** Активны два: `web_service`, `ml_product`. Остальные записи в справочнике могут существовать, но `active=false`.

**FR-PLAY-07. Срок этапа и плановая дата.** `duration_days` суммируются в плановую длительность проекта; базовая длительность проекта 12 недель (C-05), допустимый разброс сценария 10-16 недель (проверка при загрузке: предупреждение, не ошибка). Начальные сценарии: веб-сервис 84 дня (12 недель), ML-продукт 91 день (13 недель), `docs/playbooks.md`.

**FR-PLAY-08. Автоматические проверки шагов.** Ключи `auto_checks` берутся из каталога `docs/playbooks.md` (раздел 2.4). Дано: шаг с проверками. Когда: артефакт или ритуал сохранён, а для ссылок и релиза ещё и при завершении проекта. Тогда: воркер выполняет проверки. Блокирующие: `file_ok` (FR-WORK-05), `ritual_fields` (FR-WORK-06), `repo_exists`, `repo_final` (FR-GH-08), `release_alive_web`, `release_alive_ml` (FR-WORK-14), и `link_https` в части "только https и защита от SSRF" (422); для `link_https` ответ не 2xx даёт только предупреждение `broken` (FR-WORK-04). Сигнальные: `sha_dedup` (AF-06), `md_headings`, `min_files:N`, `pr_cross_review:N`, `ci_workflow`: пункт закрывается, результат пишется в `fraud_signal` с `rule_code` = `STEP_<ключ>` и баллом 0 (виден администратору в очереди ручной проверки, на порог C-61 не влияет, кроме `sha_dedup`, который действует по AF-06) [решение автора]. Данные для `pr_cross_review` (автор и ревьюер PR) и `ci_workflow` модуль github берёт из событий `pull_request`, `pull_request_review` и из запуска workflow.

### 4.6 workspace

**FR-WORK-01. Открытие этапа.** Дано: проект стартовал или предыдущий этап закрыт. Когда: этап открывается. Тогда: из шагов сценария создаются пункты чек-листа с версией 1, статусом `open`, `opened_at` записан; срок этапа = `opened_at` + `duration_days`.

**FR-WORK-02. Исполнитель и запасной шаг.** Дано: этап открыт. Когда: определяется исполнитель шага. Тогда: (1) `owner_role: any` - исполнитель любой активный участник, закрывающий пункт; (2) для шага с ролью исполнитель - активный держатель `owner_role`, а если такого нет, держатель одной из `alt_roles` (при нескольких держателях исполнителя назначает тимлид); (3) если в команде нет ни держателя `owner_role`, ни держателя `alt_roles`, пункт помечается `fallback_used`, показывается запасной шаг (шаблон/инструкция), исполнителя назначает тимлид. Обязательный шаг не пропускается и не отменяется, а упрощается. Необязательный шаг (`required: false`, например `w6_mobile`) с `fallback_used` исполнителя не требует, переход этапа и завершение проекта не блокирует; запасной вариант показывается как совет. Если роль появилась позже, пока пункт не закрыт, тимлид может вернуть обычный шаг.

**FR-WORK-03. Назначение исполнителя запасного шага.** Дано: обязательный пункт `fallback_used` без исполнителя. Когда: тимлид выбирает активного участника. Тогда: назначен; до назначения этап не переводится; назначить может только тимлид (403 иначе). Вклад исполнителя помечается его собственной ролью (FR-REW-02), а не отсутствующей: зачёта по отсутствующей роли нет.

**FR-WORK-04. Пункт-артефакт: ссылка.** Дано: пункт типа `link`. Когда: участник сохраняет URL. Тогда: только `https`; проверка в воркере по правилам SSRF (C-46: запрет приватных, loopback, link-local, metadata диапазонов; повторная проверка IP после DNS; до 3 редиректов; таймаут 10 с; тело до 1 МБ; не чаще 1 проверки в минуту на домен); ответ не 2xx помечает ссылку `broken` (предупреждение, пункт остаётся закрываемым, но при завершении проекта проверяется заново).

**FR-WORK-05. Пункт-артефакт: файл.** Дано: пункт типа `file`. Когда: участник загружает. Тогда: допустимые форматы pdf, png, jpg, webp, md, txt, docx, pptx, zip; тип по магическим байтам; размер до C-47 (10 МБ), не более C-48 (30) файлов и C-49 (50 МБ) на проект; не меньше 1 КБ; исполняемые запрещены; файл хранится в S3-хранилище под случайным ключом, SHA-256 записан, раздача с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`; лимит частоты C-34; zip проверяется на zip-бомбу (как C-25).

**FR-WORK-06. Пункт-ритуал.** Дано: пункт типа `ritual`. Когда: участник закрывает. Тогда: обязательны дата проведения (не позже сегодня, не раньше открытия этапа), внешняя ссылка (https; видеосвязь платформа не размещает) и поле итогов (от 20 до 5000 символов); без любого поля: 422.

**FR-WORK-07. Версия пункта и конфликты.** Дано: пункт версии 3. Когда: два участника одновременно пишут с версией 3. Тогда: один запрос успешен (версия 4), второй получает 409 `VERSION_CONFLICT` с актуальным состоянием; запись без версии отклоняется 400.

**FR-WORK-08. Ключ идемпотентности.** Дано: изменяющий запрос с заголовком `Idempotency-Key`. Когда: тот же запрос повторяется. Тогда: возвращается сохранённый ответ без повторного действия (срок хранения C-50, 24 часа); тот же ключ с другим телом: 422; запрос в обработке: 409. Касается всех POST/PUT/PATCH/DELETE всех модулей.

**FR-WORK-09. Чек-лист ревью.** Дано: этап с `review_checklist`. Когда: участник, не являющийся автором артефактов этапа, отвечает "да/нет" на каждый пункт по ссылке на артефакт. Тогда: автор не может проверять свои пункты (403); этап считается проверенным, когда все пункты "да" либо "нет"-пункты явно приняты тимлидом как риск с записью в протокол (поле обоснования).

**FR-WORK-10. Переход этапа.** Дано: тимлид, этап открыт. Когда: нажимает "Перейти". Тогда: в одной транзакции с блокировкой строки этапа проверено: все обязательные пункты закрыты, ревью пройдено, прошло не менее `min_hours` (C-08 = 24 часа) с открытия, этапы идут строго по порядку; следующий этап открыт, `closed_at` записан. Два параллельных перехода: один успешен, второй 409. Нарушенное условие: 409 с перечнем невыполненного. Просрочка срока этапа переход не блокирует.

**FR-WORK-11. Подтверждение участия в этапе.** Дано: участник был в команде весь этап, вклада нет. Когда: тимлид подтверждает участие. Тогда: этап засчитывается в долю участия (FR-REW-01).

**FR-WORK-12. Плановая дата и просрочка.** Плановая дата окончания проекта = `started_at` + сумма `duration_days` всех этапов + суммарное время приостановок (`suspended`), фиксируется при старте и обновляется только приостановкой. Просрочка проекта = `completed_at` - плановая дата, в целых календарных днях с округлением вверх; если результат не положителен - "без просрочки". Просрочка не останавливает и не отменяет проект. Просрочка этапа показывается как предупреждение, без блокировок и штрафов.

**FR-WORK-13. Условия завершения проекта.** Дано: тимлид нажимает "Завершить". Когда: проверка. Тогда: проект завершается, только если выполнено всё: (1) пройдены все этапы; (2) обязательные артефакты каждого этапа загружены; (3) есть ссылка на работающий релиз (FR-WORK-14) и привязанный публичный репозиторий; (4) участников не менее C-01 (3) на момент завершения; (5) длительность не менее C-06a (14 календарных дней) от открытия первого этапа и не менее C-09 (3) календарных дней с событиями вклада; (6) вклад не менее C-52 (10) слитых PR или закрытых задач в сумме и не менее 2 разных GitHub-аккаунтов с вкладом; (7) команда не в статусах `voting`, `suspended`. Любое невыполненное условие: 409 с перечнем; просрочка завершению не мешает.

**FR-WORK-14. Проверка ссылки на релиз.** Дано: ссылка на релиз сохранена в обязательном шаге `*_final_links` последнего этапа (любым участником; значение копируется в `team.release_url`, до завершения его может заменить тимлид). Когда: сохраняется. Тогда: воркер проверяет по правилам SSRF (FR-WORK-04) и по проверке из сценария. `release_alive_web` (веб-сервис): ответ 200 после редиректов, тело HTML не менее 500 байт. `release_alive_ml` (ML-продукт): принимается только работающий публичный адрес `https` - демо-страница либо API по адресу страницы документации `/docs` или проверки состояния `/health` с ответом HTTP 200; тело HTML не менее 500 байт либо непустой корректный JSON (для `/health` любого размера); архивы, контейнеры, локальные адреса и страницы GitHub Releases без работающего сервиса не принимаются, исключений по решению тимлида нет. Для обоих: заголовок не из списка заглушек; полный адрес (имя хоста и путь) не повторяется среди завершённых проектов (общий домен хостинга сам по себе не повод для отказа); вторая проверка не ранее чем через C-53 (24 часа) после первой; завершение возможно только когда обе прошли. Хостинг студентов платформа не навязывает.

**FR-WORK-15. Показ просрочки при завершении.** Дано: проект завершён. Когда: любой участник на момент завершения открывает страницу итогов. Тогда: видит "просрочка N дн." либо "без просрочки" (FR-WORK-12); данные одинаковы для всех участников; показ не зависит от награды.

**FR-WORK-16. Лента задач и вклад.** Дано: привязан репозиторий. Когда: участник открывает ленту. Тогда: пагинированный список закрытых Issues и слитых PR (по данным github), артефактов и ритуалов; вклад каждого участника (число закрытых задач, слитых PR, артефактов) по ролям. Своей доски задач нет.

**FR-WORK-17. Роль вклада.** (закрывает MEDIUM из backlog) Каждый вклад (закрытый issue, слитый PR, загруженный артефакт, закрытый ритуал) помечается ровно одной ролью исполнителя `contribution.role_code`. Определение роли: (1) явная метка `role:<code>` на issue/PR в GitHub, если участник держит эту роль; (2) для артефакта и ритуала - `owner_role` шага, если участник её держит; для шага `any`, для исполнителя по `alt_roles` и для запасного шага - явный выбор участника из своих ролей в проекте (по умолчанию основная роль); (3) иначе основная (первая по дате назначения) роль участника. У участника с одной ролью метка не нужна. Участник может сменить метку до завершения проекта; при завершении метки фиксируются. Вклад без роли в команде (например, роль, которой участник не держит) невозможен.

**FR-WORK-18. Приостановка.** Дано: статус `suspended`. Тогда: таймеры этапов заморожены, срок продлевается на длительность приостановки (FR-WORK-12), действия, кроме голосования и возобновления, запрещены.

**FR-WORK-19. Уведомления о сроках.** За C-54 (2 дня) до срока этапа и в день срока уведомление тимлиду и участникам через очередь; уведомления не блокируют работу.

### 4.7 github

**FR-GH-01. Установка GitHub App.** Дано: тимлид. Когда: нажимает "Подключить репозиторий" и устанавливает App на выбранный репозиторий. Тогда: сохранены `installation_id`, `repository_id`, название; права App только чтение (Metadata, Issues, Pull requests; Contents: read добавляется только если проверка коммитов иначе недоступна); токены установки генерируются по требованию и кэшируются в Redis не дольше 55 минут, в БД не хранятся.

**FR-GH-02. Уникальность репозитория.** Дано: репозиторий уже привязан к зачтённому или активному проекту. Когда: другая команда привязывает его. Тогда: 409 `REPO_TAKEN` (уникально по `repository_id`, не по имени); форк без собственных коммитов отклоняется; репозиторий, созданный более чем за C-55 (30 дней) до старта проекта, получает сигнал AF-03.

**FR-GH-03. Приём вебхука.** Дано: запрос от GitHub. Когда: подпись `X-Hub-Signature-256` неверна или отсутствует. Тогда: 401, тело не обрабатывается; верная подпись (сравнение за постоянное время по сырому телу): 2xx сразу, тело в очередь.

**FR-GH-04. Идемпотентность доставки.** Дано: доставка с `X-GitHub-Delivery`. Когда: приходит повторно. Тогда: игнорируется (уникальное ограничение, хранение C-56 7 дней); параллельная повторная доставка не создаёт дубль вклада.

**FR-GH-05. Вклад из событий.** Дано: событие `issues` closed или `pull_request` merged. Когда: обработано воркером. Тогда: команда определяется по `repository.id`, автор по числовому `user.id`; исполнитель задачи - assignee, иначе автор закрывающего PR; вклад слитого PR - его автор; `received_at` серверное, даты коммитов не используются; событие автора без привязки GitHub-аккаунта к участнику команды сохраняется, но вклада не создаёт; вклад передаётся в workspace (FR-WORK-17 назначает роль).

**FR-GH-06. Суточная сверка.** Дано: ежесуточный запуск (C-57). Когда: опрашивает issues и PR репозитория с ETag (`If-None-Match`). Тогда: пропущенные события дозаполняются без дублей; ответ 304 не расходует лимит; остаток лимита соблюдается плагином throttling.

**FR-GH-07. События установки.** Дано: `installation` deleted или `installation_repositories` removed. Тогда: репозиторий помечается отвязанным, тимлид уведомлён, новые вклады не принимаются, прежние сохраняются.

**FR-GH-08. Проверка репозитория при завершении.** Репозиторий существует, не архивирован, публичный, не форк без своих изменений, не менее C-58 (10) коммитов, коммиты не менее чем от 2 привязанных GitHub-аккаунтов участников; иначе завершение: 409 (блок AF-01).

**FR-GH-09. Возраст GitHub-аккаунта.** Для зачёта участнику (FR-REW-01) аккаунт не младше C-59 (30 дней) и имеет публичный репозиторий либо публичную активность; иначе зачёт откладывается (статус `pending_account`), а не отклоняется.

**FR-GH-10. Токены пользователей.** Пользовательские токены хранятся зашифрованными, ключ из переменной окружения; если токен не нужен - не сохраняется; при удалении пользователя уничтожаются (FR-AUTH-09). Секрет вебхука, ключ App, client secret только в окружении, наличие проверяется при старте.

**FR-GH-11. Опора на Issues и PR.** Projects v2 в MVP не используется для вклада; в интерфейсе подсказка тимлиду: "Ведите задачи как Issues; доска Projects - дополнительно".

### 4.8 rewards

**FR-REW-01. Условия зачёта участнику.** Участник получает зачёт по проекту, если одновременно: (1) на момент завершения он активный член команды (вышедший досрочно, исключённый - нет); (2) у него есть вклад (закрытая задача, слитый PR, загруженный артефакт или закрытый ритуал, где он указан исполнителем; роль вклада по FR-WORK-17); (3) он участвовал не менее C-60 (60%, округление вверх) этапов: участие в этапе = был в команде в окне этапа и имеет вклад в этом этапе либо подтверждён тимлидом (FR-WORK-11); (4) проект не заморожен антифродом; (5) выполнен FR-GH-09. Условия (1)-(3) проверяются на момент завершения, (5) - при окончании охлаждения.

**FR-REW-02. Зачёт по ролям при совмещении.** (закрывает MEDIUM из backlog) Дано: участник с ролями A и B. Когда: вычисляется зачёт. Тогда: зачёт по роли R выдаётся тогда и только тогда, когда выполнен FR-REW-01 и есть хотя бы один вклад, помеченный ролью R (FR-WORK-17). Один вклад помечен одной ролью и зачёта по второй не даёт. Тест: все вклады с меткой A - зачёт только по A; по одному вкладу на A и B - по обеим. Для общих счётчиков проект засчитывается один раз на человека.

**FR-REW-03. Нет зачёта по отсутствующей роли.** Дано: шаг роли X выполнен запасным шагом (FR-WORK-02) либо держателем одной из `alt_roles`. Когда: вычисляется зачёт. Тогда: вклад исполнителя помечен его собственной ролью; зачёт по роли X ни у кого не появляется; в счётчик роли X проект не входит.

**FR-REW-04. Счётчики.** Для каждого пользователя ведутся: общий счётчик зачтённых проектов (+1 за проект) и счётчик по каждой роли с зачётом (+1 за проект и роль); набор типов продукта с зачётом. Счётчик увеличивается один раз на проект и пользователя (уникальное ограничение), повторный запуск зачёта не меняет значений. Число проектов с идентичным составом (AF-13) для значков серии "Проекты" считается как 1.

**FR-REW-05. Каталог наград и "ступени серии".** (закрывает MEDIUM из backlog) Награды косметические: значок с датой и проектом, без рейтингов и списков лидеров. Серии наград состоят из ступеней, называемых "ступени серии" (не "уровни", не "бронза/серебро/золото"); в профиле серия показывается одним значком с текущей ступенью.

| Награда | Серия / ступень | Условие |
|---|---|---|
| Первый релиз | Проекты, ступень 1 | 1 зачтённый проект |
| Трое в строю | Проекты, ступень 2 | 3 зачтённых проекта |
| Пятёрка проектов | Проекты, ступень 3 | 5 |
| Десять из десяти | Проекты, ступень 4 (последняя) | 10 |
| Многоликий | Роли, ступень 1 | зачёт минимум в 3 разных ролях |
| Универсал | Роли, ступень 2 | в 5 разных ролях |
| Разные берега | Типы продукта, ступень 1 | в 2 разных типах |
| Коллекционер форматов | Типы продукта, ступень 2 | в 4 типах (включается во второй версии; в MVP недостижима) |
| В срок | отдельная | проект завершён без просрочки |
| Три в срок подряд | отдельная (не серия; название выбрано, чтобы не путать с серией наград) [решение автора] | 3 зачтённых проекта подряд без просрочек |
| Закрыл дефицит | отдельная | зачтённый проект, где участник держал роль с `deficit_at_join` |
| Закрытая вакансия | командная | см. FR-REW-10 |

**FR-REW-06. Выдача награды.** Выдача происходит после охлаждения (FR-REW-11) в транзакции с блокировкой записи проекта; награда уникальна по (пользователь, код награды) для индивидуальных и по (проект, пользователь, код) для командных; повторный запуск выдачи не создаёт дубль.

**FR-REW-07. В срок.** Дано: просрочка по FR-WORK-12 не положительна. Тогда: каждый зачтённый участник получает награду; в противном случае нет.

**FR-REW-08. Три в срок подряд.** Дано: последние 3 зачтённых проекта пользователя (по `completed_at`) без просрочки. Тогда: награда; пропуск зачёта (проект без зачёта) серию не прерывает, проект с просрочкой прерывает [решение автора].

**FR-REW-09. Закрыл дефицит.** Дано: в записи места участника `deficit_at_join=true` (FR-TEAM-25) и по роли этого места зачёт выдан. Тогда: награда; последующие изменения спроса не пересчитывают флаг.

**FR-REW-10. Командный бонус "Закрытая вакансия".** Дано: к завершению проекта желательная роль (пометка на момент завершения, FR-TEAM-03) занята участником с зачётом по этой роли, у которого `deficit_at_join=true`. Тогда: награду получает каждый участник команды на момент завершения (не вышедший досрочно), независимо от собственного зачёта и от способа вступления того участника (очередь или приглашение). Тест: роль закрыта зачтённым участником с `deficit_at_join=true`, в команде есть участник без зачёта - бонус выдан обоим; участник, вышедший досрочно, бонус не получает. Желательная роль без дефицита, дефицитная нежелательная роль, дефицитность без зачёта по роли бонус не дают. Пометка, выставленная менее C-17 (7 дней) до завершения, даёт сигнал AF-14, не отменяет бонус автоматически.

**FR-REW-11. Охлаждение.** Зачёт и награды применяются через C-17b (7 дней) после завершения; за это время проект можно оспорить (жалоба участника, действие администратора). Завершение и показ просрочки происходят сразу, зачёт - после охлаждения. Фиксация зачёта выполняется планировщиком в одной транзакции с блокировкой записи проекта.

**FR-REW-12. Отзыв наград.** При решении антифрода "нарушение" награды проекта отзываются (статус `revoked`), счётчики уменьшаются, решение пишется в журнал с автором и причиной.

**FR-REW-13. Отзывы коллег не влияют.** Модуль rewards не имеет доступа к отзывам; тест: изменение/удаление отзыва не меняет зачёт и награды.

**FR-REW-14. Без рейтингов.** API не содержит эндпоинтов сортировки пользователей по наградам или счётчикам, списков лидеров и сравнений.

**FR-REW-15. Автоматические проверки антифрода.** При завершении и в конце охлаждения выполняются правила раздела 8; сумма сигналов >= C-61 (3) или любой флаг: проект уходит в очередь ручной проверки, зачёт и награды замораживаются.

**FR-REW-16. Ручная проверка.** Администратор видит очередь (проект, сработавшие правила, данные без ПД сверх необходимого), принимает решение "в порядке" или "нарушение" с комментарием; решение пишется в журнал.

## 5. Нефункциональные требования

### 5.1 Конкурентный доступ

Общие правила: проверка "свободно ли" в коде приложения без блокировки запрещена; изменение защищается одной транзакцией с блокировкой строки (`SELECT ... FOR UPDATE`) либо уникальным ограничением БД. Для каждого сценария обязателен тест: N параллельных запросов (N не менее 20), результат строго определён.

| # | Сценарий | Защита | Ожидаемый результат теста |
|---|---|---|---|
| CC-1 | Занятие места (FR-TEAM-04) | блокировка строки места; уникальное ограничение "активный держатель на место" | 20 запросов на 1 место: 1 успех (200), 19 x 409 `SEAT_TAKEN` |
| CC-2 | Вступление и лимит проектов (FR-TEAM-05, -06) | блокировка строки пользователя + проверка внутри транзакции; блокировка строки команды для размера | один пользователь вступает параллельно в 5 команд: не более C-10 (2) успехов; в команду с 1 свободным местом вступают 10 разных: 1 успех |
| CC-3 | Автодобавление (FR-MATCH-05, -07) | блокировка пользователя и заявки (в порядке раздела 5.1) + уникальное ограничение; вызов FR-TEAM-04 | два параллельных запуска подбора: кандидат добавлен ровно один раз; одно место - ровно одному кандидату из N заявок |
| CC-4 | Голосование (FR-TEAM-16, -17) | уникальное ограничение (голосование, голосующий); блокировка голосования при закрытии | 20 голосов одного человека: 1 успех; 20 параллельных запусков голосования (выход тимлида и запрос команды): ровно одно открытое голосование; "последний голос" против "истечения срока": ровно один тимлид и один исход |
| CC-5 | Переход этапа (FR-WORK-10) | блокировка строки этапа; проверка статуса внутри транзакции | 20 запросов "Перейти": 1 успех, остальные 409; следующий этап открыт один раз |
| CC-6 | Зачёт проекта (FR-REW-04, -06, -11) | блокировка записи проекта; уникальные ограничения счётчиков и наград | 10 параллельных запусков зачёта: счётчики +1, награды без дублей |
| CC-7 | Пункты чек-листа (FR-WORK-07) | поле версии; запись условная по версии | 2 параллельных записи с версией N: 1 успех, 1 x 409 |
| CC-8 | Приглашение (FR-TEAM-09) | блокировка приглашения + CC-1 | 10 принятий одного токена: 1 успех |
| CC-9 | Привязка репозитория (FR-GH-02) | уникальное ограничение по `repository_id` | две команды одновременно: 1 успех |
| CC-10 | Заявка в очередь (FR-MATCH-03) | уникальное ограничение "одна активная заявка" | 10 запросов: 1 заявка |
| CC-11 | Вебхуки (FR-GH-04) | уникальное ограничение `delivery_id` | одна доставка 10 раз параллельно: 1 вклад |
| CC-12 | Выдача награды и счётчиков | см. CC-6 | то же |
| CC-13 | Старт и завершение проекта (FR-TEAM-10, FR-WORK-13) | блокировка строки команды; статус проверяется внутри транзакции; уникальное ограничение `completion.team_id` | 20 запросов "Завершить": 1 успех, 19 x 409, запись завершения одна; "Завершить" против "Перейти этап": один исход; 20 запросов "Начать": один первый этап |

Прочее:
- Ключ идемпотентности (FR-WORK-08) принимают все изменяющие эндпоинты; повтор с тем же ключом и телом возвращает тот же ответ; тест на каждый CC-сценарий с повтором одного запроса дважды.
- Тяжёлая работа идёт в очередях BullMQ: разбор резюме, подбор, синхронизация и обработка вебхуков GitHub, проверки ссылок, зачёт и выдача наград, уведомления. Задачи идемпотентны, повторы с экспоненциальной задержкой (до 5 попыток), "мёртвая" очередь с оповещением в журнале.
- Списки с пагинацией, индексы под каждый частый запрос, запросов в цикле нет (проверка: тест на число запросов к БД в списках).
- Блокировки берутся в едином порядке (пользователь, заявка, команда, место) для исключения взаимоблокировок; тайм-аут блокировки C-62 (5 с), при превышении 503 с повтором.

### 5.3 Безопасность

- Ограничение частоты (Redis, по пользователю и IP): регистрация и запрос ссылки - C-31, вход - C-32, загрузка резюме - C-33, загрузка артефактов - C-34, общий API 120 запросов/мин на пользователя, изменяющие 60/мин [решение автора].
- Валидация схемой (Zod/DTO) на границе каждого эндпоинта; лишние поля отбрасываются; параметризованные запросы Drizzle; весь вывод в HTML экранируется (React, без `dangerouslySetInnerHTML`); текст резюме - только plain text.
- Заголовки: CSP, `X-Content-Type-Options: nosniff`, HSTS, `Referrer-Policy`; CORS только на свои домены; CSRF: SameSite=Lax + проверка origin на изменяющих запросах.
- Секреты только в переменных окружения; обязательные проверяются при запуске (приложение не стартует без них); `.env` не коммитится.
- Загрузки: проверка типа по магическим байтам и размера; хранение вне каталога приложения (S3-бакет приватный); раздача по подписанным ссылкам со сроком C-63 (5 минут).
- Изоляция разбора резюме: отдельный контейнер `resume-worker` без доступа к БД и исходящей сети, непривилегированный пользователь, только чтение ФС.
- SSRF-защита для всех исходящих проверок ссылок (C-46).
- Доступ по правам: каждый эндпоинт проверяет членство/роль; тест на чужие ресурсы (IDOR) на каждый эндпоинт с идентификаторами.
- Отзывы и резюме: см. FR-PROF-08, FR-PROF-06.

### 5.4 Наблюдаемость

- Структурные JSON-журналы (pino): `ts`, `level`, `request_id`, `module`, `route`, `status`, `duration_ms`, `user_id` (внутренний идентификатор); запрещены в журналах: email, токены, текст резюме, текст отзывов, сырые IP (хэш).
- Хранение журналов 30 дней.
- Эндпоинты: `GET /health/live` (процесс жив), `GET /health/ready` (PostgreSQL, Redis, S3, глубина очередей; ответ не дольше 1 с), `/metrics` (внутренний) с метриками запросов, очередей, блокировок, 409/429.
- Сквозной `request_id` в ответе (`X-Request-Id`) и в задачах очереди.

### 5.5 Масштабирование

API не хранит состояние: сессии и кэш в Redis, файлы в S3, задачи в BullMQ; WebSocket через Redis pub/sub. Тест: два экземпляра API за балансировщиком, запрос с одним, продолжение с другим. Миграции совместимы с работой двух версий API на время выкатки (расширение, затем сжатие). Границы модулей позволяют вынести модуль (нет чужих таблиц, нет общих транзакций между модулями, кроме явных вызовов интерфейса в одной транзакции там, где это указано в архитектуре).

### 5.6 Интернационализация

Все строки интерфейса в словарях (ключ -> строка), в компонентах строк нет (правило линтера); язык интерфейса MVP русский (`ru`); множественные числа через ICU; даты и время хранятся в UTC, показываются в часовом поясе пользователя; английский добавляется словарём без правки компонентов (проверка: подмена словаря тестовым языком не оставляет непереведённых строк).

### 5.7 152-ФЗ и данные

- Данные пользователей из России хранятся и обрабатываются на серверах в России, включая резервные копии (VPS в РФ).
- Явное согласие (FR-AUTH-03), опубликованная политика обработки ПД, удаление по запросу (FR-AUTH-09), доступ по правам, отзывы без автора, токены GitHub зашифрованы, хэши IP хранятся не дольше C-64 (90 дней).
- В GitHub передаются только данные для интеграции (логин, репозиторий); указано в политике и согласии.
- Юридическая проверка текстов и уведомление Роскомнадзора о трансграничной передаче - в чек-лист выпуска (`docs/release.md`, закрывает MEDIUM из backlog) и в открытые вопросы.

### 5.8 Доступность

WCAG 2.1 уровень AA: контраст текста не ниже 4.5:1, управление с клавиатуры, видимый фокус, подписи полей, `aria-live` для статусов (разбор резюме, голосование), не передавать смысл только цветом (награды, статусы). Проверка: axe в сквозных тестах, 0 нарушений уровня critical и serious на ключевых страницах. Интерфейс адаптивный от 360 px.

### 5.9 Стратегия тестирования

- Vitest: модульные и интеграционные тесты API на реальной PostgreSQL и Redis (контейнеры), покрытие строк не ниже C-65 (80%) для кода модулей, для правил наград, голосования, подбора и антифрода - 95% [решение автора].
- Тесты конкурентного доступа - раздел 5.1, на реальной БД, не на моках.
- Playwright: сквозные сценарии среза в браузере, включая axe.
- Тесты контракта: ответы API соответствуют OpenAPI.
- Тесты пишутся до реализации по критериям приёмки (фаза 5); каждый критерий FR отображается хотя бы на один тест (трассировка по идентификатору FR в названии теста).
- Часы в тестах подменяются (таймеры голосования, испытательного срока, охлаждения, 24-часовых проверок).

### 5.10 Доступность сервиса и копии

Целевая доступность 99% в месяц (один VPS) [решение автора]; резервная копия БД ежедневно, RPO не более 24 ч, RTO не более 4 ч; копии хранятся в РФ; подробности и проверка восстановления - в `docs/release.md` (фаза 7).

### 6.2 Связи между модулями (только через публичные интерфейсы)

- teams -> profiles (справочник ролей, уровень), teams -> playbooks (версия сценария), teams -> matching (дефицит в транзакции вступления).
- matching -> teams (открытые места, вступление), matching -> profiles (профиль для оценки).
- workspace -> teams (состав, роли, статус), workspace -> playbooks (этапы, шаги).
- github -> teams (команда по репозиторию), github -> workspace (передача вклада), github -> auth (GitHub id).
- rewards -> teams (состав, места, дефицит), workspace (этапы, вклад), github (проверка репозитория и аккаунта), playbooks (сроки).
- profiles -> rewards (награды в профиле), profiles -> matching (витрина).
- Отзывы (profiles) в rewards не передаются.

Циклический вызов teams <-> matching разрешается так: teams при вступлении запрашивает у matching только расчёт дефицита (чтение), matching запрашивает у teams только данные и операцию вступления; детали - в `docs/architecture.md`.

## 8. Антифрод (проверяемые правила)

Источник: `docs/research/components.md`, раздел 5. Действие: **блок** (завершение или регистрация невозможны), **флаг** (проект в очередь ручной проверки, награды заморожены), **сигнал** (+баллы, при сумме >= C-61 (3) флаг). Каждое правило проверяется автотестом на фикстуре.

| ID | Правило | Действие |
|---|---|---|
| AF-01 | Репозиторий (по `repository_id`) привязан к зачтённому проекту только один раз; форк чужого репозитория без собственных коммитов недопустим | блок |
| AF-02 | Ссылка на релиз уникальна среди зачтённых проектов, отвечает проверкам (FR-WORK-14), не из списка шаблонных доменов (example.com, localhost); страница-заглушка ("coming soon") | блок / флаг |
| AF-03 | Репозиторий создан более чем за 30 дней до старта проекта | флаг |
| AF-04 | Вклад: менее 10 слитых PR / закрытых задач или менее 2 аккаунтов с вкладом | блок |
| AF-05 | Суммарно менее 200 изменённых строк в слитых PR, либо один PR содержит более 80 % изменений | флаг |
| AF-06 | Совпадение SHA-256 файлов артефактов с другим проектом; пустые файлы | флаг |
| AF-07 | Более 70 % событий вклада в последние 48 часов проекта | флаг |
| AF-08 | Название и описание проекта совпадают (нормализованно) с уже зачтённым проектом той же команды | сигнал +1 |
| AF-09 | Длительность менее 14 дней или менее 3 календарных дней с вкладом | блок |
| AF-10 | Этап закрыт быстрее 24 часов или закрыты не по порядку | блок |
| AF-11 | Завершение в течение 24 часов после создания команды, либо все этапы закрыты менее чем за 20 % плановой длительности | флаг |
| AF-12 | 3 и более этапа закрыты в течение 1 часа | сигнал +1 |
| AF-13 | Узкий круг: одни и те же 3 и более человек завершили 2 и более проектов вместе без других участников: +1; 3 и более проектов: флаг; для значков серии "Проекты" такие проекты считаются как 1 | сигнал / флаг |
| AF-14 | Пометка "желательная" выставлена менее чем за 7 дней до завершения | сигнал +1 |
| AF-15 | Один GitHub id = одна учётная запись; один нормализованный email (FR-AUTH-06) = одна запись; одноразовые домены | блок регистрации |
| AF-16 | Возраст GitHub-аккаунта менее 30 дней или нет публичной активности: зачёт откладывается (не блок регистрации и участия) | отложенный зачёт |
| AF-17 | Общий IP / отпечаток (хэш User-Agent + подсеть /24 + cookie id) у двух участников команды +1, у трёх и более +2 | сигнал |
| AF-18 | Идентичные тексты профиля/резюме (нормализованный хэш) у разных учёток | сигнал +2 |
| AF-19 | Регистрации и вступления двух аккаунтов в команду в пределах 10 минут | сигнал +1 |
| AF-20 | Вклад одного участника 100 % при остальных без единого события | сигнал +2 |
| AF-21 | Связь аккаунтов (суммарные признаки >= 3) - флаг, а не блок | флаг |
| AF-22 | При сумме сигналов >= 2 - не более 1 зачтённого проекта на человека в 14 дней | ограничение |
| AF-23 | Время событий - серверные `received_at`; вклад по числовому GitHub id | правило данных |
| AF-24 | Охлаждение 7 дней: награды и зачёт применяются позже; в охлаждении проект можно оспорить | процесс |
| AF-25 | Все решения администратора пишутся в журнал (кто, что, когда, причина) | аудит |

1. Юридическая проверка текста согласия и политики ПД; трансграничная передача в GitHub; уведомление Роскомнадзора (вынесено в `docs/release.md`).

5. Как передаётся установка GitHub App при смене тимлида (FR-TEAM-14): повторная установка или передача.
6. Подтвердить решения автора: хранение отзывов (автор не отдаётся, но хранится служебно); возврат в очередь только после исключения тимлидом; порог автодобавления 0.5; веса подбора; 5 ролей в заявке; 12 мест на команду; размер лимитов частоты; роль администратора совмещает справочники и модерацию; определение дефицита без кэша внутри транзакции (приемлемо, что параллельные вступления на разные места могут читать немного устаревшие счётчики).
7. Ссылка на релиз для ML-продукта: решено оркестратором (FR-WORK-14, `docs/playbooks.md`, 4.1): только работающий публичный адрес (демо-страница либо API с `/docs` или `/health`, HTTP 200); вариант "GitHub Releases без публичного адреса" исключён.
