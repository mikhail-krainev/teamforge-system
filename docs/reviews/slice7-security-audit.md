## Находки

### S7SEC-01 [HIGH] Решение "в порядке" зачитывает проект сразу: нет охлаждения и нет проверок фазы `cooling_end` (AF-22)

- **Где:** `apps/api/src/modules/rewards/internal/admin/fraud-case.service.ts:117-130` (`settle`: для `cooling`/`frozen` сразу `applier.apply`), `:133-140` (`creditInputs`); `apps/api/src/modules/rewards/internal/admin/dispute.service.ts:16-18, 45` (любая жалоба в охлаждении переводит проект в `frozen`).
- **Суть:** `decideFraudCase(ok)` для проекта в `frozen` вызывает `CreditApplier.apply` в тот же момент. `coolingUntil` не проверяется, антифрод фазы `cooling_end` не запускается, а это AF-22 (не больше 1 зачтённого проекта на человека за 14 дней при сумме сигналов >= 2) и повторная проверка AF-13/AF-17/AF-19 на свежих данных. После решения жалобы невозможны (`disputable` даёт `false`), поэтому окно жалоб FR-REW-11/AF-24 для остальных участников закрывается досрочно.
- **Сценарий:** группа мультиаккаунтов завершает несколько проектов подряд, у каждого сумма сигналов 2 (AF-17 пара +1, AF-19 +1). Это ниже порога C-61, проект уходит в `cooling`, и в конце охлаждения AF-22 его бы заморозил. В день завершения один из участников подаёт правдоподобную жалобу ("участник X мало делал"). Проект `frozen`, открыто дело. Администратор видит сумму 2 без флагов и решает "в порядке". Проект зачитан сразу, AF-22 не вычислялся ни разу. Так повторяется каждую неделю.
- **Исправление:** решение `ok` не выдаёт зачёт само, а возвращает проект в охлаждение:
  ```ts
  // settle(), decision === 'ok'
  if (run.status === 'frozen' || run.status === 'cooling') {
    await this.runs.setState(run.teamId, { status: 'cooling' });
    if (now < run.coolingUntil) await this.scheduleCooling(run.teamId, run.coolingUntil); // тот же jobId('credit', teamId)
    else await this.creditService.creditProject(run.teamId); // фаза cooling_end, AF-22 вычисляется
  }
  ```
  Чтобы повторная заморозка тем же набором сигналов не открывала дело заново, `creditInTx` должен учитывать флаг "дело решено ok" (поле `credit_run.reviewed_ok_at`) и замораживать только по новым правилам (AF-22 и правилам, которых в решённом деле не было). Тест: дело по жалобе -> `ok` до `coolingUntil` -> зачёта нет, `run.status = cooling`; после срока срабатывает AF-22.

### S7SEC-02 [MEDIUM] Зачёт после удаления аккаунта снова записывает данные удалённого (152-ФЗ, FR-AUTH-09)

- **Где:** `apps/api/src/modules/rewards/internal/services/credit-applier.service.ts:51-86` (строки по `snapshot.roster.members`), `:182-184` (командная награда всем из снимка); `apps/api/src/modules/rewards/internal/services/pending-recheck.service.ts:255-279`; `apps/api/src/modules/rewards/internal/events/deletion.consumer.ts:30-61` (шаг выполняется один раз); `apps/api/src/modules/profiles/internal/reviews/eligibility-scan.ts:57-61`.
- **Суть:** шаг `rewards` в саге удаляет награды, счётчики и зачёты один раз. Снимок завершения (workspace в саге не участвует) по-прежнему содержит id удалённого. Если человек удалился во время охлаждения, `apply` в конце охлаждения вставляет для него `project_credit`/`credit` (`denied` или `pending_account`) и командную награду `closed_vacancy`. Ежедневный `pending-account-recheck` потом может повысить его до `credited`, тогда растут `counter` и уходит `credits_changed` в matching. Похожий случай в `review-eligibility-scan`: если строк окна у команды не осталось (удалились все участники), сканер создаст их заново по снимку.
- **Сценарий:** участник запросил удаление на 3-й день охлаждения, сага завершилась и записала в журнал "удалено". На 7-й день в `rewards.award` и `rewards.project_credit` снова появляются строки с его `user_id`. SQL-проверка FR-AUTH-09 ("наград нет") становится ложной, и данные попадают в резервные копии.
- **Исправление:** в `apply`, `promote` и `teamBonusRecipients` пропускать удалённых: получать `AuthApi.getIdentity`/`getAccountFacts` со статусом и исключать `status = 'deleted'` (или хранить в rewards таблицу `erased_user` и читать её в той же транзакции). В `EligibilityService.record` фильтровать удалённых так же. Интеграционный тест: удаление в охлаждении -> конец охлаждения -> в `rewards.*` нет строк с этим `user_id`.

### S7SEC-03 [MEDIUM] Администратор решает дело собственной команды

- **Где:** `apps/api/src/modules/rewards/internal/admin/fraud-case.service.ts:83-114` (`decide`), `:76-81` (`get`); политика `admin` в `apps/api/src/modules/auth/internal/services/admin-policy.ts`.
- **Суть:** роль администратора совмещается с ролью пользователя (spec, таблица ролей), но `decide` не проверяет, был ли `adminId` в составе команды (снимок `roster.members` и `departedUserIds`). Администратор-участник может подтвердить "в порядке" свой замороженный проект и выдать себе награды. Ещё он читает тексты и точное время жалоб своих сокомандников: `getFraudCase` отдаёт `createdAt` до миллисекунды, и по нему легко понять, кто жаловался.
- **Сценарий:** администратор справочников вместе с двумя своими аккаунтами проходит проект. AF-21 даёт флаг, и он сам закрывает дело решением `ok`. Журнал AF-25 это фиксирует, но не мешает.
- **Исправление:** в `decide` до блокировок проверять `snapshot.roster.members/departedUserIds` (через `SnapshotReader`) и отвечать 403 `FORBIDDEN` (`code: conflict_of_interest`). В `toDtos` для такого администратора не отдавать `disputes`. В карточке дела дату жалобы показывать днём, а не временем.

### S7SEC-04 [MEDIUM] Общие лимиты частоты `apiRead`/`apiWrite` объявлены, но нигде не применяются

- **Где:** `apps/api/src/platform/ratelimit/rate-limiter.ts:24-25`. Вызовов `enforce('apiRead'|'apiWrite')` в `src/` нет, глобального хука тоже нет (`platform/http/fastify.ts:61-76`). Архитектура 13.6 требует "120/мин; изменяющие 60/мин" для всего API.
- **Суть:** у новых операций нет ни своего лимита, ни общего. Записи частично защищены уникальностью (одна пара в `peer_review_pair_uq`, одна жалоба в `dispute_team_user_uq`), но отказы (404/409/422) квоту не тратят, и их можно слать без ограничений. Каждый такой запрос берёт `FOR SHARE` на `review_eligibility` или блокировку #11 `credit_run`. Чтение `listUserAwards`/`getUserCounters` по любому `userId` не ограничено, и это массовое снятие профилей наград всех пользователей.
- **Сценарий:** скрипт с одной сессией шлёт тысячи `POST /v1/teams/{id}/disputes` в секунду по проекту в охлаждении. Каждый берёт `credit_run FOR UPDATE`, и таймер зачёта и решения администратора стоят в очереди за блокировкой (CC-12).
- **Исправление:** глобальный `RateLimitGuard` (или хук `preHandler`) по `userSubject`/`ipSubject`: `apiRead` для GET, `apiWrite` для остальных, с заголовками 13.6. Для `createDispute` и `createPeerReview` дополнительно своя категория (например, 10/ч на пользователя), которая считает и отказы.

### S7SEC-05 [MEDIUM] Мультиаккаунты с одинаковым текстом профиля не ловятся: AF-18 выключен, AF-21 требует совпадения всех трёх сетевых признаков

- **Где:** `apps/api/src/modules/rewards/internal/services/fraud-facts.service.ts:102-104, 190` (`textHolders: {}`, `textHash: null`); `apps/api/src/modules/rewards/internal/fraud/rules/AF-21.ts:62-69`, `thresholds.ts` (`LINK_FEATURES = 3`). Уже записано в `docs/backlog.md` (срез 7) как MEDIUM.
- **Суть:** без отпечатка текста AF-18 (+2) никогда не срабатывает. AF-21 может набрать 3 признака только при одновременном совпадении подсети /24, User-Agent и cookie устройства. Достаточно разных браузеров (другой UA и cookie) из одной сети, и AF-21 молчит, а AF-17 даёт лишь +1.
- **Сценарий:** один человек ведёт три аккаунта с копией резюме, каждый в своём браузере. Сумма: AF-17 +1, AF-19 +1, итого 2 < C-61. Проект зачитан (а с S7SEC-01 зачитан даже при AF-22).
- **Исправление:** порт `ProfileFingerprintsPort` в `rewards/public.ts`, адаптер вне `modules/` читает `profile.text_fingerprint` (только хэши, FR-REW-13 не нарушается: тексты отзывов недоступны). До порта временно снизить `LINK_FEATURES` до 2 для пар с общей подсетью и устройством.

### S7SEC-06 [MEDIUM] Порог "не менее 2 авторов" раскрывает автора при сговоре, особенно в команде из трёх

- **Где:** `apps/api/src/modules/profiles/internal/reviews/review-rules.ts:9` (`MIN_REVIEW_AUTHORS = 2`), `review.repository.ts:161-190` (`settleTeam`).
- **Суть:** минимальная команда C-01 = 3 человека. Если адресат договорился с одним сокомандником, тот пишет пустой отзыв "для порога". Пакет из двух отзывов публикуется, и единственный оставшийся участник однозначно опознан как автор второго текста. Без сговора в команде из трёх публикация тоже означает "оба написали", и связать текст с автором можно по стилю. Это слабость требования FR-PROF-08 (2), а не ошибка реализации, но цель SEC-04 ("нельзя вычислить по малому числу авторов") для малых команд не достигается.
- **Сценарий:** команда A, B, X. B по просьбе X пишет "ок". A пишет критический отзыв о X. После окна X видит два текста и знает, что критика от A.
- **Исправление (решение автора spec):** порог `max(2, ...)` плюс условие "в проекте не меньше 4 участников из снимка" или порог 3 автора. Если адресату известен состав < 4, отзывы удерживать. Обновить FR-PROF-08, подсказку в `i18n/ru/reviews.json` и тест "команда из 3, два автора -> пусто".

### S7SEC-08 [LOW] Экранирование текста отзыва на сервере: двойное в вебе и неполное для других потребителей

- **Где:** `apps/api/src/modules/profiles/internal/reviews/review-rules.ts:27-34`, `received-reviews.query.ts:86`; `apps/web/src/features/reviews/ReviewLists.tsx:27`.
- **Суть:** API отдаёт `&lt;b&gt;`, а React экранирует ещё раз, и адресат видит сущности буквально. Кавычки `"` и `'` не экранируются, поэтому будущий потребитель, который вставит текст в атрибут или через `innerHTML` (письмо, экспорт), окажется уязвим и при этом будет считать текст "уже безопасным".
- **Исправление:** отдавать текст как есть (это JSON), экранировать на месте вывода (React уже делает это). Если серверное экранирование нужно по контракту, экранировать и `"`, `'`, а в вебе текст не экранировать повторно.

### S7SEC-09 [LOW] Вторая связь "автор - адресат - время" в `platform.idempotency_key`

- **Где:** `apps/api/src/platform/idempotency/idempotency.service.ts:36-38, 124-145`; ответ `createPeerReview` (`review.service.ts:119`) содержит `subjectUserId`.
- **Суть:** строка ключа хранит `user_id` автора, `operation_id = createPeerReview`, `response_body.subjectUserId`, `created_at` (точное время записи) и несолёный SHA-256 от `teamId`, `subjectUserId` и текста. Это 24 часа в БД и до C-37 в резервных копиях. Тот, кто имеет доступ к БД или копии и знает опубликованный текст, подтверждает автора хэшем. Эта связь обходит обещание "связь с автором хранится только в `peer_review_authorship`". Сага удаления строки ключей удаляет, это хорошо.
- **Исправление:** для `createPeerReview` хранить в ответе только `{status}` (или выбрасывать `subjectUserId` из сохраняемого тела) и считать `requestHash` как HMAC с серверным ключом, а не голый SHA-256. Альтернатива: исключить операцию из хранения ответа, оставив только `requestHash` (HMAC).

### S7SEC-10 [LOW] Автор отзыва в открытом виде в `peer_review_authorship` (рекомендация SEC-04 п. 4 не принята)

- **Где:** `apps/api/drizzle/0019_slice7_rewards_reviews.sql:14-20`, `apps/api/src/modules/profiles/internal/schema/profiles.ts:193-207`.
- **Суть:** обзор фазы 3 предлагал `author_key = HMAC(team_id || author_id, REVIEW_HMAC_KEY)`. Сейчас `author_user_id` и `review_id` лежат рядом, и любой SQL-доступ под `tf_app` (или копия) однозначно связывает текст с автором. Граница проходит только по коду (dependency-cruiser), а не по правам БД.
- **Исправление:** либо HMAC-ключ автора, а `listSentReviews` перевести на поиск по HMAC, либо отдельная роль БД без SELECT на `peer_review_authorship` для всех путей, кроме записи и саги. Решение зафиксировать в `docs/decisions.md`.

### S7SEC-11 [LOW] Свободный текст администратора переживает удаление, журнал AF-25 изменяем

### S7SEC-12 [LOW] Пробелы антифрода в данных: AF-06 не видит удалённые файлы, сигналы шагов не доходят, AF-17 только внутри команды

### S7SEC-13 [LOW] Фильтр `visibleData` пропускает любое число и строку вида `[a-z0-9_]{1,32}`

- **Где:** `apps/api/src/modules/rewards/internal/admin/fraud-case-dto.ts:7, 16-20`.

Первое правило, которое положит в `data` `githubUserId` (число) или логин GitHub в нижнем регистре, без дефиса, раскроет ПД администратору без ревью.

## Что сделано хорошо

- Анонимность отзывов реализована по SEC-04: UUID v4 и `sort_key = randomInt`, в `peer_review` нет `created_at`, одна дата пакета на всех, порядок по случайному ключу. Публикация одним пакетом после окна под `FOR UPDATE` строк окна против `FOR SHARE` при записи (гонки "запись после публикации" нет). Удержание при одном авторе и удаление через 30 дней. Нет событий и уведомлений при создании, уведомление о публикации без числа и автора. Запрос выдачи не касается `peer_review_authorship` (правило dependency-cruiser).
- `listReceivedReviews` берёт адресата только из сессии. Курсор привязан к фильтру `subject`, чужой курсор не подставить.
- Журналы: сериализаторы не пишут URL, заголовки и тела, `*.text` в redact. Ошибки БД сериализуются без `detail`.
- Схема входа строгая: `additionalProperties: false`, длины (`text` 1..2000 и `char_length` в CHECK, жалоба 20..4000, комментарий 10..4000), `decision` enum. `teamId` проверяется как UUID до SQL.
- Идемпотентность и гонки: `ON CONFLICT DO NOTHING RETURNING` для зачётов, счётчики двигаются только на реально изменённые строки, блокировка #11 + `FOR UPDATE` дела, "одно решение из десяти" (CC-12). Отзыв наград по `RETURNING`, пересчёт `pending_account` не трогает отозванный проект.
- Сигналы антифрода хранят только HMAC и id. Администратору отдаются счётчики списков и короткие коды, IP, подсети и отпечатки не уходят ни администратору, ни участникам. `getTeamCredit` не раскрывает `fraudScore` и сигналы.
- Сага: шаги `profiles` (отзывы о человеке, связи авторства, окна) и `rewards` (награды, счётчики, зачёты, жалобы, вычёркивание id из `fraud_signal.data`). `rewards` добавлен в `EXPECTED_DELETION_MODULES`.
- SQL везде параметризован (`sql\`\``, Drizzle). `sql.raw` только для констант режима блокировки, `sql.identifier` для имени колонки из константы.
- Веб: тексты отзывов и жалоб выводятся через React без `dangerouslySetInnerHTML`, `caseId` проверяется как UUID до запроса, решение администратора идёт через диалог подтверждения с ключом идемпотентности. Ссылка на админку видна только `isAdmin`, право проверяет API.
- Секретов в диффе нет.
