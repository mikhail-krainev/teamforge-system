## Что сделано хорошо

- Подпись вебхука: строгий формат `^sha256=[a-f0-9]{64}$`, HMAC по сырым байтам, `timingSafeEqual` с проверкой длины, при отсутствии секрета подпись не совпадает никогда. Тело читается в `preParsing` с потолком до буферизации, лимит по адресу стоит до первого байта, а Fastify получает заглушку `{}`, поэтому неподписанное тело никогда не попадает в JSON-парсер.
- Дедупликация по `delivery_id` (PK, `ON CONFLICT DO NOTHING`, `jobId = delivery_id`). Событие привязывается к команде только через активную `repo_link` той же установки (SEC-06). Нерелевантные доставки хранятся без `payload`. Разрушительные события (`installation.deleted/suspend`, `installation_repositories.removed`, `repository.deleted/transferred/renamed`) применяются только после проверки через GitHub по JWT App или токену установки.
- Installation flow: `state` из 32 случайных байт, в Redis лежит только его SHA-256, одноразовость через `GETDEL`, привязка к `userId` сессии, `assertLead` и повторная проверка тимлида под блокировкой #4. Обязательный `code` и проверка установки по `GET /user/installations`, учёт `suspended_at` и прав App. Редирект строится только из `APP_ORIGIN`, UUID команды из `state` и кода ошибки `[a-z_]`, открытого редиректа нет. На web параметры `installation` и `error` проверяются регулярными выражениями, `installUrl` открывается только по `https:`.
- Факты о репозитории при привязке берутся у GitHub по `repository.id` токеном установки, а не из тела запроса. Grant проверяется и до запроса к GitHub, и внутри транзакции. Курсор `listAvailableRepositories` привязан к `(teamId, installationId)`. Отсутствие grant даёт 404, существование установки не раскрывается.
- Токены установок в Redis запечатаны AES-256-GCM (`SecretBox`), TTL 55 минут, отдаются с запасом 60 с. Ключи ограничены ACL. User-токен в БД не попадает. Сообщения `GithubError` не содержат URL, заголовков и тел ответов. В журнал Octokit пишется `NO_LOG`. В `REDACT_PATHS` добавлены `state`, `code`, `userToken`, `installationToken`, `privateKey`.
- Лимиты GitHub: `Retry-After` и `X-RateLimit-Reset` учитываются, пауза ограничена 2 часами и никогда не сокращается. Интерактивные запросы не ждут и отвечают 503. Пагинация сверки ограничена (`MAX_PAGES = 30`, `MAX_INSTALLATION_PAGES = 10`).
- Лента и вклад: каждый запрос ограничен `teamId` из пути. Курсор привязан к хэшу фильтров, подмена ключа курсора не выходит за пределы команды. `relabelContribution` выбирает запись по `(id, team_id, user_id)`. Заголовки с GitHub выводятся как текст, ссылкой становится только `https://`, с `rel="noopener noreferrer"`.
- Завершение: API сам не открывает адреса студентов, все проверки идут через `link-checker` (SSRF-клиент SEC-05). Снимок неизменяем: триггер `BEFORE UPDATE OR DELETE` (0016), у `tf_app` только DML без `TRUNCATE` и без владения таблицей, поэтому отключить триггер он не может. В снимке только id, без имён и e-mail.
- Fail-fast для группы GitHub App: ключ разбирается как RSA, секрет вебхука не короче 16 символов и не слабый, в production нельзя переопределить базовые URL GitHub. Секретов в репозитории нет: в тестах ключ генерируется (`processKey()`), значения явно тестовые.
