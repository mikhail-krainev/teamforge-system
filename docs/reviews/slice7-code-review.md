## CRITICAL

### C-1. Чтения через общий клиент `DB` внутри транзакции в новом коде антифрода (исчерпание пула)

Файлы и строки:

- `apps/api/src/modules/auth/internal/services/auth.service.ts:185-239`: новый `getAccountFacts` и `tombstonedHmacs` читают через `this.db` (общий клиент). Так же читает `getIdentitySignals` (`:135-146`).
- `apps/api/src/modules/github/internal/services/antifraud-facts.service.ts:35`: `accountChecks` вызывает `auth.getAccountFacts` и затем читает через `this.tx.tx`.
- `apps/api/src/modules/rewards/internal/services/fraud-facts.service.ts:122-126`: девять запросов в одном `Promise.all`. Среди них `auth.getAccountFacts`, `github.getAccountChecks` (внутри снова `getAccountFacts`) и `auth.getIdentitySignals`: три или четыре чтения общим клиентом параллельно с транзакцией.

Пути, где это выполняется внутри открытой транзакции:

1. `CompletionConsumer.handle` (`events/completion.consumer.ts:29`) вызывает `CreditRunService.open`. Обработчик идёт через `InboxService.runOnce` в `tx.run` (`events.processor.ts:42`). Очередь `events` работает с `concurrency: 20` (`queue-definitions.ts:18`), `DATABASE_POOL_MAX` по умолчанию 20 (`config.ts:64`).
2. `CreditRunScan.openOne` (`credit-run-scan.service.ts:53`): `tx.run(() => runService.open(...))`.
3. `FraudCaseService.decide` (`admin/fraud-case.service.ts:92`): `creditInputs` выполняется внутри `tx.run`, до `lockCreditRun`. Он вызывает `verdicts.load`, затем `github.getAccountChecks` и `auth.getAccountFacts` через общий `DB`.

Сценарий отказа:

- Двадцать завершений проектов подряд (массовое завершение, сканер после простоя, повторная доставка). Каждый из 20 обработчиков держит соединение транзакции и ждёт ещё одно соединение для `getAccountFacts` и `getIdentitySignals`.
- Пул пуст, ожидание соединения у postgres-js не ограничено. Воркер встаёт, окно `events` заблокировано, а вместе с ним остальные потребители (уведомления, matching).
- Те же 20 соединений нужны HTTP: API с общим пулом перестаёт отвечать. Это тот самый класс ошибки, найденный раньше. Для `decide` риск ниже (редкая операция), но тоже реален под нагрузкой: транзакция держит соединение, пока ждёт блокировку #11.

Исправление:

- Дать `auth` транзакционные версии `getAccountFacts` и `getIdentitySignals`: через `TxRunner.tx`, как у `TeamsFacade` и `AntifraudFactsService`. Либо читать эти данные до `BEGIN`, как сделано в `creditProject`.
- Для `decide`: прочитать `creditInputs` до `tx.run` (как `creditProject`). Это нарушает «одна транзакция на операцию»? Нет, чтения вне транзакции допустимы; архитектура 10.4 разрешает «чтения до блокировки».
- Для `open`: вынести `factsOf.build` из транзакции потребителя. Для потребителя это значит читать до `runOnce` либо перевести `auth` на транзакционный клиент.
- Убрать повторный `getAccountFacts`: `accountChecks` вызывает его, и `FraudFactsService.read` вызывает его же. Передать результат одним вызовом.
- Добавить тест CC: 25 параллельных `open` или `decide` при `DATABASE_POOL_MAX=5` должны завершиться, а не повиснуть.

## MEDIUM

### M-1. Двойное экранирование текста отзыва: пользователь видит `&amp;`, `&lt;`

`profiles/internal/reviews/received-reviews.query.ts:86` отдаёт `escapeReviewText(row.text)` (сущности HTML), а `apps/web/src/features/reviews/ReviewLists.tsx:27` выводит `{item.text}` как текст React: ещё раз экранируется браузером.

Сценарий отказа: отзыв «Q&A, R&D, a < b» показывается как `Q&amp;A, R&amp;D, a &lt; b`.

Исправление: выбрать одно место. Либо API отдаёт исходный текст (React экранирует сам), либо клиент декодирует. Рекомендую первое и тест «`<script>` приходит как текст, не исполняется» на уровне фронтенда.

### M-3. AF-17: общий `ua` считается самостоятельным признаком: много ложных заморозок

`auth/internal/services/identity-signals.service.ts:48-51` пишет `ua` как HMAC сырого User-Agent без привязки к подсети или cookie. `fraud/rules/AF-17.ts:7-35` оценивает `ua` отдельно. Спецификация: отпечаток = хэш User-Agent + подсеть /24 + cookie id.

### M-4. «Нарушение» не отзывает ряд наград, построенных на отозванном проекте; счётчик и значки расходятся

`credit-applier.service.ts:105-111`, `award.repository.ts:revokeOfTeam`: отзываются награды с `team_id` отозванного проекта. Ряд («Трое в строю», «Пятёрка проектов», «Многоликий» и др.) выдан по проекту, где достигнут порог, а он может быть не отозванным.

Сценарий: проекты A, B, C зачтены, «Трое в строю» привязан к C. Нарушение по A: счётчик 2, значок остаётся. FR-REW-12 говорит «награды проекта отзываются» и «счётчики уменьшаются». Значки при этом перестают соответствовать счётчикам.

Исправление: после `revoke` пересчитать индивидуальные значки пострадавших по `credits.stats` и отозвать те, чей порог больше не достигается.
