## Что сделано хорошо

- Условия завершения вынесены в чистые функции `completion-rules.ts`. Они читаются под блокировкой `lockTeam(teamId, 'update')`. Единственность проекта держит `project_completion.team_id` (PK) плюс триггер на UPDATE и DELETE (миграция 0016).
- Конкурентность привязки репозитория закрыта уникальными частичными индексами `repo_link_repository_uq` и `repo_link_team_active_uq`, оба замаплены в `constraints.ts`. Порядок блокировок (команда, затем строка link) соблюдается и в `unlink`, и в lifecycle-обработчике (команды по возрастанию id).
- Вебхук: подпись проверяется по сырым байтам в постоянное время и жёстким форматом заголовка. Сырое тело читается с лимитом до парсинга. Дедупликация идёт по PK `delivery_id` с `ON CONFLICT DO NOTHING`. Блокировка строки доставки и `InlineDelivery` дают атомарность «processed = вклад существует». Есть sweeper, retention и привязка installation и repository к активной ссылке (SEC-06).
- Разрушающие lifecycle-события (deleted, removed, suspend) подтверждаются запросом к GitHub, а не одной подписью.
- Модульные границы: в `modules/**` нет ни одного импорта `*/internal/*` чужого модуля, чужие таблицы не читаются. Всё идёт через `GITHUB_API`, `TEAMS_API`, `PLAYBOOKS_API`.
- Файлы не больше 800 строк (максимум 355), отладочного вывода нет. OAuth `state` одноразовый (GETDEL, в Redis только хэш), в логах он вырезан.

## HIGH

### H-1. AF-04: вклад считается по строкам `contribution`, а не по задачам и PR
`apps/api/src/modules/workspace/internal/domain/completion-rules.ts:138-160` (`countedWork`, `contributionTooLow`).

Проблема: `countedWork` возвращает строки contribution (ключ `team_id, source, ref, user_id`). Задача с двумя assignees даёт 2 строки: `ContributionConsumer.credit` пишет по строке на каждого из `userIds`. Один и тот же слитый PR или закрытая задача учитывается дважды, и порог C-52 (10) достигается пятью задачами. `contributorsTooFew` при этом выполняется «бесплатно», потому что один элемент зачтён двум аккаунтам. Спека FR-WORK-13(6) и AF-04 говорят про «10 слитых PR или закрытых задач», то есть про элементы. Это обход блока антифрода двумя заговорщиками.

Исправление: считать `new Set(items.map(c => `${c.source}:${c.ref}`)).size`. Тест: одна задача и два assignees дают count 1. `ContributionFact` нужно расширить полем `ref`.

### H-2. AF-02: проверка повтора адреса релиза неполна (LIMIT 200, ILIKE по подстроке, нет нормализации `www.`)
`apps/api/src/modules/teams/internal/services/teams-facade.service.ts:262-279`; `completion-rules.ts:198-224`.

Проблема:
1. `listCompletedReleaseUrls` берёт кандидатов через `ILIKE '%host%' ... LIMIT 200` без `ORDER BY`. Студенческие проекты массово живут на общих доменах (`vercel.app`, `github.io`, `onrender.com`), поэтому дубликат за пределами 200 строк тихо пропускается. Выборка недетерминирована.
2. Подстрока `www.foo.app` не находит сохранённый `https://foo.app/x`, а `releaseAddressKey` не отбрасывает `www.`. Достаточно дописать `www.`, чтобы обойти блок.
3. `ILIKE %…%` по `team.release_url` идёт без индекса, это seq scan по `team` при каждом завершении.

Исправление: хранить нормализованный ключ (`host` без `www.` и без точки в конце, плюс `path` без хвостового `/`) отдельной колонкой с индексом, например `team.release_key`, и проверять равенством без LIMIT. Либо добавить уникальный частичный индекс по этому ключу для `status='completed'`, чтобы даже гонка двух завершений не прошла (AF-02 и CC-13). Привести функции `releaseAddressKey` и host-фрагмент к одной нормализации. Заодно пересмотреть `.toLowerCase()` пути: пути регистрозависимы, но в сторону ложных срабатываний это допустимо.

### H-3. Сверка GitHub теряет хвост истории: `lastSyncedAt` двигается и при недочитанных лентах, а тик равного `updated_at` не применяется
`apps/api/src/modules/github/internal/jobs/repo-sync.service.ts:16, 56-67, 86-100, 125-133`.

Проблема:
1. `readFeed` при `MAX_PAGES` (30 страниц, 3000 элементов) возвращает `undefined` и не сохраняет ETag, но `syncRepository` всё равно пишет `lastSyncedAt = startedAt` (стр. 66). Следующий запуск считает `cutoff = lastSyncedAt − 1h`, и всё, что старше и не успело прочитаться, больше никогда не читается. Комментарий «a repository with more history is finished by the next runs» (стр. 15) неверен. `isStale` тоже считает такой репозиторий свежим, и `github-sync-resume` его не возобновит. Это прямо про критерий «возобновление sync-задачи».
2. `isKnown` (стр. 125-133) и `ItemRepository.upsert` (`item.repository.ts:96`) пропускают событие при `stored.sourceUpdatedAt >= incoming`. У GitHub `updated_at` с точностью до секунды. Два события в одну секунду (assigned и closed от скрипта, labeled сразу после opened) дают то, что второе отбрасывается. Сверка тоже не исправит расхождение, потому что `updated_at` совпадает. Итог: потерянный вклад навсегда.

Исправление: (1) двигать `lastSyncedAt` только если обе ленты дочитаны до `behind` или конца, иначе сохранять курсор («прочитано до страницы N» или «самый старый `updated_at` прочитанного») и продолжать с него; в `isStale` учитывать незавершённость. (2) При равных `updated_at` применять событие, если оно «продвигает» состояние (`closed` или `merged` поверх `open`), либо сравнивать составной ключ `(updated_at, state_rank)`; в `isKnown` при равенстве сверять и поля состояния (`state`, `merged`).

## MEDIUM

### M-1. N+1 в сверке: запрос и вызов GitHub на каждый элемент
`repo-sync.service.ts:104-133, 150-166`.
`isKnown` делает по SELECT на элемент (до 100 на страницу, до 3000 на ленту). `handlePull` делает `getPull` и `listReviews` на каждый PR, а `upsertReview` идёт в отдельной транзакции на каждое ревью. Нарушено правило «никаких запросов в циклах» и тратится квота GitHub.
Исправление: на странице один `SELECT … WHERE (repository_id, kind) AND number = ANY($1)`; ревью пачкой (`INSERT … VALUES … ON CONFLICT`); `getPull` только для PR, чьё состояние изменилось (в ленте `pulls` уже есть `merged_at` и `state`).

### M-2. `LinkChecks.run` опрашивает Redis каждые 200 мс по каждому заданию до 11 минут
`apps/api/src/modules/workspace/internal/services/link-checks.ts:39-48, 51-61`.
При 20 ссылках это около 100 запросов Redis в секунду на одну проверку, плюс воркер `auto-checks` занят до ~23 минут (release 11 минут и затем ссылки 11 минут). Это нагрузка и риск лимита `lockDuration`.
Исправление: `QueueEvents.waitUntilFinished(job)` или `job.waitUntilFinished`, либо ограничение по общему дедлайну на всю проверку и опрос с backoff (1-5 с). Release и ссылки запускать параллельно, а не последовательно.

### M-3. Мастер установки не привязан к GitHub-аккаунту тимлида
`apps/api/src/modules/github/internal/installation/setup-callback.service.ts:77-88`.
`findUserInstallation` проверяет, что установка доступна тому, кто авторизовал `code`, но не сравнивает `GET /user` id с привязанным `identity.githubUserId` тимлида. Тимлид может пройти OAuth чужим GitHub-аккаунтом (с доступом к установке на чужую организацию) и получить `installation_grant` на неё. Затем он может привязать репозиторий, к которому его собственный аккаунт отношения не имеет. Требование SEC-02 «доказать доступ» выполнено не полностью.
Исправление: после `exchangeUserCode` запросить `/user`, сравнить `id` с `AuthApi.getIdentity(userId).githubUserId`; при несовпадении `refused('not_lead')` или новый код `account_mismatch`.

### M-4. Квота вебхука отвечает 429, а GitHub не повторяет доставки автоматически
`webhook-receiver.service.ts:68-70`; `rate-limiter.ts:28-30` (600 в минуту на установку).
Всплеск событий (массовое закрытие задач, импорт) отбрасывает доставки, и они восстановятся только суточной сверкой (а при H-3 возможно вообще нет). Лимит применяется до записи в `webhook_delivery`.
Исправление: при превышении лимита всё равно вставлять строку `received` (без постановки в очередь), чтобы её подобрал sweeper. Либо поднять лимит и отвечать 202. Лимит оставить как защиту очереди, а не как отказ.

### M-5. Вклад может появиться после снимка завершения без блокировки команды
`workspace/internal/events/contribution.consumer.ts:63-92` и `completion.service.ts:76-133`.
`ContributionConsumer.credit` не берёт блокировку #4. Webhook-транзакция, начавшаяся до завершения и закоммитившаяся после, добавит строку `contribution` вне `snapshot` с `role_locked=false` (`lockRoles` её не видит). Комментарий класса `CompletionService` обещает, что снимок видит каждое изменение «целиком до или целиком после», но для кредита по вебхуку это не выполняется. Реальной дыры в статусе нет (ссылка уходит в `completed`, и `relabel` закрыт статусом), но фид и снимок расходятся.
Исправление: в `credit` брать `teams.lockTeam(teamId, 'share')` и пропускать запись, если статус `completed` или `archived`.

### M-6. Нет защиты от параллельных проверок готовности
`completion-check.service.ts:85-98`.
`request` под `share`-блокировкой создаёт новую строку на каждый вызов. Параллельные клики или разные Idempotency-Key запускают несколько проверок, каждая со своими link-check заданиями (до 20+ ссылок) и 11-минутным ожиданием.
Исправление: если для команды уже есть `queued` или `running` проверка моложе `CHECK_GIVE_UP_AFTER_MS`, вернуть её (с блокировкой `update` для сериализации или частичным уникальным индексом по `(team_id) WHERE status IN ('queued','running')`).

### M-7. Нет индекса под `findHolding` по `team_id`
Миграция 0015; `repo-link.repository.ts:27-37`.
`findHolding` фильтрует `team_id = ? AND status IN ('active','completed')` и сортирует по `linked_at`. Частичный `repo_link_team_active_uq` покрывает только `active`, а `completed` читается seq scan. Запрос идёт на каждый `getRepoLink`, проверку и завершение.
Исправление: `CREATE INDEX repo_link_team_idx ON github.repo_link (team_id, linked_at DESC)`. Заодно проверить, нужен ли `gh_item_author_idx` (под него запросов в коде не найдено).

## LOW

- **L-1.** `raw-body-gate.ts:77-83`: тело до 5 МиБ буферизуется до проверки подписи (политика актора выполняется позже, чем `preParsing`), а проверка IP-лимита пропускается для loopback. Безопасность держится на корректном `TRUSTED_PROXY_CIDRS`; в продакшене за reverse proxy на том же хосте `request.ip` не должен быть loopback. Добавить стартовую проверку или тест и рассмотреть лимит 1-2 МиБ (реальные payload GitHub укладываются).
- **L-2.** `completion.repository.ts:261-273`: `completed_at <= now()` внедряет тестовые часы (`Clock`) в боевой SQL и смешивает часы БД и приложения. Убрать, а в тестах создавать завершения в прошлом.
- **L-3.** `completion.repository.ts:125-144`: `insertReleaseCheck` делает SELECT и затем INSERT без блокировки, и две параллельные проверки могут получить один `checkedAt`. На проверку C-53 это не влияет, но сдвиг на +1 мс — костыль под неподвижные часы; лучше использовать `uuidv7`-порядок или вторичный ключ по `id`.
- **L-4.** `setup-redirect.ts:25`: `REQUIRED_PERMISSIONS` требует `actions`, а FR-GH-01 перечисляет Metadata, Issues, Pull requests. Если права Actions нужны для `ci_workflow`, зафиксировать это в спеке или FR-GH-01, иначе установки по документации будут отклонены с `permissions_missing`.
- **L-5.** Вебхуки `issues` `transferred` и `deleted` не обрабатываются (`event-routing.ts`): уже засчитанный вклад остаётся. Для `deleted` стоит вызывать `contribution_revoked`.
- **L-6.** `relabelContribution` (OpenAPI) не имеет `version` и не возвращает 409 при устаревшей версии. Сейчас это идемпотентный last-write-wins по одной колонке, что приемлемо, но расходится с правилом «редактируемые сущности несут version»; если роль не меняется конкурентно с другим действием, оставить и записать исключение в ADR.

### Проверка миграции 0017

- Идемпотентность: файл сам не повторяем (`ADD COLUMN`, `CREATE FUNCTION`, `CREATE TRIGGER` без `IF NOT EXISTS` / `OR REPLACE`), но это тот же стиль, что у 0015 и 0016, а повторный запуск исключает журнал drizzle; все ожидающие миграции идут одной транзакцией мигратора, неполного применения не остаётся. Требовать `IF NOT EXISTS` не нужно.

### Порядок блокировок (deadlock)

`ContributionConsumer.credit` (`contribution.consumer.ts:76`) берёт `lockTeam(share)`, уровень 4. До него в транзакции вебхука или сверки взяты только строка `webhook_delivery` и строка `gh_item` (не входят в глобальный порядок) и нет ни одного блокирующего вызова уровня выше 4 (`lockRepoLink` в `github/internal` нет ни на пути `item-events`, ни на пути сверки). После #4 `credit` ничего не блокирует. `requestCompletionCheck` (`completion-check.service.ts:95`) поднимает режим с `share` до `update` на том же уровне 4 и до блокировок других уровней, апгрейда `share` -> `update` внутри одной транзакции нет. Цикл `gh_item` -> команда против команда -> `gh_item` невозможен: завершение и проверка `gh_item` только читают (MVCC, без ожидания). `LockService` в `NODE_ENV=test` бросает исключение при нарушении порядка, тесты гонок проходят. Вывод: совпадает с порядком из `architecture.md` 12.1, риска deadlock нет. Риск `LOCK_TIMEOUT` (5 с) возможен только если держатель #4 долго занят (завершение с вызовом GitHub под блокировкой), в тестах не проявился.

### Окно 30 минут и лимит

Окно равно `CHECK_GIVE_UP_AFTER_MS`, которым `completion-check-sweep.ts` помечает проверку брошенной, поэтому проверка, которую свип уже закрыл, не блокирует новую. Самая длинная живая проверка около 15 с + 11 мин + 11 мин, то есть меньше 30 мин: окно разумно. Лимит 30/ч как «защита от щелчков» работает, но см. R-5.

### Новые находки

**HIGH**

- **R-1.** `apps/api/drizzle/0017_release_key_resume_cursor_team_index.sql:30-42`: ключ не канонизирует хост так, как это делает WHATWG `URL` (его же используют `isStorableLink` и link-checker, а `team.release_url` хранит исходную строку пользователя без канонизации, `item.service.ts:124`). Прогон функции: `https://foo%2eapp/x`, `https://fo%6f.app/`, `https://ｆｏｏ.app/` (полноширинные), `https://foo。app/` (идеографическая точка), `https://пример.рф/` против punycode дают ключи, отличные от `foo.app`; `new URL` сводит все эти записи к одному хосту. Начальный пробел даёт `NULL` (блок отключён), хотя `new URL` его обрезает. Итог: тот же обход AF-02, что и `www.` в H-2, остаётся. Исправление: в `TeamsFacade.setReleaseUrl` (или в `item.service`) сохранять `new URL(raw).href` (WHATWG уже делает punycode, нижний регистр, декодирование хоста, `.`/`..`, удаление табуляций, `\` -> `/`), а SQL-функцию оставить для `www.`, `index.html`, слеша и регистра пути; добавить `btrim` в функцию. Тесты на каждый из перечисленных вариантов.

**MEDIUM**

- **R-2.** `apps/api/src/modules/workspace/internal/services/completion.service.ts:163` (`releaseAddressHeld`) + `teams-facade.service.ts:listCompletedTeamsByReleaseKey`: две разные команды с одним ключом, завершаемые параллельно, берут блокировки разных строк `team`; каждая не видит незакоммиченное завершение другой, обе проходят. Это гонка CC-13 и AF-02, о ней говорил H-2 («даже гонка двух завершений»), частичный уникальный индекс не добавлен. Исправление: перед проверкой `pg_advisory_xact_lock(hashtextextended(release_key, 0))` (допустим архитектурой, 12.1, transaction-scoped; взять после #4 и учесть в таблице порядка) либо уникальный частичный индекс `(release_key) WHERE status = 'completed'` с отображением 23505 в `COMPLETION_BLOCKED/FRAUD_BLOCK` после проверки, что в данных нет дублей. Тест гонки: две команды, один адрес, 20 вызовов, ровно одно завершение.
- **R-3.** `0017...sql:33`: query и fragment отбрасываются целиком. Для адресов, где объект задаёт query (`play.google.com/store/apps/details?id=a` и `?id=b` дают один ключ `play.google.com/store/apps/details`), вторая команда с другим приложением получит ложный `FRAUD_BLOCK`. То же поведение было и в `releaseAddressKey`, но теперь оно закреплено в БД. Уточнить у продукта AF-02: для хостов с query-идентификатором оставлять query в ключе либо давать сигнал (флаг), а не блок.
- **R-5.** `rate-limiter.ts:28` и `completion-check.service.ts:93`: лимит 30/ч вдвое-втрое мягче SEC-27 (10/ч) и предложения аудита (5/ч); `enforce` идёт до проверки на активную проверку, поэтому отклонённый запрос (409) тоже тратит квоту; задания `ccl`/`ccr` по-прежнему не считаются в `linkCheckTeam` (30/ч), так что команда может поставить до 30 x N заданий link-check в час. Исправление: 10/ч, считать задания ссылок в `linkCheckTeam` либо переиспользовать успешные результаты ссылок за сутки (идея из бэклога). Второй запрос лучше отдавать как 202 с id уже идущей проверки (идемпотентно для двойного клика), а не 409 без пояснения для веба.

**LOW**

- **R-4.** `item.repository.ts:62-71`: при равных времени и шаге `supersedes(a, b)` и `supersedes(b, a)` одновременно истинны, когда наборы меток или исполнителей различаются. Итог зависит от порядка доставки (последний победил), возможен повторный перезапис при каждой сверке, если листинг и хранимая строка стабильно расходятся. Для состояния порядок строгий (`itemRank`), поэтому вклад не теряется; страдают только метки и исполнители внутри одной секунды. Исправление: при равном шаге сравнивать метки и исполнителей только в сверке (листинг GitHub есть истина), а для вебхука применять лишь строго новее; либо добавить детерминированный третий ключ (хэш отсортированного набора).
- **R-6.** `contribution.consumer.ts:104-115` (`takeBack`): отзыв вклада идёт без блокировки команды и без проверки статуса, после завершения он меняет `active` у строки, которая уже есть в снимке. Решить сознательно (записать в ADR) либо брать `lockTeam(share)` и не трогать завершённые.
- **R-7.** Документация не обновлена: в `docs/architecture.md` нет `team.release_key` и триггера, `*_resume_page` / `pending_sync_started_at` и `GITHUB_SYNC_MAX_PAGES` (7.4), строки про блокировку #4 при кредите вебхука (12.3, рядом со строкой «Смена роли вклада против завершения») и категории `completionCheckTeam` (13.6).
- **R-8.** `0017...sql:12`: функция помечена `STABLE`, хотя чиста; `IMMUTABLE` позволит при необходимости строить по ней индекс выражения.
- **R-9.** `repo-sync.service.ts:103-116`: параллельный прогон `syncRepository` (суточная сверка и `github-sync-resume`) не исключён явно, оба могут читать одно состояние и писать курсор. Вреда нет (запись идемпотентна), но проверить `jobId` или взять advisory-блокировку на `repository_id`.
