# S6-01. Прототип состояния установки GitHub App

Дата: 2026-10-18. Двойник и тест: `apps/api/src/modules/github/spike/**` (временно, удаляется в S6-03). Реального App нет, поведение GitHub взято из документации docs.github.com и сообщений сообщества; всё, что не подтверждено документацией, вынесено в раздел "Ручная проверка".

## Что подтверждено документацией

- Адрес установки `https://github.com/apps/<slug>/installations/new?state=<значение>` принимает `state`; назначение по документации ("Sharing your GitHub App"): вернуть человека в исходное состояние после установки, аутентификации или принятия обновлений, сопоставить установку с пользователем или аккаунтом.
- Setup URL получает `installation_id`; документация предупреждает, что его можно подделать, и требует получить user-to-server токен установившего пользователя и проверить, что установка ему принадлежит.
- `GET /user/installations` (токен пользователя App) возвращает установки, к которым у пользователя есть доступ; поля `id`, `account`, `permissions`, `suspended_at`, `repository_selection`; пагинация `per_page` до 100.
- Установку в организацию выполняет владелец; участник без прав выбирает организацию, GitHub уведомляет владельца ("Request").
- Callback URL (пользовательская авторизация) и Setup URL - разные настройки.

## Что документация не говорит прямо

- Возвращается ли `state` на Callback URL, когда включено "Request user authorization (OAuth) during installation" (документация описывает `state` только для Setup URL и обычного OAuth). Сторонние интеграции и сообщество сообщают: `setup_action`, `installation_id`, `code` и `state` приходят вместе; при `setup_action=request` (установка требует одобрения владельца организации) `installation_id` нет, а при последующем одобрении владельцем `state` отсутствует (другая сессия).
- Точные значения `setup_action` в современной документации (используются `install`, `update`, `request`).

## Выбранный поток

Поток из architecture 7.2 подтверждается как основной; запасной вариант встроен в тот же обработчик, а не отдельным маршрутом.

1. `createInstallationSession`: `state` = 32 байта `randomBytes`, base64url, Redis `gh_state:<state>` = `{teamId, userId}`, TTL 600 с (в БД только SHA-256 по architecture 15, в Redis допустимо хранить хэш).
2. Возврат на Callback URL №1: `installation_id`, `setup_action`, `code`, `state`.
3. Порядок проверок в `githubSetupCallback` (проверен тестами двойника):
   1. нет `installation_id` (в т.ч. `setup_action=request`) -> экран "ожидает одобрения владельца", grant не создаётся;
   2. нет `code` -> отказ (это же случай одобрения владельцем: приходит без `state` и `code`);
   3. `state` с `:` отклоняется до Redis; `GETDEL` (одноразово, атомарно), просроченный или повторный -> `STATE_INVALID`;
   4. `userId` в `state` равен пользователю сессии, иначе `STATE_USER_MISMATCH`; `state` при этом сгорает, владельцу нужно начать заново (осознанно: проще и безопаснее, чем возвращать значение);
   5. пользователь всё ещё тимлид `teamId` (`assertLead`);
   6. `code` обменивается на токен пользователя (одноразовый), `GET /user/installations` должен содержать `installation_id` (иначе `INSTALLATION_NOT_OWNED`; подделка id отбита);
   7. у установки есть все права Metadata, Issues, Pull requests, Actions (read), иначе `PERMISSIONS_MISSING`;
   8. upsert `gh_installation`, `INSERT installation_grant (installation_id, team_id, user_id) ... ON CONFLICT DO NOTHING`; токен пользователя отбрасывается.
4. Запасной вариант, если GitHub не вернул `state`: проверки 6-7 выполняются так же (владелец доказан токеном), grant создаётся с `team_id = NULL`-эквивалентом "установка пользователя", а команда выбирается в `PUT /v1/teams/{teamId}/repository` (assertLead + доступ установки к репозиторию). Тест двойника с `dropState` это подтверждает; чужая установка отклоняется и в запасном варианте.

## Результаты тестов двойника (17, `install-state-flow.test.ts`)

`state` одноразовый; чужой пользователь отклонён (и `state` сгорает); просроченный (>600 с) отклонён; `state` с `:` отклонён без обращения к хранилищу; смена тимлида между шагами -> `NOT_LEAD`; один и тот же возврат x10 параллельно -> 1 успех, 1 grant; подделанный `installation_id` -> `INSTALLATION_NOT_OWNED`; нет `code` -> отказ; организация, участник без прав (`setup_action=request`) -> ожидание, grant нет; одобрение владельцем приходит без `state` и `code` -> grant не создаётся; повторная установка тем же аккаунтом -> `setup_action=update`, тот же `installation_id`, новый тимлид получает свой grant; отзыв -> `installation.deleted`, grants отозваны, новая установка получает новый id; отсутствие права Actions -> `PERMISSIONS_MISSING`; `code` одноразовый; запасной вариант без `state`.

## Ограничения

- Двойник упрощает доступ в `GET /user/installations` до владения аккаунтом; на реальном GitHub доступ шире (участники организации, коллабораторы), поэтому проверка `assertLead` + выбор репозитория остаются обязательными.
- Права на стороне пользователя: `GET /user/installations` показывает установки, доступные пользователю, а не обязательно установленные им; значит, "владелец установки" в нашей модели означает "имеет доступ к установке", а не "создал её". Это совпадает с SEC-02 (grant даёт право привязывать репозитории, но выбор репозитория проверяется токеном установки).
- Подтверждение обновлённых прав (если Actions не было в первой установке) требует действия владельца; `PERMISSIONS_MISSING` должен давать экран с инструкцией.
- Одобрение установки владельцем организации не связано с сессией запросившего: команда привязывается только повторным прохождением потока (`setup_action=update` с `code`), а не автоматически.

## Требует ручной проверки на реальном App

1. Приходит ли `state` на Callback URL №1 при включённом "Request user authorization (OAuth) during installation" для: новой установки, `update` на существующей, установки в организацию владельцем.
2. Значения и набор параметров при `setup_action=request` и при последующем одобрении (приходит ли что-то на Callback URL запросившего).
3. Какой `redirect_uri` берётся, если Callback URL несколько (должен быть первым в списке).
4. Содержит ли `GET /user/installations` установку организации для владельца, не являющегося её создателем, и для обычного члена организации.
5. Что видит пользователь, у которого App уже установлен, при повторном открытии `installations/new`.
6. Поведение при приостановке (`suspended_at`) и при отзыве токена пользователя; событие `github_app_authorization`.
7. Что `code` одноразовый и живёт 10 минут; что при отзыве установки `GET /app/installations/{id}` отвечает 404.

## Решение для S6-03

- Реализовать обработчик по порядку проверок выше; `state` обязателен для привязки к команде, его отсутствие переводит в запасной вариант (grant без команды, команда выбирается в `linkRepository`), без отдельного кода: ветка уже в двойнике.
- Хранить в Redis значение по `sha256(state)`; `GETDEL` одной командой; ключ в пространстве `gh_state:` без `:` в `state` (backlog LOW про общее пространство закрывается проверкой).
- В журналах и Caddy `state`, `code` не писать (architecture 17/SEC-07).
- Двойник S6-02 (`apps/api/test/fakes/**`) должен уметь: `setup_action` `install`/`update`/`request`, отсутствие `state`, одноразовый `code`, `GET /user/installations`, `installation.deleted`. Спайк-двойник можно взять за основу и затем удалить `spike/**`.
- Пункт 1 раздела "Ручная проверка" - единственный, от которого зависит выбор основного потока; до проверки код S6-03 работает при обоих исходах.
