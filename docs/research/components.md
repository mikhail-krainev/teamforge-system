### 1.2 Выбор: Better Auth (взять, тонкая интеграция)

Решение: **взять Better Auth как есть**, писать только адаптер подключения и Nest-гард.

Почему:
- единственный кандидат, который закрывает все требования одной библиотекой на TypeScript: GitHub OAuth, magic link, Drizzle, Redis для сессий, активная разработка, MIT;
- не требует отдельного сервиса (важно: один VPS);
- хранит пользователей в нашей PostgreSQL через Drizzle (персональные данные остаются в РФ, 152-ФЗ).

Схема интеграции:
- экземпляр `betterAuth()` создаётся в `apps/api` (модуль `auth`), монтируется на Fastify как catch-all `GET/POST /api/auth/*` по официальному гайду (не через сообщественный Nest-пакет, т.к. его поддержка Fastify "beta"; можно взять пакет позже при зрелости). Для Nest-контроллеров отключить стандартный body parser только на этом маршруте, либо регистрировать маршрут на уровне Fastify до Nest (проверить на прототипе);
- гард Nest вызывает `auth.api.getSession({ headers })`;
- Next.js (apps/web) читает сессию, запрашивая `GET /api/auth/get-session` у API с пробросом cookie, либо через клиент `better-auth/react`. Один домен (`app.example.ru` + `/api` через reverse proxy) избавляет от проблем с cross-site cookie;
- `trustedOrigins` и CORS (`@fastify/cors`, `credentials: true`) только на наши домены;
- сессии: `secondaryStorage` на Redis. Нужно проверить на прототипе, пишутся ли сессии одновременно в Postgres (опция `storeSessionInDatabase`) и что при очистке Redis пользователь просто перелогинивается [не проверено];
- миграции схемы только через `drizzle-kit` (по документации `getMigrations` не работает с Drizzle).

Риски: версия 1.x выходит часто (риск breaking changes, фиксировать версию и читать changelog); peer-зависимость на конкретный диапазон `drizzle-orm`; Fastify-интеграция описана, но не "родная" для Nest.

### 1.3 Email: рекомендация

**Magic link** (основной запасной способ), пароль не вводить.
- нет хранения паролей (меньше ответственность по 152-ФЗ и поверхности атак, нет сброса пароля, нет утечки хэшей);
- аудитория студенты, забывают пароли; GitHub основной, email редкий сценарий;
- по умолчанию в Better Auth срок ссылки 300 с и лимит 5 запросов за 60 с на эндпоинтах входа; предложение: срок 15 минут, одноразовая ссылка, лимит 5 писем в час на адрес и 20 на IP;
- нужен надёжный SMTP с хорошей доставляемостью на mail.ru/yandex.ru (российский провайдер рассылок, SPF/DKIM/DMARC) [не проверено какой именно]. Это операционный риск: если письма не доходят, запасной вход не работает;
- если окажется, что письма недоставляемы, запасной план: пароль через Better Auth emailAndPassword (argon2id; `@node-rs/argon2` 2.2.2 / 2026-10-06, MIT). Включать только по необходимости.

### 1.4 Что решить отдельно (вне библиотеки)
- 152-ФЗ: GitHub OAuth означает передачу данных (id, логин, email) через серверы GitHub за пределами РФ; пользователь делает это сам при входе, но в политике обработки ПДн и согласии это нужно отразить; юридическая проверка нужна [не проверено, требуется юрист]. Хранение профилей и резюме в БД на территории РФ, как заложено.
- Account linking: один GitHub id = одна учётная запись (раздел 5). Привязка email к GitHub-аккаунту только после подтверждения письмом.

### 2.2 Выбор
- PDF: **unpdf** (взять). DOCX: **mammoth `extractRawText`** (взять), HTML-вывод не использовать вообще. Форматы .doc, .rtf, .odt не поддерживаем (сообщение пользователю).
- Никакого ML и OCR. Если из PDF не извлеклось текста (скан), показываем пустую форму для ручного ввода.
- Результат извлечения это подсказка: пользователь вручную подтверждает каждое поле (по ТЗ). Извлечённый текст рендерится только как plain text (экранирование), в БД не хранить как HTML.

### 2.3 Безопасность (недоверенные файлы)
Из документации mammoth: нет санитизации, высокая нагрузка CPU/памяти на некоторых документах, рекомендация изолировать вызов в отдельном потоке с таймаутом, `externalFileAccess` оставить выключенным. Из CVE-2024-4367: движок PDF.js уже имел RCE-класс уязвимость.

Контур обработки (предложение):
1. Загрузка в S3/MinIO в приватный бакет под случайным ключом. Лимит 5 МБ, проверка magic bytes (`%PDF-`, `PK\x03\x04`) и расширения; MIME из заголовка запроса не доверять.
2. Парсинг только в отдельной очереди BullMQ в отдельном контейнере `resume-worker`: без доступа к БД и Redis-секретам кроме очереди, без исходящей сети, read-only файловая система, непривилегированный пользователь, лимиты памяти/CPU контейнера. Внутри `worker_threads` с `resourceLimits` (например 256 МБ) и жёсткий таймаут 15 с; по таймауту поток и задача убиваются.
3. Лимиты: PDF не более 30 страниц; для DOCX проверить суммарный распакованный размер (не более ~50 МБ) и число записей архива до передачи в mammoth (защита от zip-бомбы), так как mammoth сам об этом не говорит.
4. Отключить выполнение скриптов: для pdf.js `isEvalSupported:false`, без JavaScript-движка форм [не проверено что в unpdf-сборке eval уже вырезан].
5. Вывод ограничить по длине (например 100 тыс. символов), вычистить управляющие символы, сохранить только текст.
6. Антивирус (ClamAV в отдельном контейнере) рекомендуется, но не обязателен для MVP (+~1 ГБ RAM). Оставить как возможное усиление.
7. Исходный файл хранить только если пользователь захотел (ПДн): по умолчанию удалять после подтверждения полей.

## 3. Интеграция с GitHub

### 3.1 GitHub App против OAuth App
Рекомендация: **GitHub App** (по документации GitHub рекомендован в большинстве случаев).

| Критерий | GitHub App | OAuth App |
|---|---|---|
| Права | Гранулярные (Issues: read, Pull requests: read ...) | Широкие scope вроде `repo` (доступ к коду на запись) |
| Токены | Токен установки живёт ~1 час; пользовательские токены можно сделать истекающими (8 ч + refresh) | Долгоживущие по умолчанию |
| Лимиты API | Масштабируются: 5000/ч база, +50 за репозиторий свыше 20, +50 за пользователя свыше 20 (орг.), максимум 12 500/ч | Общий лимит пользователя 5000/ч |
| Вебхуки | Один встроенный вебхук на все репозитории установки | Настраивать на каждый репозиторий/организацию |
| Установка | Владелец репозитория/организации устанавливает App на выбранные репозитории | Пользователь даёт доступ ко всему по scope |

Схема: тимлид в Teamforge нажимает "Подключить репозиторий" и устанавливает GitHub App на нужный репозиторий (только выбранный). Участники привязывают свои GitHub-учётки через вход (OAuth-поток самого App, user-to-server токен нужен лишь для идентификации, вклад читаем токеном установки). Вход (раздел 1) можно сделать через тот же App либо отдельное OAuth-приложение; чтобы не усложнять, на прототипе проверить совместимость GitHub provider в Better Auth с GitHub App (получение email требует account-permission "Email addresses") [не проверено]. Запасной вариант: отдельное OAuth App только для входа.

### 3.2 Минимальные права App
- Repository: **Metadata: read** (обязателен), **Issues: read**, **Pull requests: read**.
- Organization: **Projects: read** (только если включаем Projects v2, см. ниже).
- Account (user): **Email addresses: read** (если App используется и для входа).
- Contents, Actions, Administration, запись куда-либо: **не запрашивать**. Все действия только чтение. Проверка репозитория в 6.2 (число коммитов и их авторы) требует чтения списка коммитов; репозиторий для зачёта должен быть публичным, поэтому данные доступны без права Contents [не проверено, проверить на прототипе]. Если токен установки без Contents получит отказ, добавить **Contents: read** (только чтение) либо считать коммиты по событиям `push`/`pull_request`.
- Подписка на события: `issues`, `pull_request`, `installation`, `installation_repositories`; опционально `issue_comment`, `pull_request_review` (если вклад считаем шире; по ТЗ достаточно закрытых задач и слитых PR).

### 3.3 Projects v2 и вебхуки (важное ограничение)
По документации вебхуков: события `projects_v2` и `projects_v2_item` требуют организационного разрешения Projects и в таблице доступности указаны **только для организационных вебхуков, App не указан**; кроме того события в public preview и могут меняться. Следовательно:
- доставка `projects_v2_item` в наше приложение через GitHub App **не гарантирована** (вывод по документации; перепроверить на прототипе);
- проекты Projects v2, принадлежащие личному аккаунту, у App по сообщениям сообщества недоступны, а для приватных организационных могут возвращать пустой результат из-за того, что бот не входит в коллабораторы (источник: обсуждения сообщества и статьи, не официальная документация) [не проверено].
Решение: **не строить вклад на Projects v2.** Единицей задачи считать Issue (закрыт = задача выполнена; исполнитель = assignee, иначе автор закрывающего PR), единицей вклада слитый PR (`merged=true`, автор). Projects v2 как необязательное улучшение: периодический опрос GraphQL раз в 15 минут только для организационных досок, только чтение колонки статуса. В MVP не делать. Каждому тимлиду в пользовательской инструкции написать: "Ведите задачи как Issues; доска Projects это дополнительно".

### 3.4 Лимиты (источник: документация GitHub)
- REST/GraphQL основной лимит установки: 5000 запросов/ч (база), до 12 500; GitHub Enterprise Cloud организация: 15 000 (REST).
- GraphQL: счёт в баллах (5000/ч для пользователя; установка по тем же правилам, GHEC 10 000), каждому соединению нужен `first/last` 1-100, не более 500 000 узлов в запросе.
- Вторичные: не более 100 одновременных запросов (общих для REST и GraphQL), 900 баллов/мин на REST-эндпоинт, 2000 баллов/мин на GraphQL, 90 с CPU на 60 с времени, создание контента ~80/мин и 500/ч. Для нас важны только чтения: GET = 1 балл.
- Бюджет (расчёт): 100 команд * 1 репозиторий. Вебхуки не расходуют лимит. Сверка (reconcile) раз в сутки по открытым/закрытым issues и PR на репозиторий: ~5-10 запросов = ~1000 запросов в сутки, много ниже лимита. Лимиты считаются на установку (на репозиторий/организацию), а не на весь сервис.
- Условные запросы (ETag, `If-None-Match`): ответ 304 не списывает основной лимит, если запрос авторизован (документация GitHub, best practices, проверено).

### 3.5 Вебхуки: обработка
- Проверять `X-Hub-Signature-256` (HMAC SHA-256 тела с секретом; заголовок присылается только если задан секрет). Использовать `@octokit/webhooks` (v14.2.0, MIT) либо `crypto.timingSafeEqual` на сыром теле (в Fastify нужен raw body).
- Идемпотентность по `X-GitHub-Delivery`: хранить id в Redis (TTL 7 дней) или в таблице, повтор игнорировать.
- Отвечать 2xx сразу, тело кладётся в очередь BullMQ, обработка асинхронно.
- Автоматического повтора неудачных доставок нет [не проверено]; поэтому суточная сверка опросом обязательна (догоняет пропущенные события).
- Привязка события к команде по `repository.id` (а не по имени: имя можно менять), автор по `user.id` (число), а не по логину.

### 3.6 Хранение токенов и ключей
- Токены установки (1 час) не хранить в БД: генерировать по требованию, кэшировать в Redis до 55 минут.
- Приватный ключ App (PEM), секрет вебхука и client secret: только переменные окружения / секреты Docker, не в репозитории и не в БД.
- Пользовательские токены (access/refresh): по решению фазы 0 хранятся только зашифрованными. В Better Auth есть опция `account.encryptOAuthTokens` (по умолчанию `false`, проверено по справочнику опций): включить её обязательно, ключ из секрета окружения. Если токен не нужен для работы, не сохранять вовсе.

## 4. Косметические награды

Принципы: нет рейтингов, лидербордов и сравнений между людьми; значок виден в профиле как бинарный факт с датой и проектом; уровни внутри значка (бронза/серебро/золото) это порог, а не место. Засчитываются только зачтённые проекты (раздел 6). Выдача только после "охлаждения" 7 дней после завершения проекта (раздел 5), при срабатывании антифрода значок отзывается.

| # | Название | Условие выдачи |
|---|---|---|
| 1 | Первый релиз | Первый зачтённый проект |
| 2 | Трое в строю | 3 зачтённых проекта |
| 3 | Пятёрка проектов | 5 зачтённых проектов |
| 4 | Десять из десяти | 10 зачтённых проектов (максимум по числу проектов, дальше значков нет) |
| 5 | Многоликий | Зачтённые проекты минимум в 3 разных ролях |
| 6 | Универсал | Зачтённые проекты минимум в 5 разных ролях |
| 7 | Разные берега | Зачтённые проекты минимум в 2 разных типах продукта (веб, мобильное, бот, игра, данные/ML, инструмент CLI и т.д. по справочнику) |
| 8 | Коллекционер форматов | Зачтённые проекты минимум в 4 типах продукта |
| 9 | В срок | Проект завершён без просрочки: дата завершения не позже даты старта плюс сумма плановых сроков этапов маршрута (та же просрочка проекта, которую платформа показывает участникам при завершении; сроки этапов из methodologies.md, поправок и льгот нет) (предложение: просрочка считается на весь проект, а не по каждому этапу; ТЗ это не уточняет); выдаётся каждому зачтённому участнику |
| 10 | Серия без просрочек | 3 зачтённых проекта подряд без просрочек |
| 11 | Закрыл дефицит | Зачтённый проект, где участник был в роли, помеченной дефицитной на момент вступления в команду |
| 12 | Командный бонус "Закрытая вакансия" | Выдаётся всей команде (зачтённым участникам), если к завершению проекта желательная роль занята зачтённым участником и эта роль была дефицитной на момент его вступления на неё (способ вступления, через очередь подбора или по приглашению, не важен). За желательные роли без дефицита бонуса нет |

Примечания: "дефицитная роль" это роль, на которую открытых мест во всех командах больше, чем кандидатов в очереди поиска на эту роль (правило из ТЗ). Расчёт выполняется в момент вступления участника на роль (витрина спроса может кэшироваться, но не дольше нескольких минут; не суточный снимок), считается до самого вступления (занимаемое место и вступающий кандидат входят в подсчёт) и сохраняется в записи участия до конца проекта без пересчёта, чтобы награду нельзя было получить задним числом. Пометка "желательная" проверяется на момент завершения проекта (по ТЗ); история её изменений пишется в журнал, а пометка, выставленная в последние 7 дней перед завершением, считается сигналом (+1) в разделе 5. Платформа ведёт счётчик зачтённых проектов отдельно по каждой роли и общий (по ТЗ). Справочник ролей и типов продукта добавляется только администратором. В MVP два типа продукта (веб-сервис, ML), поэтому из значков 7-8 достижим только значок 7; значок 8 (4 типа) включается со второй версии. Значки 2-4 и 5-6 и 7-8 это уровни одной серии, показывать как один значок с уровнем.

## 5. Защита от фиктивных завершений

Цель: сделать накрутку дорогой и заметной, не наказывая добросовестных. Каждое правило имеет действие: **блок** (завершение невозможно), **флаг** (в очередь ручной проверки администратору, награды замораживаются) или **сигнал** (учитывается в сумме баллов подозрительности; при сумме >= 3 флаг).

### 5.1 Фиктивные проекты
1. (блок) Репозиторий уникален: один репозиторий (по `repository.id`) может быть привязан к зачтённому проекту только один раз. Нельзя привязать форк чужого репозитория без собственных коммитов; репозиторий, созданный до старта проекта в Teamforge более чем на 30 дней, флаг (так как проект мог быть сделан до платформы).
2. (блок) Ссылка на релиз уникальна среди всех зачтённых проектов и отвечает на проверки (раздел 6.5). Ссылка не из чёрного списка шаблонов (example.com, localhost, платформа-заглушки типа "coming soon" определяются по заголовку страницы, флаг).
3. (блок) Вклад: минимум 10 слитых PR или закрытых задач в сумме по проекту, и не менее 2 разных GitHub-аккаунтов участников, имеющих вклад.
4. (флаг) Размер: суммарное число изменённых строк в слитых PR менее 200 или единственный PR содержит более 80% всех изменений.
5. (флаг) Содержание артефактов: одинаковые хэши (SHA-256) файлов артефактов с другим проектом; пустые файлы.
6. (флаг) Темп: более 70% событий вклада приходится на последние 48 часов проекта (штурм перед закрытием).
7. (сигнал) Название и описание проекта совпадают (нормализованно) с уже зачтённым проектом той же команды.
7а. (сигнал) Пометка роли "желательная" выставлена менее чем за 7 дней до завершения проекта (защита от пометки роли задним числом ради командного бонуса, раздел 4): +1.
8. Время событий брать из серверных меток получения вебхуков (`received_at`) и событий платформы, а не из дат коммитов (дату коммита автор меняет).

### 5.2 Проекты за один день (короткие)
1. (блок) Минимальная длительность 14 дней от старта (раздел 6) и минимум 3 разных календарных дня с событиями вклада.
2. (блок) Этап нельзя закрыть быстрее минимального времени этапа (предложение: 24 ч от открытия этапа); этапы закрываются только последовательно.
3. (флаг) Завершение в течение 24 ч после создания команды вообще, либо все этапы закрыты за менее чем 20% плановой длительности.
4. (сигнал) Команда сформирована и сразу пройдены этапы пачкой (3 и более этапов закрыты в течение 1 часа).

### 5.3 Мультиаккаунты
1. (блок) Один GitHub id = одна учётная запись Teamforge. Один подтверждённый email = одна запись. Нормализация почты: приведение к нижнему регистру, для gmail удаление точек и части после `+`; блок списка одноразовых доменов (`disposable-email-domains` или аналог [не проверено]).
2. (блок зачёта, не регистрации) Возраст GitHub-аккаунта не менее 30 дней, и в аккаунте есть хотя бы 1 публичный репозиторий или активность. Регистрация и участие в проектах допускаются всегда, но зачёт проекта и награды откладываются до выполнения порога. Порог мягкий для студентов-новичков: никого не блокируем, просто зачёт наступает, когда условие выполнено.
3. (сигнал) Общий IP или тот же отпечаток устройства/браузера (hash от User-Agent + IP-подсети /24 + cookie id) у двух участников одной команды: +1. Три и более участников: +2. Ограничение: общежития и университетские сети дают ложные срабатывания, поэтому только сигнал, не блок. Хранить хэши, а не сырой IP дольше 90 дней; указать в политике ПДн (152-ФЗ) [не проверено, требуется юрист].
4. (сигнал) Идентичные или почти идентичные тексты профиля/резюме (нормализованный текст, одинаковый хэш) у разных учёток: +2.
5. (сигнал) Узкий круг: одни и те же 3 и более человек завершили 2 и более проектов вместе, при этом других участников не было: +1; 3 и более проектов: флаг. Награды засчитываются, но число проектов с одним и тем же составом считать как 1 для значков "число проектов".
6. (сигнал) Аккаунты регистрируются и вступают в команду в течение 10 минут друг после друга: +1.
7. (сигнал) Вклад одного участника (по GitHub id) в команде составляет 100% при остальных участниках без единого события: +2, т.е. остальные не получают зачёт (и так не пройдут условие "есть вклад").
8. (блок) Нельзя быть в одной команде двумя ролями как две разные учётки: связь аккаунтов (признаки выше при сумме >= 3) переводит в флаг.

### 5.4 Общие меры
- Охлаждение: награды и зачёт участникам применяются через 7 дней после завершения проекта; в течение этого времени проект можно оспорить (жалоба участника, действие администратора).
- Лимит 1 зачтённый проект на человека в 14 дней при подозрении (сумма сигналов >= 2), без подозрений ограничения нет.
- Очередь ручной проверки с чек-листом и журналом решений (аудит). Отзыв значков возможен задним числом, решение фиксируется.
- Вклад считать по GitHub id, не по логину (логин можно переименовать и передать).

### 6.1 Голосование за нового тимлида (предложения)
- Запуск: тимлид вышел или удалил аккаунт (или не проявлял активность 14 дней и команда подала запрос).
- Кто голосует и за кого: все действующие участники, у которых закончился испытательный срок (1 человек = 1 голос). Кандидат: любой такой участник (самовыдвижение или выдвижение другим с согласием), нужно согласие кандидата. Голосовать за себя можно. Если таких участников нет (все остались на испытательном сроке, например команда целиком набрана автоподбором), право голоса и выдвижения получают все действующие участники; если остался один участник, он становится тимлидом автоматически без голосования.
- Срок: **72 часа** с открытия. Досрочно закрывается, как только один кандидат набрал более половины голосов от всех имеющих право (а не от проголосовавших).
- Кворум: проголосовали более половины имеющих право, то есть не менее ⌊N/2⌋+1 человек, где N число имеющих право (для команды 3 человека кворум 2, для 2 человек кворум 2, для 8 человек кворум 5). При отсутствии кворума срок продлевается один раз на 48 часов; повторно нет кворума, то ответственность переходит к участнику с наибольшим сроком в команде (по дате вступления); если тот отказался, к следующему.
- Победитель: большинство голосов проголосовавших (простое). Выбор одного из кандидатов, подтверждение кандидатом в течение 24 часов.
- Ничья: повторный тур между ничейными кандидатами, 24 часа. Если опять ничья, тимлидом становится тот, чьё участие в команде дольше (дата вступления); при равенстве случайный выбор через серверный генератор (записать в журнал).
- Нет кандидатов: в течение первых 24 часов приём самовыдвижений. Если никто не выдвинулся, предложить роль участнику с наибольшим сроком в команде, он может отказаться; если отказались все, проект получает статус "приостановлен" на 14 дней (таймеры этапов замораживаются), затем архивируется без зачёта.
- Если участников осталось меньше минимального размера (3), проект переходит в "ожидает участников", автоподбор может добавить людей (с испытательным сроком). Голосование при этом не откладывается: оно проводится с любым составом из 2 и более человек (при одном участнике он назначается тимлидом автоматически, см. выше); минимум 3 проверяется только при зачёте.
- Новый тимлид получает права на привязку репозитория; права владельца GitHub-репозитория на нашей стороне не меняются (устанавливал App старый тимлид; нужно передать установку или повторно установить App, поэтому в интерфейсе показывать уведомление) [не проверено как именно переустанавливается App при смене владельца].
- Журнал голосования хранится, итоги публичны для команды.

### 6.2 Автоматические проверки артефактов
Проверки выполняются в воркере (BullMQ) при загрузке/вводе и повторно при завершении проекта.

**Ссылки (общие правила, защита от SSRF):** только `https`; разрешение DNS и запрет адресов приватных/loopback/link-local/метаданных облака (127.0.0.0/8, 10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7); перепроверка IP после разрешения (защита от DNS rebinding); максимум 3 редиректа с повторной проверкой каждого; таймаут 10 с; максимум 1 МБ тела; собственный User-Agent; не более 1 проверки в минуту на домен.

**Репозиторий:** через GitHub API (токен установки): репозиторий существует по `repository.id`, не архивирован, не пуст (минимум 10 коммитов в сумме), коммиты минимум от 2 различных GitHub-аккаунтов участников, не форк без собственных изменений; публичный ИЛИ App установлен (для приватных доступ нужен для проверки, но для зачёта предпочтителен публичный: пользователь сам решает; предложение: для зачёта требовать публичный репозиторий либо открыть хотя бы README, иначе пользователи не смогут показать результат; **итог: требовать публичный**). Наличие README и лицензии: не блок, сигнал.

**Релиз:** URL отвечает HTTP 200 (после редиректов) при двух проверках с интервалом не менее 24 часов (чтобы нельзя было поднять страницу на минуту); HTML не пустой (минимум 500 байт тела), заголовок страницы не из типовых заглушек; для мобильных/CLI/бот-продуктов релиз это ссылка на страницу релиза GitHub (Releases) с прикреплённой сборкой или ссылка на магазин/бота; тип определяется полем типа продукта, проверка зависит от типа. Тот же домен/URL не повторяется в других зачтённых проектах.

**Файлы (артефакты):** размер не более 10 МБ на файл, не более 50 МБ на проект, не более 30 файлов; разрешены pdf, png, jpg, webp, md, txt, docx, pptx, zip не более 10 МБ [zip с проверкой на zip-бомбу]; запрещены исполняемые (exe, msi, sh, bat, js как отдельный файл, apk можно в разделе релиза через GitHub, а не загрузкой); определение типа по magic bytes, не по расширению и MIME клиента; имя файла нормализуется, хранится под случайным ключом, раздаётся с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`; SHA-256 фиксируется (для дедупликации, 5.1.5); антивирус ClamAV по желанию. Минимальный размер артефакта 1 КБ (против пустых). Обязательные артефакты определяются плейбуком этапа (в справочнике этапов).
