## Принятые решения

- Пользователь разрешил полностью автономную работу: оркестратор сам коммитит, открывает и сливает запросы, переходит между фазами и срезами подряд в одной сессии без подтверждений (2026-10-14). Проверку делают независимые агенты-ревьюеры.
- Авторизация: Better Auth, email через magic link, токены GitHub шифруются (`encryptOAuthTokens`).
- Разбор резюме: unpdf + mammoth в изолированном воркере.
- GitHub: GitHub App; вклад по Issues и PR, Projects v2 не основа (вебхуки только для организаций).
- Базовая длительность проекта 12 недель, минимум для зачёта 14 календарных дней.
- Команда для зачёта 3-8 человек, доля этапов 60%, лимит 2 активных проекта, испытательный срок 7 дней, голосование 72 ч с кворумом floor(N/2)+1.
- Просрочка считается по проекту целиком: фактическая дата завершения минус плановая.
- Платформа даёт свои шаблоны (устав, мини design doc, PR/FAQ, model card).
- Хостинг релизов студентов не навязывается: список вариантов, доступных из РФ/СНГ, проверяется только ответ ссылки.
- Релиз ML: только публичный адрес (демо или API с /docs или /health, HTTP 200).
- Командный бонус получают все участники на момент завершения, кроме вышедших досрочно.
- Вход через тот же GitHub App (user-to-server OAuth), права App: Metadata, Issues, Pull requests, Actions read.
- apps/api собирается как ESM на Node 22+; транзакции через `@nestjs-cls/transactional` + Drizzle.
- Уведомления в MVP: в интерфейсе и email.
- Разбор резюме: отдельный контейнер и отдельный Redis, дочерний процесс на файл.
- Отзывы публикуются пакетом, только при отзывах от 2 и более авторов.
- Локальное S3: SeaweedFS (образы MinIO недоступны), ADR-0019.
- Redis 8 вместо 7: в 7.4 загрузка AOF теряет MULTI/EXEC при выключенном `default`, ADR-0020.
- e2e запускает автодобавление через CLI воркера `dist/cli/run-job.js` с закрытым списком задач, без HTTP.
- Исключение из команды действует на пользователя (все его заявки); исключившая команда не показывается в рекомендациях.
- Возвращение неактивного тимлида - отдельная операция `returnAsLead`; выход кандидата снимает кандидатуру.
- Роли БД: `tf_migrator` владелец схем, `tf_app` только DML.
- Лишние поля в теле запроса отклоняются 400. Токены OAuth шифруются `BETTER_AUTH_SECRET`.
- resume-worker: родитель root с cap_drop ALL + SETUID/SETGID, дочерний процесс uid 10002.
- IP клиента: первый недоверенный адрес справа в XFF; исключение loopback из лимитов только флагом, запрещённым в production.
- Исключение участника тимлидом только для автодобавленных и только в испытательный срок.

S6-08 закончена (2026-10-18): завершение проекта (backend, `modules/workspace/internal/{services,jobs,domain,repositories,authz}`). `requestCompletionCheck` (202, `lockTeam share`, тимлид, статус `active`: `voting`/`suspended` -> `TEAM_STATUS_BLOCKS_ACTION`, прочие -> `INVALID_STATE`) пишет `completion_check` (`queued`) и ставит задачу `completion-check` в очередь `auto-checks` (`jobId` `ccheck_<id>`); процессор `CompletionCheckProcessor` в `worker`: `repo_final` (`GithubApi.checkRepositoryFinal`, сбой GitHub - результат `ok:false`, `data.reason=GITHUB_UNAVAILABLE`, а не успех), `release_alive_web|ml` (ключ берётся из `auto_checks` шага `*_final_links`), `link_https:<шаг>` для каждой сохранённой ссылки (кроме релиза). Релиз и ссылки проверяет только `link-checker` через очередь `link-check` (`LinkChecks`: постановка и опрос состояния заданий до 11 минут, ответ - код); вторая проверка релиза не ранее 24 ч (C-53) после первой успешной: первая - проверка при сохранении ссылки (`ReleaseCheckRecorder` пишет `release_check` по ответу задания `item-link_*`, время берётся из `savedAt` в задании, а не из момента обработки), иначе сама проверка завершения становится первой; слишком рано - `ok:false`, `data.reason=SECOND_CHECK_PENDING`, `data.nextCheckAt` (то, что читает фронтенд), причина провала - `data.reason`/`data.httpStatus`. Дефекты, найденные тестами и исправленные: (1) снимок `project_completion` можно было удалить (триггер `0015` закрывал только UPDATE, а `tf_app` имеет DELETE) - миграция `0016` распространяет триггер на DELETE, тесты, которые подкладывают «завершённый проект», удаляют запись через `forgetCompletion` (отключение триггера владельцем на транзакцию); (2) `repository.renamed` брал имя из тела доставки, запоздавшая старая доставка возвращала старое имя - имя теперь читается у GitHub, как при `transferred`; (3) FR-GH-07 «тимлид уведомлён» не был реализован - потребитель `workspace.notifications` слушает `github.repo_unlinked` и создаёт уведомление `repo_unlinked` (код причины и id команды, без имён; своя отвязка тимлидом уведомления не даёт), текст в `i18n/ru/notifications.json`; (4) `parsers.test.ts` падал с `Cannot find package 'tsx'`: дочерний процесс разбора резюме запускался с `--import tsx` относительно рабочего каталога родителя (корень репозитория, где `tsx` не установлен) - адрес `tsx` теперь абсолютный (`import.meta.resolve`); (5) нестабильность CC-9 (503 «GitHub не отвечает» при параллельных файлах): двойник нумеровал установки с одного числа во всех мирах, а кэш токенов установки лежит в общем Redis под этим номером - миры выдавали друг другу чужие токены (401); старт номера теперь случайный; (6) `cc-slice6-races` считал ключи `gh_state:*` всего Redis - теперь только состояния своей команды.
Решения (зафиксированы тестами): AF-02 учитывает завершения с датой не позже `now()` БД, шаблонные хосты (`example.com/org/net`, `localhost` и поддомены) дают `FRAUD_BLOCK`, ключ адреса - хост и путь без схемы, регистра, запроса и конечных `/`; `issues.deleted` игнорируется, вклад закрытого issue остаётся; после `unsuspend` права тимлида возвращаются повторным прохождением установки.
