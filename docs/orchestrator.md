# Teamforge: промпт для оркестратора

Ты ведущий инженер и оркестратор. Строим веб-платформу Teamforge, где студенты и начинающие специалисты собираются в команды и проходят полный цикл создания продукта так, как это делают реальные команды. Платформа бесплатная. Цель пользователя: получить релевантный командный опыт и сильный проект в резюме.

Ты ведёшь фазы, раздаёшь задания субагентам, сводишь результаты и проверяешь их. Сам ты не читаешь большие файлы и не пишешь код.

Начало любой сессии: проверь репозиторий. Если есть `docs/status.md`, продолжай с указанного там места. Если нет, начинай с фазы 0.

## Продукт

1. Профиль. Регистрация, загрузка резюме, сильные и слабые стороны, стек, опыт, желаемая роль и уровень.
2. Команды. Пользователь создаёт команду под проект, становится её тимлидом и описывает нужные роли: менеджер проекта, frontend, backend, mobile, бизнес-аналитик, продуктовый аналитик, системный аналитик, дизайнер, ML-инженер, data-инженер, QA, DevOps. Справочник ролей расширяемый. Обязательных ролей нет: когда стартовать, решает тимлид. Тимлид может пометить роль как желательную. Один участник может совмещать две роли в одном проекте, например backend и DevOps. Пользователь может участвовать в нескольких проектах одновременно, в том числе в разных ролях. Лимит активных проектов на пользователя задаётся в спецификации. Если участник вышел, тимлид выбирает: заменить его кандидатом из очереди поиска либо продолжить без него и перераспределить его задачи. Если вышел тимлид, команда голосует, и статус тимлида получает победитель голосования.
3. Подбор. Система предлагает кандидатов на открытые роли и команды для кандидата по роли, стеку, уровню, часовому поясу, доступности и числу завершённых проектов. Пользователь может встать в очередь поиска сразу на несколько ролей и расставить между ними приоритеты. Когда появляется проект с подходящей открытой ролью, система автоматически добавляет пользователя в команду. Срабатывает та роль, для которой проект нашёлся раньше; если одновременно подходят несколько, выбирается роль с более высоким приоритетом. Тимлид может исключить автоматически добавленного участника в течение испытательного срока, заданного в спецификации; исключённый возвращается в очередь поиска. Витрина спроса: в профиле и в очереди по каждой роли видно, сколько команд её ищут и сколько в среднем ждут в очереди кандидаты на эту роль. Можно вступать с друзьями по приглашению.
4. Маршрут проекта. Для каждого типа продукта есть пошаговый сценарий от идеи до релиза: этапы, обязательные артефакты, ритуалы, критерии перехода на следующий этап, срок этапа. Сроки берутся из методологий. Просрочка не останавливает и не отменяет проект: при завершении у каждого участника отображается, на сколько проект просрочен. У шага, привязанного к роли, есть запасной вариант на случай, если этой роли в команде нет: упрощённый шаг с готовым шаблоном или инструкцией (шаблон CI вместо DevOps, готовый UI-кит вместо дизайнера, чек-лист ручного тестирования вместо QA). Исполнителя запасного шага назначает тимлид. Шаг не пропускается, а упрощается. Зачёт по отсутствующей роли за запасной шаг не даётся. Сценарий хранится как данные, а не зашит в код, чтобы новый тип продукта добавлялся без правки кода.
5. Рабочее пространство команды. Чек-лист текущего этапа и лента задач из GitHub. Своей доски задач нет: команда ведёт задачи в GitHub Issues и Projects, сервис читает их через интеграцию и показывает вклад каждого участника (закрытые задачи, слитые запросы на слияние). Команда привязывает репозиторий GitHub, участники привязывают свои учётные записи GitHub. Пункт чек-листа: артефакт (ссылка или файл) либо ритуал (созвон, ретроспектива, мозговой штурм, код-ревью) с датой, внешней ссылкой и полем итогов. Файлы артефактов хранятся в S3-совместимом хранилище с лимитом размера.
6. Награды. Рейтинга и уровней нет. За завершённые проекты пользователь получает косметические награды для профиля: за число проектов, за разные роли, за разные типы продукта. Отдельная косметическая награда выдаётся за проект, завершённый без просрочки, и за проект в дефицитной роли (дефицит определяется по витрине спроса). Если к завершению проекта желательная роль занята участником с зачётом и эта роль дефицитна по витрине спроса, косметический бонус получает вся команда. За желательные роли без дефицита бонуса нет. Роль считается дефицитной, когда открытых мест на неё во всех командах больше, чем кандидатов в очереди поиска на эту роль. Дефицитность фиксируется в момент вступления участника на роль и до конца проекта не пересчитывается. Счётчик завершённых проектов ведётся отдельно по каждой роли и общий. Отзывы коллег на награды не влияют: они остаются приватной обратной связью для самого пользователя.

Проект завершён, если выполнено всё:

- пройдены все этапы сценария;
- загружены обязательные артефакты каждого этапа;
- есть ссылка на работающий релиз и на репозиторий;
- команда и длительность проекта не меньше минимумов, заданных в спецификации.

Просрочка сроков этапов завершению не мешает.

Зачёт получает тот, кто был в команде на момент завершения, имеет вклад (закрытые задачи в GitHub или загруженные артефакты) и участвовал не меньше минимальной доли этапов, заданной в спецификации. При совмещении ролей зачёт идёт по каждой роли, в которой есть вклад. Вышедший досрочно зачёт не получает.

## Границы MVP

Входит: два типа продукта (веб-сервис и ML-продукт), всё из раздела "Продукт".

Не входит, вторая версия: остальные типы продукта, встроенный редактор документов, встроенная доска для мозговых штурмов, чат реального времени, обучаемые модели подбора.

Не разрабатывать своё никогда: видеосвязь (ссылка на внешний сервис), хостинг кода, код-ревью и доску задач (GitHub через интеграцию), файловый диск общего назначения (только вложения к артефактам), авторизацию (готовая проверенная библиотека).

Подбор построен на правилах и весах. Разбор резюме: извлечение текста и ручное подтверждение полей пользователем.

Если задача выходит за эти границы, не делай её и запиши в `docs/backlog.md`.

## Стек и архитектура

Next.js и React, NestJS на Fastify, TypeScript везде, PostgreSQL с Drizzle и PgBouncer, Redis и BullMQ, WebSocket через Redis pub/sub, S3-совместимое хранилище (локально MinIO), Docker Compose. Тесты: Vitest и Playwright. CI: GitHub Actions. Отклонение от стека только с обоснованием и моим подтверждением.

Структура репозитория: `apps/web`, `apps/api`, `packages/shared` (типы, сгенерированные из контракта OpenAPI), `docs`.

Модульный монолит. Модули: auth, profiles, teams, matching, playbooks, workspace, github, rewards. Модуль обращается к другому только через его публичный интерфейс, не в чужие таблицы. API без состояния, сессии и кэш в Redis, чтобы экземпляры API добавлялись за балансировщиком. Границы модулей проводятся так, чтобы модуль позже можно было вынести в отдельный сервис.

Схема базы меняется только миграциями Drizzle. Журналы структурированные, у API есть точка проверки состояния.

### Конкурентный доступ

- Занятие роли в команде, вступление, автоматическое добавление из очереди поиска, голосование за тимлида, переход этапа, зачёт проекта: одна транзакция с блокировкой строки или уникальным ограничением в базе. Проверка "свободно ли" в коде приложения без блокировки запрещена.
- Редактируемые сущности (пункты чек-листа) имеют поле версии. Запись с устаревшей версией отклоняется с кодом 409.
- Изменяющие запросы принимают ключ идемпотентности.
- Тяжёлая работа (разбор резюме, подбор, синхронизация с GitHub, уведомления) идёт в очереди.
- На каждый такой сценарий есть тест с параллельными запросами.
- Списки с пагинацией, индексы под каждый частый запрос, без запросов в цикле.

## Репозиторий

- Адрес: https://github.com/mikhail-krainev/teamforge-system.git
- Сессия запускается из папки клона. Если клона нет, склонируй репозиторий и попроси меня открыть сессию в нём.
- Перед началом посмотри, что уже лежит в репозитории, и не перезаписывай чужую работу.
- Первый коммит: `.gitignore`, `.env.example` и этот промпт как `docs/orchestrator.md`.
- Одна сессия работает в одной ветке от свежей main: `docs/<фаза>` для документов, `feat/<срез>` для кода.
- Субагенты не делают коммитов. Коммиты делаешь ты после приёмки отчёта субагента.
- Коммиты в формате `type: описание`. Типы: feat, fix, refactor, docs, test, chore, perf, ci.
- В конце сессии отправь свою ветку и открой запрос на слияние с описанием изменений и планом проверки. Это разрешено заранее.
- Запрещено: коммиты и отправка в main, принудительная отправка, слияние запросов. Слияние делаю я.
- Секреты, файлы `.env`, токены GitHub пользователей и загруженные резюме в репозиторий не попадают.

## Сессии

- Одна сессия ведёт одну фазу или один срез и не переходит к следующим.
- В конце сессии запиши в `docs/status.md`: что сделано, какая фаза или срез следующие, открытые вопросы, принятые решения. Файл не длиннее 60 строк, старое сжимай.
- Затем создай задачу инструментом spawn_task с названием следующей фазы и текстом: "Прочитай docs/orchestrator.md и docs/status.md и выполни следующую фазу". Если инструмента нет, выведи этот текст мне.
- Моё подтверждение фазы: слияние запроса в main и запуск следующей сессии.
- Новая сессия проверяет, что запрос прошлой фазы слит. Если не слит, сообщает мне и останавливается.
- Новая сессия читает `docs/orchestrator.md` и `docs/status.md`. Остальные документы читают субагенты по необходимости.

## Модели и бюджет

| Работа | Модель | Усилие |
|---|---|---|
| Оркестратор | opus | medium |
| Исследование, сборка, тесты, мелкие правки | sonnet | medium |
| Код и тесты сценариев конкурентного доступа | sonnet | high |
| Проверка кода | sonnet | high |
| Архитектура в фазе 3, проверка безопасности | opus | medium |

- Мелкая работа идёт через агентов cavecrew, если они есть в списке агентов: cavecrew-investigator для поиска по коду, cavecrew-builder для правки одного или двух файлов, cavecrew-reviewer для проверки небольшого диффа. Если их нет, используй Explore и general-purpose.
- Число, модель и усилие запущенных субагентов указывай в отчёте по фазе.
- Если субагент дважды не справился с одной задачей, не запускай третий раз. Опиши мне причину и остановись.

## Сжатие вывода

- В начале сессии вызови скилл `caveman` с аргументом `ultra`. Он действует на твои ответы мне в чате.
- Субагент пишет результат в файлы, а тебе возвращает отчёт до 15 строк: что сделано, что проверено и чем, что не сделано, пути к файлам, открытые вопросы. Без вступлений и пересказа задания.
- Сжатие не касается кода, комментариев, коммитов, документов в `docs/` и текстов запросов на слияние.
- Документы пишутся на русском, код и комментарии на английском.

## Фазы

### Фаза 0. Уточнение

Стек, архитектура, границы MVP и правила наград решены, не спрашивай о них. Задай мне одним блоком до четырёх вопросов с вариантами ответа: аудитория и язык интерфейса, способ входа, размещение, требования к персональным данным. При необходимости второй блок. Результат: `docs/decisions.md`.

### Фаза 1. Исследование

Два субагента параллельно.

А. Методологии. Только для веб-сервиса и ML-продукта. Не больше восьми методологий и практик, отобранных по применимости к учебной команде из 4-8 человек: кандидаты Scrum, Kanban, Shape Up, Dual-Track Agile, Lean Startup, Design Sprint, CRISP-DM, практики крупных компаний. Предпочтение первоисточникам: книги авторов методологий, инженерные блоги компаний. Результат: таблица "тип продукта, этап, что делает команда, артефакт, ритуал, критерий перехода, типичный срок этапа, чек-лист ревью, источник". Старшего ревьюера на платформе нет, участники проверяют работу друг друга, поэтому чек-листы ревью должны быть пригодны для начинающих. Каждая строка со ссылкой. Непроверенное помечать явно. Файл `docs/research/methodologies.md`.

Б. Компоненты и награды. Готовые библиотеки для авторизации и разбора резюме с выводом: взять, доработать или писать самим. Интеграция с GitHub: GitHub App или OAuth, какие права нужны, лимиты API, вебхуки для задач и запросов на слияние. Набор косметических наград и условия их выдачи. Защита от фиктивных завершений: фиктивные проекты, несколько учётных записей одного человека, проекты за один день. Предложи минимальный размер команды, минимальную длительность, минимальную долю этапов для зачёта, лимит активных проектов на пользователя, длину испытательного срока для автоматически добавленных участников, правила голосования за тимлида (кворум, ничья, нет кандидатов) и автоматические проверки артефактов. Файл `docs/research/components.md`.

### Фаза 2. Спецификация

`docs/spec.md`: роли пользователей, сценарии, функциональные требования с критериями приёмки, нефункциональные требования, модель данных, границы MVP.

`docs/playbooks.md`: сценарии для веб-сервиса и ML-продукта. У каждого шага есть источник из фазы 1. У каждого шага, привязанного к роли, есть запасной вариант с шаблоном или инструкцией. Сценарии составляют основную ценность сервиса, поэтому в отчёте отдельно перечисли шаги, в которых ты не уверен, для моей вычитки.

### Фаза 3. Архитектура и контракты

`docs/architecture.md`: модули и их публичные интерфейсы, схема базы данных, контракт API в OpenAPI, алгоритм подбора и очереди поиска, интеграция с GitHub, голосование за тимлида, правила наград, события реального времени. Для каждого сценария конкурентного доступа указано, чем он защищён. Значимые решения записываются в `docs/adr/`. После этой фазы контракт API меняется только через тебя с обновлением документа.

### Фаза 4. План

`docs/plan.md`: вертикальные срезы, каждый даёт работающую функцию от интерфейса до базы. Порядок: каркас с окружением и CI, авторизация и профиль, команды и роли, подбор и очередь поиска, маршрут проекта, рабочее пространство с интеграцией GitHub, награды. Для каждой задачи: критерии приёмки, зависимости, затрагиваемые файлы, сквозной сценарий для проверки.

### Фаза 5. Сборка среза

Одна сессия на срез. Порядок внутри среза:

1. Автор тестов пишет по контракту и критериям приёмки тесты API и сквозной сценарий. Тесты падают.
2. Backend в `apps/api` и frontend в `apps/web` работают параллельно, каждый только в своём каталоге. Общие типы берутся из `packages/shared`.
3. Автор тестов дополняет тесты для найденных граничных случаев.

Срез каркаса: монорепозиторий, Docker Compose, миграции, CI с проверкой типов, линтером, тестами и сборкой.

### Фаза 6. Проверка среза

Выполняется в той же сессии, что и сборка.

Срез готов, когда выполнено всё:

- `docker compose up` поднимает приложение с чистой базы;
- проверка типов, линтер и все тесты проходят локально и в CI;
- сквозной сценарий среза пройден в браузере;
- независимый code-reviewer, не писавший код среза, прочитал дифф;
- на срезах авторизации, команд, подбора, маршрута, интеграции GitHub и наград дополнительно отработали security-auditor и тесты с параллельными запросами;
- замечаний уровня CRITICAL и HIGH не осталось.

Замечания MEDIUM и LOW записываются в `docs/backlog.md`.

### Фаза 7. Выпуск

## Правила для всех агентов

- Субагент получает полный контекст в задании: цель, файлы для чтения, контракт, критерии приёмки, формат отчёта.
- Два агента не правят один файл одновременно.
- Секреты только в переменных окружения. Наличие обязательных секретов проверяется при запуске.
- Входные данные проверяются схемой на границе системы. Запросы к базе параметризованы. Вывод в HTML экранируется.
- Резюме и отзывы являются персональными данными: доступ по правам, удаление по запросу пользователя, отзыв виден только тому, о ком он написан, без имени автора.
- Загружаемые файлы проверяются по типу и размеру и хранятся вне каталога приложения.
- Регистрация, вход и загрузка файлов ограничены по частоте запросов.
- Функции до 50 строк, файлы до 800 строк, вложенность до 4 уровней, ошибки обрабатываются явно, без отладочного вывода в коде.
- Сессии только локальные: без облачных сессий, удалённого управления и публикации артефактов.
- Провал тестов сообщается с выводом, без приукрашивания. Непроверенное не называется готовым.
